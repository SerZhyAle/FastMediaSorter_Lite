# Тактическая спецификация С11 (modern): асинхронное ядро - ничто сетевое не блокирует UI

Статус: частично реализовано 2026-07-16 - У-02, У-03(б), У-07, У-11, У-12 сделаны; У-03(в) и У-01 - см. §0.1
Дата: 2026-07-16, ревизия 1
Родитель: [SPECIFICATION_VIEWER_CORE_AUDIT_DOTNET10.md](done/SPECIFICATION_VIEWER_CORE_AUDIT_DOTNET10.md)
Заменяет: утверждённую часть [С7](SPECIFICATION_VIEWER_CORE_S7_MODERN_PIPELINE.md), [С8](SPECIFICATION_VIEWER_CORE_S8_MODERN_FILEOPS.md), [С9](SPECIFICATION_VIEWER_CORE_S9_MODERN_FOLDER.md), [С10](SPECIFICATION_VIEWER_CORE_S10_MODERN_UX.md)
Сборки: **только .NET 10 mainline** (за швом `#If Not NETFRAMEWORK`; net48 не меняется вообще)

## 0. Почему именно этот срез

Состав утверждён владельцем 2026-07-16 **по фактической конфигурации**, а не по общей теории.
Что показал реестр рабочей машины (`HKCU\..\SZA\FastMediaSorter`):

| Настройка | Значение | Что из этого следует |
|---|---|---|
| `ImageFolder` | `\\p7\_i\output` | рабочая папка - **сетевая шара**; 9 из 11 недавних папок - её подпапки |
| `MoveOn4` | `\\p7\down` | единственный приёмник, и это **другая шара** - перенос идёт копированием по проводу |
| `UseIndependentThreadForOperationsWithFiles` | `0` | фоновые операции выключены → **каждый перенос морозит окно на всю передачу** |
| `SortDir` | `0` (abc) | сортировка по имени: размер и дата файлов **не нужны**, а сканер читает их для каждого файла (stat по SMB) |
| `mediaViewedCount` / `RunsCount` | 7862 / 147 | ~53 файла за запуск - листание это и есть работа |

Вывод, определивший срез: **всё, что этот пользователь делает, идёт по SMB, и почти всё это
сейчас выполняется на UI-потоке.** Отсюда состав.

### 0.1 Замеры на рабочей шаре (2026-07-16) - и что они опровергли

Перед реализацией предпосылки были **измерены на `\\p7`**, и две из них не подтвердились.
Числа здесь, чтобы к этому вопросу не возвращаться:

| Что | Замер | Вывод |
|---|---|---|
| `f.Length` + `f.LastWriteTime` из `EnumerateFiles`, 5032 файла | **+3 мс** (8 мс против 5 мс) | `EnumerateFiles` отдаёт `FileInfo` уже заполненным из данных перечисления - **stat-а на файл нет**. Для контраста, принудительный `Refresh()` на каждый файл - 356 мс. **Пункт (а) отменён**: экономить нечего |
| Первый обход **холодной** папки `\\p7\_i\output\C` (15 779 файлов) | **1 097 мс** | окно стоит ~1.1 с при открытии крупной папки → (в) обоснован, но это ~1 с, а не «секунды» |
| Обход + фильтр + сортировка `\\p7\_i\output` (5030 медиа) | ~157 мс (с накладными PowerShell) | тёплая папка - не проблема |
| Чтение + декод фото 1.3 МБ с шары | 9 мс чтение + **53 мс декод** | по сети идёт быстро; дорог **декод (CPU)**, а не сеть |
| **Состав рабочей папки** | **5011 `.mp4` из 5032**, 26.5 ГБ, ролики до **212 МБ** | **приложение используется как видео-сортировщик, а не фото** |

**Главное следствие - У-01 переоценён.** Конвейер декодирования обслуживает *изображения*,
а их в рабочей папке 19 штук из 5032. Выигрыш там, где владелец реально работает, близок к
нулю; ценность остаётся только для папок с фото (`C:\Common`, `OneDrive\Документы`), где
шаг назад стоит 5-60 мс - заметно, но это не «фриз». При этом У-01 - самый рискованный
пункт среза (совместное владение `Image` между кэшем и `PictureBox`).
→ **У-01 отложен до решения владельца**, обоснование выше.

**У-02 подтверждён, но скромнее, чем я писал.** Перенос на `\\p7\down` - это действительно
копирование **через провод между разными шарами**. Замер на настоящем файле:

| Файл | Копия шара→шара | Скорость |
|---|---|---|
| 43.9 МБ | **198 мс** | 221 МБ/с |
| 212 МБ | 231 мс | 919 МБ/с (явно из кэша клиента - холодная будет ~1 с) |

Канал до p7 быстрый, поэтому заморозка окна на перенос - **~0.2 с**, а не «несколько
секунд», как утверждала первая редакция. Это заметный рывок при быстрой раскладке (жмёшь
4 - окно дёргается), но не катастрофа. Очередь его убирает полностью и заодно снимает
отказ «!Ждите..» при включённой галке - обоснование остаётся, масштаб честный.

**Сделано:** У-02 (очередь), У-03(б) (двойной обход), У-12 (эвристика рескана),
У-07 (коллизии имён), У-11 (пробы доступности).
**Осталось:** У-03(в) (сам скан в фон - холодная папка на 15k даёт ~1.1 с неподвижного
окна; правка требует механики продолжения в конвейере), У-01 (см. выше - ждёт решения).

**Замер после стадии:** запуск на `\\p7\_i\output` (5030 медиафайлов) → первый кадр за
**1.96 с** (в это время входит старт self-contained .NET 10, чтение реестра и скан).

**Отложено** (решение владельца, с причинами - чтобы не пересматривать заново):
- **У-06 (корзина)** - на `\\p7` корзины не существует: Windows не хранит удалённое с
  сетевых шар. Основной сценарий владельца фича не покрывает.
- **У-15 (LockBits)** - `color_scheme = 1` (чёрный): динамический анализ цвета не
  выполняется вообще, обоснование наполовину отпало.
- **У-04 (watcher)** - сценарий («output», файлы прилетают) реален, но FileSystemWatcher
  по SMB ненадёжен; нужен выбор между ним и дешёвым опросом.
- **У-09 (слайдшоу ждёт видео)** - конфликтует с `IsVideoLoop = 1`; нужно решение.
- **У-10 (async Stop)** - сначала измерить; неверный `await` вернёт «файл занят».
- **У-05, У-08, У-13, У-14** - ценность не подтверждена этой конфигурацией.

## 1. У-03 + У-12: скан каталога вне UI-потока

Файлы: [Main_Form.FileScanning.vb](../../src/Main_Form.FileScanning.vb),
[Main_Form.MediaLoading.vb](../../src/Main_Form.MediaLoading.vb),
[Main_Form.Lifecycle.vb](../../src/Main_Form.Lifecycle.vb).

Две вещи (третья отменена замером - см. §0.1):

**~~(а) Не читать метаданные, которые не нужны.~~ ОТМЕНЕНО.** Предполагалось, что
`f.Length`/`f.LastWriteTime` стоят по round-trip на файл. Замер: **+3 мс на 5032 файла** -
`EnumerateFiles` отдаёт `FileInfo` уже заполненным. Экономить нечего.

**(б) Убрать двойной обход при старте.** [Lifecycle.vb](../../src/Main_Form.Lifecycle.vb)
перечисляет папку целиком (нефильтрованный `Count`) только чтобы проверить сохранённый
индекс, а потом `GetFiles` обходит её второй раз. Проверка не нужна: клампы в
`Mode_Files` и так приводят индекс в границы, а `LoadFiles` сам сообщит о пустой/
недоступной папке. **Эта правка безопасна и для net48** - чистое удаление лишнего обхода,
шов не нужен.

**(в) Сам скан - в `Task.Run` с отменой,** а UI остаётся живым.

Асинхронность **не должна расползтись** по ~30 вызывающих `ReadShowMediaFile`. Приём -
продолжение вместо `await` в конвейере:

```vb
''' <summary>True - список готов, работаем дальше в этом же вызове. False - скан
''' запущен, и ReadShowMediaFile будет вызван ЗАНОВО с тем же режимом, когда он сядет.
''' Так асинхронность заперта в одном месте, а конвейер остаётся синхронным.</summary>
Private Function EnsureFolderList(mode As String, force_Rescan As Boolean) As Boolean
```

- Состояние: `folder_List_Loaded_For` (папка, которой принадлежит текущий список) вместо
  эвристики «`current_File_Index = 0` → перечитать» (**это и есть У-12**: сейчас R на
  первом файле сетевой папки запускает полный рескан уже загруженного списка).
- Отмена: `CancellationTokenSource` на скан; смена папки → `Cancel()` + результат
  отбрасывается по счётчику поколения (та же схема, что `media_Generation`).
- Продолжение вызывает `ReadShowMediaFile(mode, is_Continuation:=True)` - в обход
  40-мс троттлинга (это не действие пользователя, а вторая половина его же действия).

## 2. У-01: конвейер декодирования

Файл: новый `src/MediaCache.vb` (целиком `#If Not NETFRAMEWORK`) +
[Main_Form.MediaLoading.vb](../../src/Main_Form.MediaLoading.vb).

Сегодня кэшируется **ровно один файл вперёд**: любое «назад», прыжки ±10/±100 и промахи
декодируют синхронно на UI-потоке (`File.ReadAllBytes` + `Image.FromStream` + EXIF). По
сети это фриз на каждом шаге назад, при том что вперёд летит мгновенно.

```vb
Friend NotInheritable Class MediaEntry
    Public Property Path As String
    Public Property WriteTimeUtc As DateTime   ' ключ вместе с путём: перезаписанный снаружи файл обязан перечитаться
    Public Property Picture As Image
    Public Property Data As IO.MemoryStream    ' Nothing, если декодер отдал отвязанный образ
End Class
```

- Декод в `Task.Run` через **существующий шов** `LoadImageWithStream`/`ImageDecoderProvider` -
  декодеры не трогаем.
- LRU на 5 записей (prev-1, prev, current, next, next+1), вытеснение с `Dispose`.
- Префетч **в обе стороны**, направление берётся из `is_Nav_Direction` (введено в С3).
- Отмена по поколению навигации (`media_Generation`, введено в С4).
- **Двойная буферизация сохраняется**: меняется только доставка образа в бокс.

**Владение образом - главный риск стадии.** Кэш и `PictureBox` ссылаются на один `Image`.
Правило: диспозит **только** кэш, и только если образ не присвоен видимому боксу.
Следствия: `ReleaseActiveMedia` (С2) в modern зовёт `media_Cache.Evict(path)`;
`StartGifLoopPlayback` держит ссылку - вытеснение обязано звать `StopGifLoopPlayback`;
`RotateActiveImage` мутирует образ **на месте** → инвалидировать запись при повороте.

## 3. У-02: очередь файловых операций

Файл: новый `src/FileOpQueue.vb` (`#If Not NETFRAMEWORK`) +
[Main_Form.FileOperations.vb](../../src/Main_Form.FileOperations.vb).

Тип `FileOp` уже введён в [С2](done/SPECIFICATION_VIEWER_CORE_S2_FILEOPS.md) и несёт всё
нужное - здесь меняется **только транспорт**: понятие «воркер занят» исчезает.

- `Channel(Of FileOp)` (unbounded, single reader) + один consumer-`Task`.
- Завершение маршалится на UI: статус, а при ошибке - откат оптимистичной мутации списка
  (`InsertFileIntoList`, С2).
- `PoMove`/`Undo`/DEL в modern кладут операцию в канал: без `IsBusy`, без отказа.
- **Галка «независимый поток» в modern фактически уходит в прошлое** - операции всегда
  фоновые. Это осознанная смена семантики (у владельца галка выключена, и именно поэтому
  каждый перенос на `\\p7\down` морозит окно).
- `FormClosing`: `Await DrainAsync(5s)` вместо ожидания сигнала (сигналы Б-36 остаются
  для net48).
- При `PendingCount > 1` показывать «в очереди: N» - хвост операций должен быть виден.

## 4. У-07: коллизии имён

Файл: [Main_Form.FileOperations.vb](../../src/Main_Form.FileOperations.vb).

`ResolveDestinationCollision(dest)` → свободное имя в стиле проводника

## 5. У-11: пробы доступности без блокировки

Файл: [Main_Form.Lifecycle.vb](../../src/Main_Form.Lifecycle.vb).

Классификация исключений (missing / denied / network) и число попыток **сохраняются один
в один** - меняется только исполнение: `Task.Run` + `Task.Delay` вместо
`Thread.Sleep` на UI-потоке, общий дедлайн ~10 с, статус «проверяю доступность..».

- `ProcessArgument` становится `Async Sub` → после `Await` проверять `media_Generation`.
- **Риск порядка старта**: `Form1_Load` больше не гарантирует, что к `Main_Form_Shown`
  файл загружен. Проверить первый показ перспективы (гейт `is_form_shown`) при запуске с
  файлом в командной строке.
- Обработчик `WM_COPYDATA` обязан возвращаться мгновенно (ставить аргумент в очередь) -
  иначе процесс-отправитель ждёт нашу сетевую пробу.

## 6. Приёмка

Все сценарии - на **сетевой** папке (`\\p7\_i\output\*`), иначе они ничего не доказывают.

1. **Открытие папки**: окно остаётся отзывчивым (двигается, статус «чтение каталога..»),
   первый файл появляется по готовности; смена папки на ходу - показана вторая, результат
   первого скана не всплывает.
2. **Старт**: восстановление последней сетевой папки - **один** обход каталога
   (в логе одно `w1095: GetFiles..`), время до первого кадра заметно меньше.
3. **Листание назад** по папке с крупными фото: переходы такие же мгновенные, как вперёд;
   окно не «белеет».
4. **R на первом файле**: рескана нет (в статусе не мелькает «чтение каталога.. ждите!»).
5. **Раскладка**: хоткей переноса на `\\p7\down` - следующий файл показан **сразу**, не
   дожидаясь передачи; серия из 10 нажатий подряд доезжает целиком, в статусе «в очереди: N».
6. **Коллизия**: перенести файл с именем, которое уже есть в `\\p7\down` → создан
   `name (2).ext`, статус показывает фактическое имя; U возвращает **именно его**.
7. **Ошибка операции**: занять файл-приёмник эксклюзивно → откат, файл остался в списке,
   очередь не встала.
8. **Уснувшая шара**: открыть файл с недоступного `\\p7` → окно **не** висит, статус
   «проверяю доступность..», через ~10 с - «Сетевой ресурс недоступен»; всё это время
   можно листать локальную папку.
9. **Память**: пролистать 500 файлов → рабочий набор не растёт линейно (LRU ≤ 5 образов).
10. **Операции над файлом из кэша**: DEL/перенос показанного файла проходит (файл не
    залочен потоком кэша).
11. **net48 без регрессий**: x86 собирается и ведёт себя как до стадии (кроме 1(б) -
    удаления лишнего обхода, оно общее).
