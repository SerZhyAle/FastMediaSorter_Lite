## 1. Цель

Обменяться с командой проекта DOC2HTML опытом реализации двух связанных задач:

1. распознавание текста на изображениях с получением геометрии слов, строк и блоков;
2. отрисовка распознанного или переведённого текста строго на исходном месте на картинке.

Результат обмена должен дать проверяемые решения, которые можно применить к OCR-overlay
в FastMediaSorter_Lite и, при необходимости, вернуть в DOC2HTML. Это исследовательская
спецификация: она не меняет пользовательское поведение и не предписывает немедленную
переработку текущего OCR-пайплайна.

## 2. Контекст

В FastMediaSorter_Lite уже есть OCR-перевод с неразрушающим overlay поверх текущего
`PictureBox`. Координаты OCR-блоков хранятся в пикселях исходного изображения, а при
отрисовке переводятся в координаты видимой области. DOC2HTML решает близкую задачу для
HTML-результата: распознаёт текст на картинке и размещает переводимые плашки в браузере.

Оба проекта должны сравнить не только используемый OCR-движок, но и весь путь геометрии:

```text
исходная картинка -> OCR bounding boxes -> группировка текста -> хранение координат
                  -> image-to-view transform -> плашка/HTML-элемент -> текст внутри неё
```

### 3.1 Получение геометрии OCR

## 5. Проверяемые инварианты для обоих проектов

1. Единственный источник истины для OCR-геометрии - пиксели ориентированного исходного
   изображения (`imageWidth`, `imageHeight`).
2. Любая предобработка OCR обязана сохранять матрицу преобразования, позволяющую вернуть
   прямоугольники в эту систему координат.
3. Рендер использует одну явную трансформацию `image -> viewport`; координаты не
   пересчитываются цепочкой независимых коэффициентов в разных слоях.
4. Плашка не должна смещаться при resize, масштабировании, полноэкранном режиме и
   повороте - меняется только преобразование viewport.
5. Длинный перевод не изменяет якорную точку исходного OCR-блока. Его поведение должно
   быть предсказуемым и зафиксированным в UI-правиле.
6. Отладочное отображение исходного OCR-бокса и итоговой плашки должно быть доступно
   разработчику без изменения данных OCR.

## 6. Кандидат на общий контракт данных

Для сравнения реализаций использовать нейтральный JSON-представитель. Это не требование
перевести оба проекта на один формат, а средство сверки геометрии.

```json
{
  "image": { "width": 2400, "height": 1600, "orientation": 1 },
  "blocks": [
    {
      "id": "b-001",
      "text": "Source text",
      "translation": "Перевод",
      "confidence": 92.4,
      "box": { "x": 320, "y": 180, "width": 640, "height": 96 },
      "rotationDegrees": 0,
      "readingOrder": 1
    }
  ]
}
```

Для FastMediaSorter_Lite это соответствует направлению модели `OcrBlock`/
`OcrOverlayDocument`; при сравнении отдельно зафиксировать, какой угол и какая точка
являются началом координат.

> **`rotationDegrees` не заполняет ни одна сторона** (выяснено во втором раунде): у DOC2HTML OSD
> выключен в обоих используемых режимах сегментации, поэтому поле может быть только нулём, а у нас
> его источника нет вовсе. Читать этот ноль как «не повёрнуто» нельзя - он означает «неизвестно».
> Решение - убрать поле из контракта или пометить зарезервированным - остаётся за этим документом;
> спецификация реализации вынесла его в свои развилки, чтобы не потерялось
> ([точность OCR-overlay](../SPECIFICATION_OCR_OVERLAY_ACCURACY.md), §12.3).

## 10. Ответы DOC2HTML (получены 2026-08-12)

Сторона DOC2HTML держит две независимые реализации одного пайплайна - десктопное Go-приложение,
вызывающее CLI `tesseract`, и браузерное расширение на `tesseract.js`, - удерживаемые в паритете
общими константами и guard-тестами, парсящими оба исходника. Ниже - ответы в порядке вопросов §3.

### 10.1 Получение геометрии OCR (ответ на 3.1)

- Движок: Tesseract 4/5, модели `tessdata_fast` 4.0.0. Go читает **TSV** из stdout
  (`-c tessedit_create_tsv=1`), расширение - воркер `tesseract.js`, по одному на язык.
- TSV даёт пять уровней: page, block, paragraph, line, word. Читаются **три**: page (размер
  изображения), **line** (прямоугольник), word (текст и confidence). Боксы block и paragraph
  **намеренно отбрасываются**: доверие к ним приводит к плашке, накрывающей рисунок, который
  движок свернул в «абзац».
- Система координат - пиксели исходного изображения. Предобработка: DPI оценивается как длинная
  сторона, делённая на предполагаемые 11 дюймов (сырое число пикселей - плохой критерий: скан
  страницы проходит порог в 1000 px и при негодных 100 DPI). Ниже 120 DPI изображение
  ресемплится 2× (Catmull-Rom в Go, canvas в JS), и координаты делятся обратно после
  распознавания. DPI в любом случае **объявляется движку** (пол 70) - именно это заставляет
  анализ раскладки разделять соседние области (два речевых баббла) вместо их слияния в одну.
- Go дополнительно копирует файл во временный ASCII-путь: Tesseract/Leptonica открывают путь
  через ANSI-кодовую страницу Windows и молча падают на кириллическом имени файла.
- Порог: строка со средним confidence слов **ниже 50** отбрасывается. Реальный текст даёт
  примерно 80-97, галлюцинации по рисунку - 0-50. Без этого шума порог превращается в
  непрозрачную плашку поверх графики, а его завышенные боксы ещё и раздувают шрифт.
  Rescue-проходы (§10.5) сравниваются по более строгому полу 80.

### 10.2 Группировка и порядок чтения (ответ на 3.2)

- Выжившие строки сливаются в порядке чтения в одну плашку на серию вертикально соседних,
  горизонтально пересекающихся строк.
- Соседство считается по **шагу строк** (top-to-top), а не по зазору между чернильными боксами,
  и это различие нагружено смыслом: капитель без выносных элементов даёт бокс заметно ниже
  собственной строки, поэтому тест по зазору разрывает один баббл на три плашки и отдаёт
  переводчику три обрывка фразы.
- Эталонный шаг - **медиана по всему изображению**, считается только по парам, которые делят
  колонку, идут вперёд и отстоят не более чем на 3 медианных высоты (дальше это разрыв секции,
  а не интерлиньяж). Коэффициент допустимого шага - 1.2.
- Бокс плашки - объединение её строк, шрифт следует медианной высоте строки.
- Фильтр переводимости: кластер сохраняется, только если есть что переводить - минимум 5 букв,
  хотя бы одна гласная (согласная каша - это шум OCR), не целиком URL / e-mail / домен / путь,
  и среди токенов с буквами хотя бы половина похожа на настоящие слова. Короткие CJK-фрагменты
  обходят правила гласной и длины.
- Явного описания порядка чтения между блоками, RTL/CJK-направления и вертикальных надписей в
  ответе нет - см. §13.

### 10.3 Точное размещение результата (ответ на 3.3)

- Вывод никогда не перерисовывает изображение. Картинка оборачивается в блочный контейнер с
  `aspect-ratio: W / H` и `container-type: inline-size`; сам `img` - `width:100%` с обнулёнными
  `margin` и `max-height`, чтобы CSS-reset страницы-хоста не сдвинул плашки.
- Каждая плашка позиционируется **в процентах натурального размера** изображения: `left`, `top`,
  `width` и `min-height` (именно min-height, чтобы плашка могла вырасти). Шрифт задаётся в
  `cqw` - процентах ширины контейнера - и выводится из медианной высоты строки блока,
  умноженной на фактор подгонки **0.92**. Проценты плюс `cqw` - то, что даёт переживание
  отзывчивого масштабирования вообще без JS.
- Цвет берётся из изображения: белая плашка поверх цветной панели хуже, чем её отсутствие.
  Под каждой плашкой изображение подвыбирается (~6000 пикселей, прозрачные пропускаются). Фон -
  **медиана** цвета по всему блоку; чернила - среднее по пикселям, отличающимся от фона более
  чем на 90 (сумма канальных расстояний), и **только в пределах первой строки** (настоящий
  текст живёт там, а не в графике ниже по слитому блоку). Два гварда: если чернильных семплов
  меньше ~1.5 %, берётся near-black/near-white фолбэк; если итоговый контраст по luma ниже 55,
  фолбэк заменяет сэмплированные чернила.
- **Ring-тест ориентации.** Медиана исходит из того, что текст - меньшинство в собственном
  боксе. Для основного текста в баббле это верно, для тяжёлой дисплейной капители - нет: её
  штрихи покрывают больше площади тесного бокса, чем бумага между ними, и результат становится
  точной инверсией цветов. Поэтому ориентация решается по тому, что **снаружи** блока: полоса
  шириной в одну высоту строки (минимум 2 px) сверху, снизу, слева и справа; если больше её
  пикселей ближе к цвету чернил, чем к цвету бумаги, - при минимум 40 проголосовавших семплах -
  пара меняется местами. Снаружи, а не внутри, потому что у тесно обведённой капители штрихи
  лежат на самих границах бокса.
- Переполнение при длинном переводе: после раскладки и снова при каждой подмене текста плашка
  перефитится - высота прижимается к исходной области, затем `cqw`-шрифт уменьшается шагами
  8 % (минимальный шаг 0.3, пол - 50 % базового, не более 40 итераций), пока содержимое не
  перестанет переполнять. Если и на полу не влезло, бокс отпускается в `height:auto` и растёт
  вниз - **не обрезается никогда**. При выключенном JS деградация - CSS `overflow:hidden`.
- Исходный текст визуально не удаляется никаким inpainting: ни один пиксель изображения не
  меняется, перекрывает его непрозрачная плашка.
- Порядок операций различается по изданиям: в десктопном пайплайне overlay накладывается **до**
  шага перевода, чтобы текст плашек переводился тем же движком, что и остальная книга; в
  расширении плашка остаётся на исходном языке и помечается через `<html lang>` (код Tesseract
  отображается в BCP-47), из-за чего браузер сам предлагает перевести страницу.

### 10.4 Диагностика и тестирование (ответ на 3.4)

- `DOCHT_OCR_DIAG=<file>` заставляет десктопное приложение дописывать по одной JSON-строке на
  наложенное изображение: размер картинки и для каждого блока - текст, бокс, высота строки,
  итоговый inline-стиль и сэмплированные цвета. Значения пересчитываются **теми же чистыми
  функциями**, что использовал рендер, поэтому включение диагностики не может изменить вывод.
- `tools/ocrlab` - лаборатория визуальной точности: обе реализации прогоняются по одному корпусу
  одним пакетом метрик с одной схемой доказательств.
- Дрейф общих констант между реализациями ловят guard-тесты, парсящие оба исходника
  (`tests/parity_test.go`, `extension/test/*.test.mjs`).
- Измерения, стоящие за screen-проходом и ring-тестом: `DEV/research/ocr_halftone_2026-08-12.md`
  и `DEV/research/ocr_display_lettering_2026-08-12.md`.
- Числового допуска на ошибку позиционирования в ответе нет - см. §13.

Формат диагностической строки (образец из ответа):

### 10.5 Rescue-лестница и halftone (сверх заданных вопросов)

Ответ содержит слой, о котором §3 не спрашивал, но который прямо относится к «почему на части
картинок не находится текст».

- Лестница запускается **только когда не прочиталось ничего**. Место, где распознавание тихо
  умирает, - цвет: пороговик по умолчанию считает Otsu по каждому каналу RGB и признаёт пиксель
  чернилами лишь там, где согласны все три; на насыщенной графике (кирпично-красная панель за
  белым бабблом, печатный плакат) каналы делят картинку в трёх разных местах и маска приходит
  в распознавание без текста.
- Рунги идут по яркостной копии, каждый меняет ровно одно решение: 1) серый + глобальный Otsu;
  2) серый + плиточный Otsu Leptonica (порог локальный, подпись поверх градиента перестаёт в нём
  растворяться); 3) серый + PSM 11 sparse (без анализа раскладки - для входа, который не
  страница); 4) halftone-проход - единственный, меняющий пиксели, поэтому последний.
- Выполняются **все** рунги, побеждает сильнейший, где сила - число размещённых на изображении
  слов; при равенстве остаётся действующий результат. Правило «побеждает первый непустой» было
  прежним и измеримо проиграло: на одном плакате рунг 1 вернул одно слово и закончил поиск до
  того, как sparse-рунг вернул шесть строк.
- Детектор полиграфического растра не требует частотного преобразования: до 96 плиток 64×64
  раскладываются по картинке, каждая хай-пассится (пиксель минус среднее 3×3), отбрасывается при
  остаточной энергии ниже 3, затем автокоррелируется по обеим осям суммарно (растр повёрнут,
  поэтому ни одна ось в одиночку сигнал не несёт). Победивший лаг обязан быть локальным
  максимумом с пиком не ниже 0.30 от лага 0, попадать в 3-24 px, и минимум четверть текстурных
  плиток должна проголосовать за тот же лаг - именно это межплиточное согласие отделяет растр от
  JPEG-блокинга, зерна плёнки и гравюрной штриховки. Измеренный шаг задаёт ядро: сепарабельный
  гаусс с sigma = шаг / 4, обрезанный на 3 sigma (в расширении - CSS `blur(Npx)`, тот же гаусс).
  Гаусс, а не среднее по окну, потому что растр надо подавить и на гармониках, а у box-ядра в
  полосе подавления дыры.
- Для страницы, которая **прочиталась**, у screen-прохода есть вторая точка входа, и она
  аддитивна: все плашки основного прохода сохраняются, плашки screen-прохода добавляются лишь
  там, где площадь в основном не покрыта. Три части делают это безопасным: детектор ограничен
  площадью, не покрытой плашками (плитка, более чем наполовину покрытая существующей плашкой,
  перестаёт считаться уликой); кандидат отбрасывается, если более 0.2 **его собственной**
  площади уже покрыто, причём покрытие считается точным **объединением** существующих плашек
  через сжатие координат (сумма перекрытий двоила бы, а поштучная проверка пропускала бы
  кандидата, лежащего на стыке двух плашек); любой сбойный путь возвращает вход без изменений.
  Замер: screen-проход даёт +47 % и +18 % уверенных слов на двух реальных растрированных
  сценах и проигрывает там, где растра нет (16 уверенных слов против 0 на одной обложке) -
  аддитивное слияние берёт выигрыш без проигрыша.

### 10.6 Общие константы, к которым прибиты обе реализации DOC2HTML

| Константа | Значение | Что решает |
|---|---|---|
| Режим сегментации | PSM 3 / 11 | авто-анализ раскладки; sparse как rescue-рунг |
| Пол confidence строки | 50 | отсев галлюцинаций (в rescue-проходах 80) |
| Коэффициент шага кластера | 1.2 | насколько далеко может стоять следующая строка и всё ещё войти в плашку |
| Максимальное отношение интерлиньяжа | 3 | верхняя граница того, что считается интерлиньяжем при оценке шага |
| Апскейл / пол DPI | 2 / 120 | когда низкое разрешение увеличивается перед распознаванием |
| Предполагаемая высота страницы | 11 дюймов | знаменатель оценки DPI |
| Минимальный объявляемый DPI | 70 | ниже не объявляется |
| Делитель sigma для растра | 4.0 | шаг растра в sigma гаусса |
| Плитка / максимум плиток | 64 / 96 | окно автокорреляции; потолок работы независимо от размера |
| Границы шага растра | 3-24 px | ниже - шум сенсора, выше - грубее любого шрифта |
| Пол пика / доля голосов | 0.30 / 0.25 | пик автокорреляции против лага 0; доля согласных плиток |
| Максимум покрытия плитки | 0.5 | сколько плитки может покрывать плашка, оставаясь уликой |
| Максимум перекрытия при слиянии | 0.2 | выше - плашка screen-прохода считается дубликатом |
| Минимум голосов ring-теста | 40 | сколько нужно, чтобы поменять пару бумага/чернила |
| Фактор подгонки шрифта | 0.92 | шрифт плашки = медианная высота строки × это |

## 12. Переносимое в FastMediaSorter_Lite, по отношению «эффект к риску»

Порядок - предлагаемый; каждый пункт остаётся кандидатом, пока не оформлен спецификацией
реализации (см. §9 - настоящий документ ничего не предписывает менять). Такая спецификация
написана 2026-08-12 и отревизована по коду 2026-08-13:
[точность OCR-overlay](../SPECIFICATION_OCR_OVERLAY_ACCURACY.md) - пункты 1-5 разложены там по
стадиям S1-S5, пункт 6 отложен как S6. **Основание отсрочки S6 изменилось:** корпус передан во
втором раунде, поэтому «нечем проверить» больше не действует, и первым шагом отдельной
спецификации S6 становится замер на переданных сценах, а не перенос кода. Ревизия 2026-08-13
добавила к пунктам 1-5 то, чего в этом документе нет и быть не могло - следствия из нашего
собственного кода: общий для двух exe файл кэша, объединение плашки с текстовым прямоугольником,
бюджет роста вниз, версия пайплайна в ключе кэша.

**Состояние на 2026-08-13, вечер: пункты 1-5 реализованы** (стадии S1-S5, отчёт - §15
спецификации реализации). Автоматическая приёмка зелёная на обеих сборках; ручная часть §9 той
спецификации не прогонялась, поэтому тикет стоит в `BlockNeedUserTest`, а не закрыт. Пункт 6
(S6) не начинался и остаётся отдельным документом, первым шагом которого является замер на
переданном корпусе. Одно ограничение зафиксировано красным тестом и оставлено осознанно: абзац
крупного текста рядом с массивом мелкого рассыпается построчно (§15.3 там же) - снятая в 13.7
поправка чинила бы не тот случай.

1. **Кластеризация по шагу строк вместо зазора** ([OcrBlockBuilder.vb](../../../src/Ocr/OcrBlockBuilder.vb)):
   медианный шаг top-to-top по парам в одной колонке, коэффициент 1.2, верхняя граница 3 высоты.
   Дёшево, локально, чинит разорванные плашки бабблов и косвенно - размер шрифта, который
   считается по медианной высоте строк блока.
2. **Подгонка текста без обрезания** ([Main_Form.OcrOverlay.vb](../../../src/Main_Form.OcrOverlay.vb)):
   ввести фактор 0.92, а на полу шрифта перестать обрезать по `EllipsisWord` - вместо этого
   разрешить блоку вырасти. Сейчас длинный перевод молча теряет хвост.
3. **Цвет плашки из изображения**: медиана фона под блоком, чернила по первой строке,
   ring-тест ориентации, контрастный гвард. Самое заметное пользователю изменение; требует
   аккуратной работы с уже снятым `Bitmap` через `LockBits` в фоновом потоке, а не в `Paint`.
4. **Фильтр переводимости**: гласная, отсев URL/e-mail/пути, доля словоподобных токенов,
   исключение для коротких CJK. Дёшево, снижает число мусорных плашек.
5. **Отладочный режим** (инвариант 6 §5): показ исходных OCR-боксов и итоговых плашек поверх
   изображения плюс выгрузка JSONL той же формы, что в §10.4, посчитанная теми же функциями,
   что и рендер.
6. **Дороже и не первым**: объявление DPI движку, Otsu и плиточная бинаризация, детектор растра
   с аддитивным sweep. Польза именно в нашем сценарии (одиночная картинка, а не книга) не
   измерена. Прежняя приписка «и без общего корпуса (§4 п.3) её нельзя подтвердить» снята: корпус
   передан, подтвердить теперь есть чем - именно поэтому S6 начинается с замера.

## 13. Что осталось открытым

Второй раунд (см. §11 и §11.3 [спецификации реализации](../SPECIFICATION_OCR_OVERLAY_ACCURACY.md))
закрыл большую часть этого списка. Ниже - что закрыто и чем, и что действительно осталось.

**Закрыто:**

- Порядок чтения между блоками, RTL/CJK-направление, вертикальные надписи (вопрос 3.2). Ответ
  получен и он отрицательный: порядка чтения у них нет вообще (строки идут в порядке движка,
  сортировки нет), RTL-логики нет ни у одной стороны, вертикальное письмо не поддерживается.
  Для нас это не задача, а названное ограничение переносимой кластеризации.
- `rotationDegrees` (§6): выяснено, что поле не заполняет никто и ноль в нём означает
  «неизвестно». Осталось не выяснение, а решение - убрать или пометить зарезервированным.
- Материалы §4 переданы полностью: два минимальных примера с сырым выводом всех проходов, 13 сцен
  с проверенной человеком разметкой (8 синтетических с пиксельно точной истиной), замеры
  выравнивания на 100/125/150/200 % плюс планшет и телефон, описание преобразования координат в
  обе стороны.
- Как измеряется ошибка позиционирования (3.4): описание обратного преобразования - из
  отрисованного прямоугольника в пиксели исходника - и есть тот способ измерения, которого не
  хватало. Допуск на нашей стороне назначен самостоятельно: полвысоты строки блока
  (§9 спецификации реализации).

**Осталось открытым:**

- Переносы и дефисация: строки склеиваются одним пробелом, разорванное переносом слово так и
  уходит переводчику. Общее ограничение обеих сторон, ни у кого не решено.
- CJK-сцена и RTL-сцена с эталонной разметкой - в переданном корпусе не покрыты.
- Слияние двух колонок в один блок - известный дефект их группировки, удерживаемый порогом
  приёмки, а не исправленный.
- Поведение при печати (3.3): для нас неприменимо, у них плашки печатаются прозрачными.

Ни один из оставшихся пунктов не блокирует стадии S1-S5.
