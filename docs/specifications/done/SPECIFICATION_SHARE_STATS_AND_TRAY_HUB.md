## 0. Зачем это нужно (триггер)

Пользовательский запрос (дословно): SFTP-сервер (воркер) должен сам вести статистику -
следить за количеством и временем подключений, а из трея должно быть можно (а) запустить
новую программу-компаньон ([SPECIFICATION_SHARE_COMPANION_APP.md](SPECIFICATION_SHARE_COMPANION_APP.md)),
(б) запустить основную программу-просмотрщик и (в) посмотреть текущее состояние раздачи -
последнее подключение, количество обработанных файлов, дату последнего подключения и т.д.

Сегодня ([src/Main_Form.ShareTray.vb](../../../src/Main_Form.ShareTray.vb)) трей показывает
только МГНОВЕННОЕ состояние (запущено/нет, LAN-адрес) через `GetStatus` -
[src/Companion/WorkerIpc.vb](../../../src/Companion/WorkerIpc.vb) `WorkerStatus` не содержит ни
счётчика подключений, ни времени последнего подключения, ни счётчика файлов; воркер это
нигде не копит. Меню трея сегодня: Открыть / Показать штрихкод / Описание / Настроить /
Выключить / Выход - пункта «открыть другую программу» и пункта «текущее состояние» нет.

## 1. Цель и рамки

**Цель.** Две независимые, но связанные части:

- **(A) Статистика использования на стороне воркера.** Воркер сам копит и персистентно
  хранит счётчики подключений (всего / с момента запуска), время первого и последнего
  подключения, счётчик обработанных (переданных по SFTP) файлов - и отдаёт их по уже
  существующему IPC-каналу как аддитивное поле ответа `GetStatus`.
- **(B) Трей как «хаб» двух программ.** Меню трея получает пункт «Открыть <другую
  программу>» (симметрично: из трея LITE - открыть Companion, из трея Companion - открыть
  LITE) и пункт «Текущее состояние..», показывающий статистику из (A) плюс уже известное
  живое состояние (running/порт/адрес).

**В рамках:** протокольное расширение (аддитивное поле, без бампа `schemaVersion`),
дизайн хранения статистики на стороне воркера (на уровне спецификации - код воркера живёт
в отдельном репозитории, раздел 3.1), дизайн UI трея (новый пункт меню + окно статуса),
дизайн взаимного запуска программ.

**Вне рамок:** сама реализация (эта спецификация - только план, см. заголовок), любая
отправка статистики куда-либо за пределы ПК пользователя (раздел 4 - явный инвариант),
детализация по устройствам/IP как первичная фича (открытый вопрос O-3), любые изменения
самого SFTP-протокола, hostkey, credential.json.

## 3. Дизайн

### 3.1 Статистика на стороне воркера (Go, `P:\windows\fms_companion`)

Что копится (все счётчики - только локальные, на этом ПК, никуда не отправляются -
см. инвариант в разделе 4):

| Поле | Смысл |
|---|---|
| `totalConnections` | Число SFTP-подключений за всё время (персистентно, переживает перезапуск воркера) |
| `connectionsSinceStart` | Число подключений с момента текущего запуска воркера (сбрасывается при рестарте) |
| `firstConnectionAt` | UTC ISO8601 первого подключения за всё время; `""`, если ни разу |
| `lastConnectionAt` | UTC ISO8601 последнего подключения; `""`, если ни разу |
| `lastConnectionAddress` | LAN-адрес клиента последнего подключения, best-effort (может быть пустым, если недоступно на уровне SSH-транспорта) |
| `filesServedTotal` | Счётчик файловых операций чтения по SFTP за всё время (открытие/чтение файла; листинг каталога не считается) |
| `filesServedSinceStart` | То же с момента текущего запуска |

**Персистентность.** Новый файл `%LOCALAPPDATA%\FastMediaSorterCompanion\stats.json`,
отдельно от `shares.json`/`settings.json`/`hostkey`/`credential.json` - осознанно НЕ
трогаем существующие файлы (инвариант 3 `SPECIFICATION_ANDROID_FOLDER_SHARE.md` §3 не
нарушается: он про существующие файлы; сюда просто добавляется ещё один). Запись -
не на каждое событие (SFTP-сессия может быть короткой и частой), а с дебаунсом (например,
раз в несколько секунд, если счётчики изменились) - по аналогии с уже существующим у
воркера паттерном персиста порта в `settings.json`.

**Потокобезопасность.** Инкременты - через мьютекс/atomic на стороне воркера, т.к.
несколько SFTP-сессий (несколько телефонов, либо повторные подключения одного) могут
идти конкурентно.

**Порча файла.** Если `stats.json` повреждён/не читается при старте - воркер не должен
падать и не должен трогать остальные данные; счётчики просто стартуют с нуля (`ok=true`,
без падения сервера) - тот же принцип graceful degradation, что уже применяется к
остальной обвязке воркера.

### 3.2 Расширение IPC-протокола (аддитивно, версия схемы НЕ меняется)

Новое поле `stats` внутри `status` в ответе `GetStatus` (и, по побочному эффекту, в любом
другом ответе, где `status` уже присутствует), по образцу уже принятого в этом же
протоколе принципа «аддитивное поле, `schemaVersion` не меняется» (Appendix B
`SPECIFICATION_ANDROID_FOLDER_SHARE.md`, раздел «Multi-path export .. additive»):

```json
{
  "schemaVersion": 1,
  "ok": true,
  "status": {
    "running": true,
    "...": "как сегодня",
    "stats": {
      "totalConnections": 42,
      "connectionsSinceStart": 3,
      "firstConnectionAt": "2026-06-01T10:00:00Z",
      "lastConnectionAt": "2026-07-13T21:04:00Z",
      "lastConnectionAddress": "192.168.1.55",
      "filesServedTotal": 1830,
      "filesServedSinceStart": 12
    }
  }
}
```

Правила: поле `stats` отсутствует у СТАРОГО (ещё не обновлённого) воркера - клиент
(LITE/Companion) трактует `Nothing`/`null` как «данных пока нет», не как ошибку (тот же
принцип, что уже применяется к отсутствующим полям `Reachability`). На стороне клиента -
новый класс `WorkerStats` в [src/Companion/WorkerIpc.vb](../../../src/Companion/WorkerIpc.vb),
`WorkerStatus.Stats As WorkerStats` - зеркалит структуру таблицы 3.1, десериализуется тем
же `JavaScriptSerializer` (регистронезависимо, как и весь остальной DTO сегодня).

Дополнительный запрос (открытый вопрос O-4) - `ResetStats`: обнуляет счётчики (кроме,
возможно, `firstConnectionAt`/`totalConnections` - решить при реализации), полезен для
тестирования и «начать учёт заново».

### 3.3 Трей: «открыть другую программу»

Взаимный запуск, а не запуск в одну сторону - из трея LITE открывается Companion, из
трея Companion открывается LITE. Транспорт **переиспользуется**, не изобретается заново:
тот же мьютекс + `WM_COPYDATA`-паттерн, что уже спроектирован в
[SPECIFICATION_SHARE_COMPANION_APP.md §5](SPECIFICATION_SHARE_COMPANION_APP.md) для
пробуждения Companion из LITE, и уже РЕАЛИЗОВАН для собственного single-instance LITE в
`Application_Events.vb`/`Main_Form.vb` (`COPYDATASTRUCT`, `ProcessArgument()`,
`Show_Window_Command` = `::fms-show-window::`). Companion, когда появится, точно так же
умеет быть «отправителем» в сторону LITE, каким сегодня LITE является в сторону самого
себя (второй запуск exe).

Две временных развилки в зависимости от порядка реализации относительно
`SPECIFICATION_SHARE_COMPANION_APP.md` (см. открытый вопрос O-1):

- **(a) Промежуточный вариант**, если этот пункт реализуется РАНЬШЕ переноса трея в
  Companion: пункт «Открыть Fast Media Sorter Companion» в СЕГОДНЯШНЕМ
  `Main_Form.ShareTray.vb`, скрытый/задизейбленный, если `FastMediaSorterCompanion.exe`
  не найден рядом с LITE (программа ещё не установлена/не собрана) - тот же принцип
  graceful degradation, что уже применяется в `WorkerProcess.IsAvailable()` для воркера.
- **(b) Целевой вариант**, после реализации `SPECIFICATION_SHARE_COMPANION_APP.md`: трей
  живёт в Companion; его меню получает пункт «Открыть Fast Media Sorter» (LITE), который
  ищет `Mutex.TryOpenExisting("FastMediaSorterSingleInstanceMutex")` - не найден -> `Process.Start`
  LITE; найден -> `WM_COPYDATA` с маркером `::fms-show-window::` в его `WndProc` (уже
  готовый, ничего нового не требует). Пункт «Открыть <себя>» (Companion) в этом варианте
  тривиален - просто `RestoreMainWindow()`-аналог самого Companion (уже есть в его
  собственном плане, раздел 4.3 того файла).

Рекомендация (раздел 8, O-1): реализовывать сразу целевой вариант (b) вместе с
`SPECIFICATION_SHARE_COMPANION_APP.md`, не городить промежуточный (a) ради пункта меню,
открывающего ещё не существующую программу.

### 3.4 «Текущее состояние» (окно статистики)

Новый пункт меню трея «Текущее состояние..» / «Status..» - открывает небольшое немодальное
окно (не балун - данных слишком много для tooltip/balloon, раздел 2.2) с:

- Запущено: да/нет, порт, LAN/внешний адрес (уже есть сегодня в статус-опросе).
- Последнее подключение: дата/время + адрес клиента (`lastConnectionAt`/`lastConnectionAddress`).
- Подключений: всего / с момента запуска воркера.
- Обработано файлов: всего / с момента запуска воркера.
- Используется с (`firstConnectionAt`) - опционально, «когда функцией воспользовались
  впервые».

RU/EN по правилам стиля репозитория (дефис не тире, ё, `..` не `...`). Открытый вопрос
O-2: отдельное окошко (проще, работает независимо от того, где живёт трей) против
расширения существующего блока статуса в `Table_Form.Share.vb` (переиспользует уже
готовую вёрстку, но там, где трей уже переехал в Companion, `Table_Form` вообще не
участвует) - рекомендация: отдельное окошко, оно работает одинаково что в LITE, что в
Companion, не завязано на Settings-окно, которого в Companion, возможно, не будет в
сегодняшнем виде (O-4 спецификации Companion).

## 4. Инварианты

1. **Статистика - только локальный счётчик использования, не телеметрия.** Данные
   остаются в `stats.json` на ПК пользователя и в ответе `GetStatus` по локальному пайпу;
   никуда за пределы ПК (никакой аналитики/отправки на сервер) не передаются. Явно
   зафиксировано, т.к. слово «статистика» само по себе может читаться как телеметрия -
   в UI и в документации формулировка должна быть однозначной («только на этом ПК»).
2. Новый файл `stats.json` не заменяет и не трогает существующие файлы data-каталога
   воркера (`hostkey`, `credential.json`, `shares.json`, `settings.json`) - наследует
   инвариант 3 `SPECIFICATION_ANDROID_FOLDER_SHARE.md` §3, применённый к новому файлу:
   добавление разрешено, порча/удаление существующих - нет.
3. IPC-схема остаётся версии 1; `stats` - аддитивное поле, отсутствие трактуется как
   «данных нет», никогда как ошибка (наследует принцип из Appendix B того же файла).
4. Взаимный запуск программ (раздел 3.3) переиспользует уже существующий и проверенный в
   этом репозитории транспорт (мьютекс + `WM_COPYDATA`) - никакого нового IPC-канала
   между LITE и Companion не создаётся.
5. Ни статистика, ни трей-хаб не требуют новой элевации/firewall-исключений - вся
   обвязка работает поверх уже существующего opt-in гейта `ServerFeatures.IsEnabled()`
   (`SPECIFICATION_SHARE_SERVER_OPTIN_INSTALL.md`), ничего не меняет в этом гейте.
6. Все пользовательские строки - RU и EN, по правилам стиля репозитория (дефис не тире,
   ё, `..` не `...`).
7. Ни `v*`-тега, ни `tools/Release.ps1 -Push` как часть этой работы - релиз отдельная,
   подтверждаемая владельцем операция.

| Слово «статистика» пугает пользователей как намёк на телеметрию | Явная формулировка в UI и документации «только на этом ПК» (инвариант 1, раздел 4) |
| Пункт «Открыть Companion» ведёт в никуда, пока `SPECIFICATION_SHARE_COMPANION_APP.md` не реализован | Рекомендация - не показывать пункт до готовности Companion (раздел 3.3, вариант (a) как явно НЕ рекомендуемый путь) |
| Счётчик `filesServedTotal` может закрепить неверную семантику (например, считать ли повторное чтение одного файла в рамках одной сессии) до того, как воркер это точно определит | Зафиксировать точное определение «файловая операция» в самой Go-реализации при Ф0 - вне рамок VB-стороны этой спецификации |

## 8. Открытые вопросы (решение за пользователем)

- **O-1. Когда делать взаимный запуск программ (раздел 3.3)?** Сразу вместе с
  `SPECIFICATION_SHARE_COMPANION_APP.md` (рекомендуется - иначе пункт меню либо не
  показывается, либо ведёт в никуда), или отдельным промежуточным заходом в сегодняшнем
  LITE-трее с деградацией «Companion ещё не установлен»? Рекомендация - вместе.
- **O-2. Форма показа статистики.** Отдельное немодальное окошко (рекомендуется - работает
  одинаково в LITE и в Companion, не завязано на Settings-окно) или расширение уже
  существующего блока статуса в `Table_Form.Share.vb`? Рекомендация - отдельное окошко
  (раздел 3.4).
- **O-3. Детализация по устройствам.** Считать только агрегированные счётчики (как в
  таблице 3.1, рекомендуется для v1 - SSH-транспорт не гарантирует стабильный
  идентификатор устройства сверх IP-адреса) или пытаться различать «какой телефон
  подключился» (например, по SSH-клиентской строке)? Рекомендация - только агрегаты в v1,
  детализация по устройствам - будущая фаза при явном запросе.
- **O-4. Ручной сброс счётчиков.** Нужен ли запрос `ResetStats` (раздел 3.2) - например,
  кнопка «Сбросить статистику» в окне статуса? Рекомендация - да, простой и дешёвый в
  реализации, полезен после тестирования/при желании «начать учёт заново».
- **O-5. Байты, а не только файлы.** Считать ли объём переданных данных (байты), а не
  только количество файловых операций? Рекомендация - вне рамок v1 (усложняет Go-сторону
  ради не запрошенной пользователем метрики) - вернуться к вопросу, если будет отдельный
  запрос.
