# Спецификация: опция «Разрешать запуск в новых окнах»

Статус: **реализовано** (сборка 26.8.6.1446)
Дата: 2026-07-30, ревизия 1
Область: запуск процесса (`src/Application_Events.vb`, модель приложения `My.MyApplication`),
окно настроек `Table_Form` - страница «Файлы и система», запись настроек при выходе
(`src/Main_Form.Lifecycle.vb`).
Сборки: **только .NET 10 mainline** (`FastMediaSorter_LITE.exe`). В x86/net48
(`FastMediaSorter_x86.exe`) опции нет и поведение не меняется ни на йоту - политика
сопровождения из [CLAUDE.md](../../CLAUDE.md) запрещает добавлять туда функции.
Соседи: [SETTINGS_WINDOW_INVENTORY_DOTNET10.md](../contracts/SETTINGS_WINDOW_INVENTORY_DOTNET10.md)
(контракт окна настроек - его придётся дополнить), [SPECIFICATION_SETTINGS_EXPANSION.md](SPECIFICATION_SETTINGS_EXPANSION.md)
(механизм `ModernViewerPreferences`, куда садится новый параметр),
[SPECIFICATION_THIRTEEN_UI_LANGUAGES.md](SPECIFICATION_THIRTEEN_UI_LANGUAGES.md) (локализация строк).

**Решения, принятые до написания** (зафиксированы, чтобы не тормозить работу; изменить легко):

1. **По умолчанию выключено.** Обновление не меняет поведение ни одному существующему
   пользователю: повторный запуск по-прежнему передаёт файл уже открытому окну.
2. **Опция действует и на «пустой» повторный запуск** (без файла в аргументах). Сейчас такой
   запуск разворачивает существующее окно; при включённой опции он открывает новое окно с тем,
   что предписывает «Что открывать при запуске» (`StartupOpenMode`).
3. **Роль процесса решается один раз при старте и не передаётся.** Первое окно - **основное**
   (`primary`), все следующие - **дополнительные** (`secondary`). Настройки, позицию окна и
   состояние сессии в реестр пишет **только основное**. Иначе два процесса затирают один
   куст `SZA\FastMediaSorter` на выходе, и выигрывает тот, кто закрылся последним - ровно та
   беда, из-за которой мутекс в `Application_Events.vb` вообще появился.
4. **Дополнительное окно честно подписано** - суффикс в заголовке. Пользователь должен видеть,
   какое окно владеет настройками, без чтения документации.
5. **Переключатель работает «на следующие запуски»**, а не задним числом: уже запущенный процесс
   свою роль не меняет. Поэтому значение пишется в реестр **сразу при переключении**, а не при
   выходе - иначе снятая галочка не действовала бы до полного закрытия программы.

## 0. Зачем

Программа устроена как одно окно: второй запуск (двойной клик по файлу в проводнике, «Открыть
с помощью», перетаскивание на ярлык) не создаёт второе окно, а передаёт путь уже работающему
экземпляру. Для сортировки это правильно по умолчанию - один экземпляр, один куст настроек, один
набор каталогов-получателей. Но есть законные сценарии, где нужно именно второе окно.

| Ид | Ценность | Что |
|---|---|---|
| Н-1 | ★★★ | Сравнить два файла рядом: открыть два окна и поставить их бок о бок |
| Н-2 | ★★★ | Смотреть две папки одновременно (например разбирать «Загрузки», не теряя открытый архив) |
| Н-3 | ★★ | Один экран на видео, другой на изображениях - независимая громкость, слайдшоу, масштаб |
| Н-4 | ★★ | Несколько мониторов: по окну на монитор |
| Н-5 | ★★ | Опция выключена по умолчанию, поэтому существующее поведение не меняется вообще |
| Н-6 | ★★ | Настройки не портятся от нескольких окон: пишет только основное, и это видно в заголовке |

## 1. Поведение

Обозначения: **выкл** - опция снята (значение по умолчанию), **вкл** - опция стоит.

| Сценарий | выкл (как сейчас) | вкл |
|---|---|---|
| Двойной клик по файлу в проводнике, программа уже открыта | файл открывается в существующем окне, фокус не крадётся | открывается **новое окно** с этим файлом, фокус получает оно |
| Выделены 10 файлов, «Открыть» | все 10 уходят в одно окно (последний остаётся на экране) | **10 окон**. Так работает проводник: он запускает exe на каждый файл |
| Запуск exe/ярлыка без аргументов | существующее окно разворачивается и получает фокус | **новое окно**, содержимое - по `StartupOpenMode` |
| Перетаскивание файла на окно | грузится в это окно | **без изменений**: drag-drop - это не запуск процесса |
| Запуск `FastMediaSorter_x86.exe`, когда работает mainline | файл уходит в окно mainline | открывается окно x86-сборки (см. §8) |
| Второй запуск, пока первый ещё не показал окно | аргумент доезжает (за это отвечает уровень 1, см. §2) | новое окно |
| Закрытие окна | пишет настройки, позицию, последнюю папку и индекс | пишет **только основное** окно; дополнительные не пишут ничего (§4) |

Что опция **не** делает: не открывает второе окно по горячей клавише из уже запущенной
программы (это отдельная функция, см. §11 «Чего мы не делаем»), не синхронизирует окна между
собой и не превращает программу в MDI.

## 2. Почему это не однострочник: два уровня подавления второго окна

Единственное окно держат **два независимых механизма**, и опция обязана снять оба. Пропустить
один - значит получить «работает при запуске из-под отладчика и не работает из проводника».

| Уровень | Где | Что ловит | Как узнать |
|---|---|---|---|
| **1. VB single-instance** | `My Project\Application.Designer.vb`: `Me.IsSingleInstance = True` | повторный запуск **того же exe по тому же пути** - обычный случай проводника и ассоциаций. Второй процесс не доходит даже до события `Startup`: каркас передаёт аргументы по именованному каналу первому процессу и завершается, а в первом срабатывает `MyApplication_StartupNextInstance` | в логе есть `w0004: MyApplication_StartupNextInstance called`, но нет `n00-2` |
| **2. Мутекс + `WM_COPYDATA`** | `MyApplication_Startup` в [src/Application_Events.vb](../../src/Application_Events.vb) | всё остальное: **другое имя exe** (пара `FastMediaSorter_LITE.exe` / `FastMediaSorter_x86.exe`), другой путь (debug против release, переименованная копия). Мутекс `FastMediaSorterSingleInstanceMutex` от пути не зависит | `n00-2: Another instance detected via mutex, forwarding args` и далее `n00-3` |

Приёмная сторона у обоих уровней одна и та же по смыслу: `StartupNextInstance` вызывает
`Main_Form.ProcessArgument`, а `WM_COPYDATA` - `Main_Form.External_message`
([src/Main_Form.Lifecycle.vb:81](../../src/Main_Form.Lifecycle.vb#L81)), который делает то же
самое плюс разбирает `::fms-show-window::` и возвращает фокус прежнему окну. То есть уровень 2
функционально перекрывает уровень 1, но **не** перекрывает его по времени: канал каркаса живёт
с первых миллисекунд процесса, а окно, которому можно послать `WM_COPYDATA`, появляется гораздо
позже. Поэтому уровень 1 при выключенной опции сохраняем как есть - он и есть тот, кто не теряет
аргумент во время старта.

## 3. Механизм

### 3.1 Одно решение на процесс

Новый модуль `src/MultiWindowPolicy.vb`:

| Член | Что делает |
|---|---|
| `Friend Function AllowNewWindows() As Boolean` | читает **один** ключ реестра `AllowNewWindows` (`"1"`/`"0"`, по умолчанию `"0"`) и кэширует результат в `Shared` поле на весь процесс. На net48 - `#If NETFRAMEWORK Then Return False` без чтения реестра |
| `Friend Sub MarkInstanceRole(created_New As Boolean)` | вызывается из `MyApplication_Startup` сразу после создания мутекса; запоминает роль |
| `Friend Function IsSecondaryInstance() As Boolean` | `True`, если мутекс уже существовал (то есть это не первое окно). На net48 всегда `False` |

Читаем именно один ключ, а не `ModernViewerPreferences.Load()`: решение нужно в конструкторе
модели приложения, где ещё нет ни формы, ни объекта настроек. Это **единственное** место, где
ключ читается в обход `ModernViewerPreferences` - имя ключа общее, так что расхождения нет.

Файл добавить в `<Compile Include>` старого проекта [src/FastMediaSorter.vbproj](../../src/FastMediaSorter.vbproj)
в том же коммите (правило «Two builds, one source tree» в [CLAUDE.md](../../CLAUDE.md)).

### 3.2 Уровень 1: `IsSingleInstance` становится вычисляемым

`Me.IsSingleInstance` присваивается в конструкторе `My.MyApplication`, а конструктор - в
**сгенерированном** файле `My Project\Application.Designer.vb` (генератор - `My Project\Application.myapp`).
Править сгенерированный файл руками нельзя (инвариант 16 канона: render target регенерируют, а не
редактируют), а `.myapp` умеет хранить только константу `true`/`false`.

Поэтому **сгенерированную пару выводим из обращения** и заменяем одним рукописным партиалом
`src/ApplicationModel.vb`:

```vb
Namespace My
    Partial Friend Class MyApplication
        Public Sub New()
            MyBase.New(Global.Microsoft.VisualBasic.ApplicationServices.AuthenticationMode.Windows)
            ' Единственная строка, которая отличается от сгенерированной версии.
            Me.IsSingleInstance = Not MultiWindowPolicy.AllowNewWindows()
            Me.EnableVisualStyles = False      ' пиксельная вёрстка - не трогать
            Me.SaveMySettingsOnExit = True
            Me.ShutDownStyle = Global.Microsoft.VisualBasic.ApplicationServices.ShutdownMode.AfterMainFormCloses
        End Sub

        Protected Overrides Sub OnCreateMainForm()
            Me.MainForm = Global.fmsl.Main_Form
        End Sub

        Protected Overrides Function OnInitialize(commandLineArgs As ...) As Boolean
            Me.MinimumSplashScreenDisplayTime = 0
            Return MyBase.OnInitialize(commandLineArgs)
        End Function
    End Class
End Namespace
```

Правки проектов и файлов:

| Файл | Действие |
|---|---|
| `src/My Project/Application.Designer.vb` | удалить |
| `src/My Project/Application.myapp` | удалить |
| `src/FastMediaSorter.vbproj` | убрать `<Compile Include="My Project\Application.Designer.vb">` и `<None Include="My Project\Application.myapp">`, добавить `<Compile Include="ApplicationModel.vb" />` |
| `src/Modern/FastMediaSorter.Modern.vbproj` | правок нет: новый файл подхватывает глоб `..\**\*.vb` |

Базовый класс, `Shared Sub Main` и `<STAThread>` даёт шаблон `My` при `MyType=WindowsForms` -
оба проекта его уже задают, `StartupObject` остаётся `fmsl.My.MyApplication`. Удаление `.myapp`
на сборку не влияет (компилятор его не читает), но вкладка «Application» в дизайнере проекта
Visual Studio может попытаться создать его заново. Если это случится, файл вернёт и
`Application.Designer.vb` - тогда сборка **громко** упадёт на дубле `Public Sub New` (BC30269);
лечится удалением обоих файлов заново. Тихого расхождения этот сценарий не даёт, что нас и
устраивает.

### 3.3 Уровень 2: пропуск пересылки

В `MyApplication_Startup` ([src/Application_Events.vb](../../src/Application_Events.vb)) после
создания мутекса:

```vb
Main_Form.Single_Instance_Mutex = New Mutex(True, Main_Form.app_Mutex_Name, created_New)
MultiWindowPolicy.MarkInstanceRole(created_New)

If Not created_New AndAlso Not MultiWindowPolicy.AllowNewWindows() Then
    ' .. существующий блок пересылки WM_COPYDATA целиком, без изменений ..
End If
```

Мутекс создаётся **всегда**, в том числе при включённой опции: он теперь работает не только как
сторож единственности, но и как определитель роли (§4). Блок пересылки не переписываем - только
оборачиваем условием.

### 3.4 Отвергнутые механизмы (с доказательствами)

| Вариант | Почему нет |
|---|---|
| Переопределить `GetApplicationInstanceID` и сделать id уникальным на запуск | на .NET 10 такого члена нет. Проверено пробной сборкой: `error BC30284: function 'GetApplicationInstanceID' cannot be declared 'Overrides' because it does not override a function in a base class` (на net48 он есть - механизм разъехался бы по сборкам) |
| `MyType=WindowsFormsWithCustomSubMain` и собственный `Sub Main`, который выставляет `IsSingleInstance` перед `Run` | в этом режиме `My.Application` перестаёт быть `WindowsFormsApplicationBase`. Проверено пробной сборкой: `error BC30456: 'IsSingleInstance' is not a member of 'MyApplication'` и `'Run' is not a member of 'MyApplication'`. Заодно отвалились бы `Handles Me.Startup`, `Handles Me.StartupNextInstance`, `Application.MainForm` и `My.Application.CommandLineArgs` |
| Просто поставить `<SingleInstance>false</SingleInstance>` в `.myapp` | константа: уровень 1 исчезает и при выключенной опции, вместе с ним - надёжная доставка аргумента во время старта первого окна. И меняет net48, которого нам трогать нельзя |
| Второй `Main_Form` в том же процессе (по событию `StartupNextInstance`) | состояние программы глобальное: `Common_Module` (`Current_File_Name`, `Hardkeys_to_move_mediafile`, флаги просмотра), `Table_Form` как default instance, запись настроек на закрытии формы. Два окна в одном процессе портили бы друг другу состояние и настройки |

## 4. Дисциплина записи настроек при нескольких окнах

Настройки в программе пишутся **блоком при закрытии** ([src/Main_Form.Lifecycle.vb:758-843](../../src/Main_Form.Lifecycle.vb#L758)):
около сорока `SaveSetting`, `ModernViewerPreferences.Save()`, `SaveOcrSettings()`,
`Localization.SaveToSettings()`. Два окна = два таких блока со своими копиями значений, прочитанных
при старте. Кто закрылся последним, тот и переписал чужие изменения - включая каталоги-получатели.

**Правило: дополнительный процесс не пишет настройки вообще.** Не «пишет частично», не «пишет
свою группу ключей» - ничего. Так исключается весь класс ошибок «затёрло устаревшим значением»,
и правило можно объяснить одной фразой.

| Точка записи | Правка |
|---|---|
| блок сохранения в `Main_Form_FormClosing` | обернуть в `If Not MultiWindowPolicy.IsSecondaryInstance() Then .. End If` |
| `ModernViewerPreferences.Save()` | ранний выход `If MultiWindowPolicy.IsSecondaryInstance() Then Return` - страхует все вызовы, включая импорт настроек |
| `SaveOcrSettings()` | тот же ранний выход: OCR-настройки пишутся ещё и при закрытии окна настроек |
| `Localization.SaveToSettings()` | проверить все места вызова; те, что не в блоке выхода, закрыть тем же условием |
| ключ `AllowNewWindows` | **исключение**, см. §4.2 |

### 4.1 Что пользователь видит

- Заголовок дополнительного окна получает суффикс: `Fast Media Sorter for Windows by SZA - `
  плюс `Localization.T("дополнительное окно")`. Заголовок в программе присваивается ровно один раз
  ([src/Main_Form.Designer.vb:427](../../src/Main_Form.Designer.vb#L427)), поэтому это одна строка
  в `Form1_Load` при `IsSecondaryInstance()`.
- Окно настроек, открытое из дополнительного окна, показывает наверху одну строку-предупреждение:
  «Это дополнительное окно. Изменения настроек действуют до его закрытия и не сохраняются - настройки
  хранит первое окно.» Строка добавляется в современную оболочку `Table_Form` (`ModernLayout`) и
  видна только при `IsSecondaryInstance()`.

Изменения по-прежнему применяются **живьём** к своему окну - запрещена только запись в реестр.

### 4.2 Одно исключение: сам переключатель

Галочка «Разрешать запуск в новых окнах» обязана действовать сразу на **следующие** запуски -
иначе снятая галочка не сработает, пока не закрыты все окна. Поэтому:

- обработчик галочки пишет один ключ немедленно (`SaveSetting(App_name, Second_App_Name, "AllowNewWindows", ..)`),
  из любого процесса, основного или дополнительного;
- `ModernViewerPreferences.Save()` перед записью этого ключа **перечитывает** его из реестра
  (`AllowNewWindows = ReadBool("AllowNewWindows", AllowNewWindows)`), чтобы блочная запись основного
  окна на выходе не воскресила устаревшее значение;
- уже запущенные процессы своё поведение не меняют - значение прочитано и закэшировано при их
  старте (§3.1).

### 4.3 Позиция окна: каскад

Все окна читают одни `AppTop`/`AppLeft`/`AppWidth`/`AppHeight`, поэтому второе окно легло бы
ровно на первое - пользователь решит, что окно не открылось. При `IsSecondaryInstance()` позиция
восстановления сдвигается каскадом: `+32` по обеим осям на каждое уже существующее окно просмотрщика
(количество берётся тем же перечислением, что и в `GetProcessTopLevelWindows`), с зажимом в рабочую
область текущего монитора (`Screen.FromPoint(..).WorkingArea`), чтобы окно не уехало за край.
Позицию дополнительное окно, как и всё остальное, не сохраняет.

## 5. Где живёт галочка

Страница **«Файлы и система»** (`Tab_Page_4`), сразу после строки «Что открывать при запуске»
(`startup_open`) - обе строки про поведение запуска.

| Точка | Правка |
|---|---|
| [src/ModernViewerPreferences.vb](../../src/ModernViewerPreferences.vb) | `Public Property AllowNewWindows As Boolean = False`; в `Load()` - `ReadBool("AllowNewWindows", ..)`; в `Save()` - `WriteBool` с перечитыванием из §4.2 |
| [src/Table_Form.ExpandedSettings.vb](../../src/Table_Form.ExpandedSettings.vb) | в `AddExpandedSettingsRows`, в блоке `files`, после `startup_open`: собственная строка (не `AddPreferenceCheck`, потому что нужна немедленная запись ключа) - чекбокс + `AddSettingRow(files, "allow_new_windows", check, 34, True)` + подсказка |
| [src/Table_Form.ModernLayout.vb](../../src/Table_Form.ModernLayout.vb) | `ModernSettingTitle`: `Case "allow_new_windows"`; `ModernSettingDescription`: `Case "allow_new_windows"` |

Строки (русский - это и есть ключ словаря):

| Роль | Текст |
|---|---|
| Заголовок строки | «Разрешать запуск в новых окнах» |
| Описание | «Обычно повторный запуск программы отдаёт файл уже открытому окну. Если отмечено, каждый запуск открывает своё окно.» |
| Подсказка (tooltip) | «Действует со следующего запуска. Настройки и позицию окна хранит первое окно. Помните: выделив в проводнике десять файлов, вы получите десять окон. По умолчанию выключено.» |
| Предупреждение в окне настроек дополнительного окна | «Это дополнительное окно. Изменения настроек действуют до его закрытия и не сохраняются - настройки хранит первое окно.» |
| Суффикс заголовка окна | «дополнительное окно» |

Все пять - через `Localization.T`, с полными переводами на 12 языков в таблицах:
заголовок - `src/Localization/Localization.Settings.vb`, описание - `Localization.SettingsDesc.vb`,
подсказка - `Localization.SettingsHints.vb`, две строки главного окна/оболочки -
`Localization.Chrome.vb`. Без умных кавычек `“ ”` (ломают компилятор VB - см.
[SPECIFICATION_THIRTEEN_UI_LANGUAGES.md](SPECIFICATION_THIRTEEN_UI_LANGUAGES.md)). Тесты
`LocalizationParityTests` и `LocalizationCoverageTests` должны остаться зелёными.

## 6. Хранение

| Ключ | Значения | По умолчанию | Кто пишет |
|---|---|---|---|
| `AllowNewWindows` | `"1"` / `"0"` | `"0"` | обработчик галочки (немедленно, любой процесс) и блочная запись основного окна с перечитыванием |

Куст тот же: `HKCU\Software\VB and VBA Program Settings\SZA\FastMediaSorter`. Новых кустов, файлов
и мутексов не добавляется. Ключ попадает в экспорт/импорт настроек автоматически - он обычное
свойство `ModernViewerPreferences` (`ExportJson`/`FromJson`).

## 7. Журнал

`AppFileLogger` открывает `current.log` в режиме `FileMode.Append` с `FileShare.ReadWrite`, поэтому
два процесса пишут в один файл без ошибок, но строки перемешиваются. Правка минимальная: в стартовый
баннер журнала добавить PID процесса и его роль (`primary`/`secondary`). Разделять файлы по процессам
не надо - «Отправить логи автору»
([SPECIFICATION_SEND_LOGS_TO_AUTHOR.md](SPECIFICATION_SEND_LOGS_TO_AUTHOR.md)) собирает именно
`current.log`, и один общий файл с PID в баннере разбирать удобнее, чем набор файлов.

В `report.txt` того же архива добавить строку `AllowNewWindows=0|1` - при разборе жалоб на «не
сохраняются настройки» это первое, что нужно знать.

## 8. Что ещё делится между окнами

| Ресурс | Оценка |
|---|---|
| Пара exe (`FastMediaSorter_LITE.exe` / `FastMediaSorter_x86.exe`) | опция читается из общего куста, но на net48 `AllowNewWindows()` всегда `False`, поэтому x86-процесс **всегда** пересылает аргумент и никогда не открывает второе окно сам. Обратное направление разрешено: mainline с включённой опцией не отдаёт файл работающему x86 |
| Загрузка нативных рантаймов (`OptionalRuntimeManager`) | два окна, одновременно потянувшие `tesseract50.dll`/`libvlc`, пишут в один и тот же путь - можно получить битый файл. Обязательная мелкая правка: загрузку/распаковку взять под именованный мутекс `FastMediaSorterRuntimeDownloadMutex`, второй процесс ждёт и затем видит готовый файл |
| Дисковый кэш OCR (`TranslationCache`) | ключ включает путь, время записи и параметры движка, поэтому два процесса пишут одну и ту же запись. Запись делать через временный файл + `File.Move` (перезапись), если это ещё не так |
| Одна и та же папка в двух окнах | синхронизации нет и не будет: удалили файл в окне A - окно B узнает об этом при следующей навигации, ровно как при внешнем изменении папки сейчас. Осознанное ограничение |
| Ассоциации файлов, `SHChangeNotify` | пишутся в `HKCU\Software\Classes` по кнопке, идемпотентно - несколько окон не мешают |
| Share Manager (Companion) | не затрагивается: LITE только будит его через свой мутекс, а сам Companion остаётся одноэкземплярным |
| Память | каждое окно поднимает свой LibVLC и свои декодеры. Это цена функции, включаемой руками; в описании опции об этом не пишем, но в CHANGELOG упомянем словом «каждое окно - отдельный процесс» |

## 10. Как проверять

Сборка: `.\build.ps1` - обе сборки обязаны собраться, x86 в том числе (Э-2 трогает модель
приложения, общую для двух проектов).

**Опция выключена (регрессия важнее самой функции):**

1. Двойной клик по картинке при уже открытой программе - файл открывается в существующем окне,
   второго окна нет, фокус не украден. В журнале виден путь `StartupNextInstance`.
2. Запуск exe без аргументов - существующее окно разворачивается и получает фокус.
3. Быстрый двойной запуск с файлом (второй - пока первое окно ещё не нарисовалось): в итоге одно
   окно с файлом, аргумент не потерян.
4. Запущен mainline, запускаем `FastMediaSorter_x86.exe` с файлом - файл уходит в окно mainline
   (путь мутекса, `n00-2`/`n00-3` в журнале).
5. Обратный случай: запущен x86, запускаем mainline - файл уходит в окно x86.
6. Настройки, позиция окна, последняя папка и индекс сохраняются как раньше.

**Опция включена:**

7. Второй запуск с файлом - **новое окно**, у него суффикс «дополнительное окно» в заголовке.
8. Три окна одновременно: независимые папки, масштаб, громкость, слайдшоу.
9. Второе окно не легло на первое (каскад) и целиком в пределах экрана; на левом/верхнем мониторе
   с отрицательными координатами тоже.
10. Окно настроек в дополнительном окне: предупреждение видно; смена, например, цветовой схемы
    применяется живьём; после закрытия **обоих** окон в реестре остались значения основного окна
    (проверять `reg query "HKCU\Software\VB and VBA Program Settings\SZA\FastMediaSorter"` до и после).
11. Закрыть дополнительное окно первым, потом основное - записалось состояние основного
    (`ImageFolder`, `LastCounter`, `AppTop/AppLeft`).
12. Закрыть основное первым, потом дополнительное - настройки **не** изменились после закрытия
    дополнительного (роль не передаётся).
13. Снять галочку в дополнительном окне, не закрывая программу, и запустить exe заново - открылось
    **не** новое окно, а файл ушёл в существующее (немедленная запись ключа, §4.2).
14. Поставить галочку, закрыть все окна, запустить - значение уцелело.
15. Пустой запуск при включённой опции - новое окно с содержимым по `StartupOpenMode`.
16. Экспорт/импорт настроек переносит `AllowNewWindows`.
17. Два окна, в обоих запустить OCR на одном и том же файле - кэш не побился, оба показали перевод.
18. x86-сборка с `AllowNewWindows=1` в кусте: второе окно **не** открывается, поведение прежнее.

## 11. Риски и чего мы не делаем

| Риск | Что делаем |
|---|---|
| Правка модели приложения (Э-2) задевает **обе** сборки | содержимое конструктора переносится дословно, меняется одна строка; проверяется пунктами 1-6 и 18 плана §10 |
| Visual Studio восстановит `Application.myapp` | сборка упадёт на дубле `Public Sub New` - громко и однозначно (§3.2) |
| Пользователь включит опцию, наплодит окон и решит, что «настройки не работают» | суффикс в заголовке, предупреждение в окне настроек, фраза в подсказке, `AllowNewWindows` в `report.txt` |
| Десять файлов из проводника = десять процессов | так работает проводник; предупреждение в подсказке. Ограничивать число окон искусственно не будем |
| Роль не передаётся: после закрытия первого окна настройки не пишет никто | осознанное ограничение, зафиксировано здесь и в пункте 12 плана проверки. Передача роли на выходе означала бы запись устаревших значений - хуже, чем не писать |

**Чего мы не делаем в этой работе:** горячей клавиши/кнопки «открыть новое окно» из работающей
программы (это про запуск себя же и стоит отдельного решения о том, что наследует новое окно);
общего состояния между окнами; окна-табов; ограничения количества окон; каких-либо правок net48
кроме компилируемых заглушек.
