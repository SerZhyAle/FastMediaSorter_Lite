# Спецификация: локальный выбор «Перенести / Скопировать» и новая галочка после копирования

Статус: план
Дата: 2026-07-16, ревизия 1
Область: основной viewer (`src/*.vb`), обе сборки если не оговорено иначе

## 0. Проблема

Сейчас копирование включается не в момент действия, а через глобальный режим в
настройках: галочка `chkbox_Copy_Mode` в `Table_Form` меняет общий флаг
`Is_Copying_not_Moving`, он сохраняется в ключ `CopyMode`, а дальше все точки
сортировки просто наследуют это состояние.

Это создаёт UX-ошибку:

1. Пользователь думает в терминах **действия над текущим файлом**: «этот файл
   перенести», «этот файл скопировать».
2. Программа заставляет думать в терминах **глобального режима приложения**:
   чтобы один раз скопировать, надо идти в настройки, менять галочку, потом не
   забыть вернуть её обратно.
3. Из-за этого копирование спрятано, медленнее, менее предсказуемо и опаснее:
   можно случайно оставить режим копирования включённым или, наоборот, ожидать
   копию, а получить перенос.

Пользовательское требование: **везде, где можно инициировать перенос, рядом должна
быть простая возможность инициировать копирование**, а в настройках вместо
существующей галочки должна появиться новая:

**«переходить к следующему файлу после копирования»**  
по умолчанию: **включено**

## 1. Текущее состояние (as-is)

### 1.1 Глобальный copy mode

- `chkbox_Copy_Mode` живёт в [src/Table_Form.Designer.vb](../../../src/Table_Form.Designer.vb)
  и настраивается в [src/Table_Form.vb](../../../src/Table_Form.vb).
- Тексты:
  RU: `Режим копирования файлов (не перенос)`
  EN: `COPY mode (files are not moving)`
- Обработчик
  [src/Table_Form.vb](../../../src/Table_Form.vb) (`CheckBox1_CheckedChanged`) делает
  только одно: `Is_Copying_not_Moving = chkbox_Copy_Mode.Checked`.
- Загрузка/сохранение глобального режима идёт через
  [src/Main_Form.Lifecycle.vb](../../../src/Main_Form.Lifecycle.vb):
  ключ `CopyMode`, `"0"`/`"1"`.

### 1.2 Где пользователь реально инициирует файловую операцию

На сегодня перенос/копирование запускаются через одни и те же пути, но тип
операции выбирается **не локально**, а только через `Is_Copying_not_Moving`.

1. **Клавиатура `0..9`**:
   [src/Main_Form.KeyboardInput.vb](../../../src/Main_Form.KeyboardInput.vb) вызывает
   `PoMove(1..10)`.
2. **Плавающий оверлей получателей**:
   [src/Main_Form.RecipientsOverlay.vb](../../../src/Main_Form.RecipientsOverlay.vb)
   по клику вызывает `PoMove(slot)`.
3. **Контекстные меню медиа**:
   [src/Main_Form.MediaMenu.vb](../../../src/Main_Form.MediaMenu.vb) строит подпункт
   `Move to` или `Copy to` в зависимости от текущего глобального флага и тоже
   вызывает `PoMove(slot)`.
4. **Таблица получателей в настройках**:
   двойной клик по номеру клавиши в [src/Table_Form.vb](../../../src/Table_Form.vb)
   вызывает `Main_Form.DoKey(row)`, который затем идёт в `PoMove`.

### 1.3 Где тип операции решается фактически

Авторитетная точка - [src/Main_Form.FileOperations.vb](../../../src/Main_Form.FileOperations.vb),
метод `PoMove`.

Сейчас он:

- читает каталог-получатель по слоту;
- записывает `history_Was_Copy = Is_Copying_not_Moving`;
- строит `FileOp.Kind = If(Is_Copying_not_Moving, Copy, Move)`;
- показывает статус `копируется` или `переносится`;
- дальше исполняет ту операцию, которую продиктовал глобальный флаг.

Иными словами, почти весь UI уже умеет «довезти файл в слот», но **не умеет явно
сказать, что именно делать: move или copy**.

## 2. Цель (to-be)

Сделать модель прямой и локальной:

1. В каждой точке, где пользователь может **перенести** файл, рядом есть столь же
   простой способ его **скопировать**.
2. Выбор `Перенести`/`Скопировать` делается **в момент действия**, а не заранее в
   настройках приложения.
3. Глобальный `Copy mode` удаляется.
4. В настройках вместо него появляется отдельная поведенческая галочка:
   **«переходить к следующему файлу после копирования»**, по умолчанию включена.
5. Копирование и перенос используют один и тот же транспорт, историю, undo,
   обработку ошибок и очередь; различается только тип операции.

## 3. Новая модель операции

### 3.1 Явный тип действия

Вместо «вызвать `PoMove(slot)` и надеяться на глобальный флаг» вводится явная модель:

- `Move`
- `Copy`

Минимальное изменение шва:

```vb
Private Enum RecipientActionKind
    Move
    Copy
End Enum

Private Sub ExecuteRecipientAction(slot As Integer, action As RecipientActionKind)
```

Допустимая альтернатива: расширить сам `PoMove`, чтобы он принимал тип действия
параметром и без параметра больше не использовался на пользовательских путях.

Требование спецификации: **ни одна UI-точка не должна выбирать тип операции через
чтение глобального `Is_Copying_not_Moving`**.

### 3.2 Новая настройка после копирования

Новый флаг:

- RU: **`переходить к следующему файлу после копирования`**
- EN: `Go to the next file after copying`
- дефолт: **включено**

Назначение флага:

- Если включён: после успешной постановки/выполнения `Copy` UI ведёт себя как
  нынешний быстрый сортировочный сценарий и показывает следующий файл.
- Если выключен: после копирования пользователь остаётся на текущем файле.

Это поведение касается только **Copy**. Для **Move** текущая модель перелистывания
сохраняется без изменений.

## 4. Изменения по поверхностям UI

## 4.1 Настройки (`Table_Form`)

Надо убрать старую галочку `chkbox_Copy_Mode` и использовать то же место для новой.

Новый текст:

- RU: **`Переходить к следующему файлу после копирования`**
- EN: `Go to the next file after copying`

Новый tooltip:

- RU: `Если отмечено, после копирования программа сразу показывает следующий файл. Если снять галочку, после копирования остаётся текущий файл. По умолчанию включено.`
- EN: `If checked, after copying the app immediately shows the next file. If unchecked, it stays on the current file after the copy. On by default.`

Персистентность:

- новый ключ, например `AdvanceAfterCopy`
- значения `"0"`/`"1"`
- дефолт `"1"`

Старый ключ `CopyMode`:

- больше не читать для поведения приложения;
- больше не сохранять;
- миграция в новый флаг **не нужна**, потому что это другая по смыслу настройка.

## 4.2 Клавиатура `0..9`

Это самый чувствительный участок: сейчас цифровые клавиши уже заняты переносом.
Нужен **рядом простой способ копирования**, не требующий захода в настройки.

Обязательное требование:

- у каждой горячей клавиши переноса должен появиться парный, легкообъяснимый путь
  копирования в тот же слот.

Рекомендуемая реализация:

1. `0..9` оставляем за **переносом**.
2. `Shift+0..9` вводим как **копирование** в тот же слот.

Причины выбора:

- это действительно «рядом»;
- не ломает мышечную память для основного сценария переноса;
- визуально и ментально объясняется просто: «цифра - перенести, Shift+цифра - скопировать».

Альтернативы вроде `Ctrl+0..9` или отдельного режима клавиатуры здесь не рекомендуются:
они хуже читаются, хуже документируются и частично конфликтуют с привычными
системными сочетаниями.

## 4.3 Плавающий оверлей получателей

Сейчас оверлей показывает по одной строке на слот и клик по строке делает одно
действие, которое зависит от глобального режима.

После переработки глобального режима больше нет, поэтому оверлей должен явно давать
оба действия.

Требование спецификации:

- рядом с каждым получателем в оверлее должны быть **две простые зоны действия**:
  `Перенести` и `Скопировать`.

Рекомендуемый UI:

- строка получателя = путь;
- справа две компактные кнопки или две явные кликабельные зоны:
  `M` / `C` или лучше локализованные `Перенести` / `Скопировать` в краткой форме.

Нельзя оставлять вариант, где:

- строка делает только `Move`, а `Copy` снова прячется в настройках;
- строка делает «что-то одно» по неочевидному модификатору клавиатуры без подсказки.

## 4.4 Контекстные меню изображения/видео

Сейчас подменю строится как **либо** `Move to`, **либо** `Copy to`.

Это надо заменить на одновременную доступность обоих действий:

- `Переместить в`
- `Скопировать в`

Оба подпункта показывают один и тот же список слотов-получателей.
Различается только передаваемый `RecipientActionKind`.

Преимущество: пользователь видит оба варианта сразу, без скрытого режима.

## 4.5 Таблица получателей в настройках

Сегодня двойной клик по номеру клавиши сразу исполняет действие для этой клавиши.
После отмены глобального режима такой запуск тоже не должен зависеть от несуществующей
галочки.

Требование:

- рядом с запуском `Move` в этой поверхности тоже должен существовать простой запуск
  `Copy`.

Рекомендуемый вариант:

1. двойной клик по номеру клавиши оставить за `Move`;
2. `Shift+двойной клик` по номеру клавиши сделать `Copy`;
3. tooltip и hint под таблицей обновить явно.

Допустима альтернатива с контекстным меню строки (`Перенести` / `Скопировать`), если
она окажется понятнее и чище в коде, но одинарный сценарий «только перенос» здесь
оставлять нельзя.

## 5. Поведение файловых операций

## 5.1 История и undo

Существующая логика уже хранит `history_Was_Copy` отдельно от текущего флага и
должна быть сохранена как принцип: undo обязан отменять **фактически выполненное**
действие, а не читать текущие настройки UI.

После рефакторинга это должно стать проще:

- `Move` записывается как `Move`;
- `Copy` записывается как `Copy`;
- никакого участия глобального режима в undo больше нет.

## 5.2 Следующий файл после копирования

Новая галочка меняет только пост-эффект Copy.

Требования:

1. **Move** работает как сейчас.
2. **Copy + галочка ON**:
   после успешного копирования переход к следующему файлу.
3. **Copy + галочка OFF**:
   после успешного копирования остаться на текущем файле.
4. При ошибке копирования перехода не происходит независимо от галочки.

Для modern-сборки с очередью это означает:

- UI должен принимать решение на основании результата операции;
- если перелистывание делается оптимистически до завершения I/O, нужно отдельно
  проверить, что поведение `Copy + OFF` остаётся корректным и не ломает очередь.

Это главный технический риск данной работы.

## 6. Обратная совместимость и миграция

## 6.1 Поведенческая совместимость

- Основной быстрый сценарий `0..9 = перенести` должен сохраниться.
- Мышечная память существующих пользователей не должна ломаться для move.
- Копирование должно стать быстрее, но не ценой скрытого изменения старых move-путей.

## 6.2 Настройки

- `CopyMode` считать устаревшим.
- На запуске его можно игнорировать полностью.
- Если пользователь ранее оставил `CopyMode=1`, это **не** должно автоматически
  включать или выключать `AdvanceAfterCopy`, потому что смысл настроек разный.

## 6.3 Тексты и документация

Нужно обновить:

- `README.md`
- `README_RU.md`
- `CHANGELOG.md`
- tooltips и help-тексты, где copy/move описываются как глобальный режим

Отдельно проверить формулировки в тех местах, где сейчас написано, что панель,
меню или клик «move/copy the current file» без объяснения, как именно выбирается
действие.

## 7. Риски

1. **Очередь modern + Copy without advance**:
   если нынешний код жёстко связан с немедленным показом следующего файла после любой
   операции, поведение `Copy + OFF` потребует аккуратного разведения UI- и I/O-слоёв.
2. **Размножение ad-hoc логики**:
   если каждая поверхность (`KeyboardInput`, `RecipientsOverlay`, `MediaMenu`,
   `Table_Form`) будет по-своему решать, что такое copy, поведение быстро разойдётся.
   Нужна одна авторитетная точка исполнения.
3. **Перегруженный оверлей**:
   добавление второго действия в строку может ухудшить читаемость на маленьких окнах.
   Нужен компактный, но однозначный UI.
4. **Коллизии клавиатуры**:
   перед финальным выбором `Shift+0..9` проверить, что эти сочетания не заняты в
   приложении и не конфликтуют с вводом в фокусируемых контролах.

## 8. Приёмка

1. Чистый запуск: в настройках нет галочки `Copy mode`; вместо неё есть
   `Переходить к следующему файлу после копирования`, и она включена.
2. `0..9` по-прежнему переносят файл в соответствующий слот.
3. Парный сценарий копирования рядом с `0..9` существует и работает в те же слоты.
4. В оверлее у каждого получателя доступны и `Перенести`, и `Скопировать`.
5. В контекстном меню одновременно видны `Переместить в` и `Скопировать в`.
6. Из таблицы получателей в настройках можно и перенести, и скопировать без похода
   к отдельной глобальной галочке.
7. `Undo` после `Move` возвращает файл назад; `Undo` после `Copy` удаляет созданную
   копию, а не трогает оригинал.
8. `Copy + AdvanceAfterCopy=ON`: после успешного копирования показывается следующий файл.
9. `Copy + AdvanceAfterCopy=OFF`: после успешного копирования остаётся текущий файл.
10. Ошибка copy/move не приводит к ложному переходу на другой файл и не ломает
    список/очередь.
