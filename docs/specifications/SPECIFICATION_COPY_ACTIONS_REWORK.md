# Спецификация: локальный выбор «Перенести / Скопировать» и новая галочка после копирования

Статус: **реализовано** (2026-07-30, локальные сборки `26.7.30.0127` и `26.7.30.0137/0138`;
тег не создавался)
Дата: 2026-07-30, ревизия 3
Область: основной viewer, **только .NET 10 mainline** (`FastMediaSorter_LITE.exe`).
Сборка net48 x86 (`FastMediaSorter_x86.exe`) сохраняет текущее поведение за швом
`#If NETFRAMEWORK` - см. §0.1.

## 0. Проблема

Сейчас копирование включается не в момент действия, а через глобальный режим в
настройках: галочка `chkbox_Copy_Mode` в `Table_Form` меняет общий флаг
`Is_Copying_not_Moving`, он сохраняется в ключ `CopyMode`, а дальше все точки
сортировки просто наследуют это состояние.

Это создаёт UX-ошибку:

1. Пользователь думает в терминах **действия над текущим файлом**: «этот файл
   перенести», «этот файл скопировать».
2. Программа заставляет думать в терминах **глобального режима приложения**:
   чтобы один раз скопировать, надо идти в настройки, менять галочку, потом не
   забыть вернуть её обратно.
3. Из-за этого копирование спрятано, медленнее, менее предсказуемо и опаснее:
   можно случайно оставить режим копирования включённым или, наоборот, ожидать
   копию, а получить перенос.

Пользовательское требование: **везде, где можно инициировать перенос, рядом должна
быть простая возможность инициировать копирование**, а в настройках вместо
существующей галочки должна появиться новая:

**«переходить к следующему файлу после копирования»**
по умолчанию: **включено**

### 0.1 Почему только mainline

Действующее решение владельца (2026-07-19, зафиксировано в `CLAUDE.md`, «Two builds,
one source tree»): .NET 10 x64 - активная цель разработки; в net48 x86 не добавляются
новые возможности и намеренные изменения поведения. Эта работа - именно новая
возможность, поэтому:

- вся новая модель (явный тип действия, новые точки UI, галочка `AdvanceAfterCopy`)
  живёт под `#If Not NETFRAMEWORK`;
- в net48 остаются `chkbox_Copy_Mode`, глобальный `Is_Copying_not_Moving` и ключ
  `CopyMode` ровно в нынешнем виде;
- общий код (`PoMove`, история, undo) обязан компилироваться и работать в обеих
  сборках - шов делается в одной авторитетной точке исполнения, а не в каждом
  вызывающем месте.

### 1.2 Где пользователь реально инициирует файловую операцию

На сегодня перенос/копирование запускаются через одни и те же пути, но тип
операции выбирается **не локально**, а только через `Is_Copying_not_Moving`.

1. **Клавиатура `0..9`**:
   [src/Main_Form.KeyboardInput.vb](../../src/Main_Form.KeyboardInput.vb) вызывает
   `PoMove(1..10)` (`D1..D9`/`NumPad1..NumPad9` -> слоты 1..9, `D0`/`NumPad0` -> слот 10).
2. **Плавающий оверлей получателей**:
   [src/Main_Form.RecipientsOverlay.vb](../../src/Main_Form.RecipientsOverlay.vb)
   по клику вызывает `PoMove(slot)`; отдельная строка со слотом `-1` - удаление.
3. **Контекстные меню медиа**:
   [src/Main_Form.MediaMenu.vb](../../src/Main_Form.MediaMenu.vb) строит подпункт
   `Move to` или `Copy to` в зависимости от текущего глобального флага и тоже
   вызывает `PoMove(slot)`.
4. **Таблица получателей в настройках**:
   двойной клик по колонке 0 в [src/Table_Form.vb](../../src/Table_Form.vb)
   вызывает `Main_Form.DoKey(row)`; **строка 0 - это DEL** (`DoKey(0)` удаляет файл),
   строки 1..10 идут в `PoMove(row)`.
5. **Панель миниатюр** ([src/Image_Panel_Form.vb](../../src/Image_Panel_Form.vb)):
   цифровые клавиши вызывают `PoMove_for_Panel(0..9)` - **отдельная реализация**, которая
   сама читает `Is_Copying_not_Moving` и сама зовёт `File.Copy`/`File.Move` для
   мультивыделения, минуя `PoMove`, очередь, историю и undo.

### 1.3 Где тип операции решается фактически

Основная точка - [src/Main_Form.FileOperations.vb](../../src/Main_Form.FileOperations.vb),
метод `PoMove`.

Сейчас он:

- читает каталог-получатель по слоту;
- записывает `history_Was_Copy = Is_Copying_not_Moving`;
- строит `FileOp.Kind = If(Is_Copying_not_Moving, FileOpKind.Copy, FileOpKind.Move)`;
- показывает статус `копируется` или `переносится`;
- дальше исполняет ту операцию, которую продиктовал глобальный флаг.

Вторая, независимая точка - `PoMove_for_Panel` в `Image_Panel_Form` (см. §1.2.5).
Она не разделяет с `PoMove` ни очередь, ни историю, поэтому «одна авторитетная точка»
из §7.2 - это не только рефакторинг `PoMove`, но и решение, что делать с панелью.

Иными словами, почти весь UI уже умеет «довезти файл в слот», но **не умеет явно
сказать, что именно делать: move или copy**.

## 2. Цель (to-be)

Сделать модель прямой и локальной (в mainline-сборке):

1. В каждой точке, где пользователь может **перенести** файл, рядом есть столь же
   простой способ его **скопировать**.
2. Выбор `Перенести`/`Скопировать` делается **в момент действия**, а не заранее в
   настройках приложения.
3. Глобальный `Copy mode` уходит из UI mainline-сборки.
4. В настройках вместо него появляется отдельная поведенческая галочка:
   **«переходить к следующему файлу после копирования»**, по умолчанию включена.
5. Копирование и перенос используют один и тот же транспорт, историю, undo,
   обработку ошибок и очередь; различается только тип операции.

## 3. Новая модель операции

### 3.1 Явный тип действия

Вместо «вызвать `PoMove(slot)` и надеяться на глобальный флаг» вводится явная модель:

- `Move`
- `Copy`

Минимальное изменение шва:

```vb
Private Enum RecipientActionKind
    Move
    Copy
End Enum

Private Sub ExecuteRecipientAction(slot As Integer, action As RecipientActionKind)
```

Существующий `PoMove(slot)` остаётся тонкой обёрткой и становится единственным местом,
где ещё жив глобальный флаг:

```vb
Private Sub PoMove(ByVal move_Slot_index As Integer)
#If NETFRAMEWORK Then
    ExecuteRecipientAction(move_Slot_index, If(Is_Copying_not_Moving, RecipientActionKind.Copy, RecipientActionKind.Move))
#Else
    ExecuteRecipientAction(move_Slot_index, RecipientActionKind.Move)
#End If
End Sub
```

Требование спецификации: **ни одна UI-точка mainline-сборки не должна выбирать тип
операции через чтение глобального `Is_Copying_not_Moving`**; все новые точки зовут
`ExecuteRecipientAction` с явным типом.

### 3.2 Новая настройка после копирования

Новый флаг:

- RU (ключ локализации): **`Переходить к следующему файлу после копирования`**
- EN: `Go to the next file after copying`
- дефолт: **включено**

Назначение флага:

- Если включён: после успешной постановки/выполнения `Copy` UI ведёт себя как
  нынешний быстрый сортировочный сценарий и показывает следующий файл.
- Если выключен: после копирования пользователь остаётся на текущем файле.

Это поведение касается только **Copy**. Для **Move** текущая модель перелистывания
сохраняется без изменений.

## 4. Изменения по поверхностям UI

### 4.1 Настройки (`Table_Form`)

В mainline-сборке галочка `chkbox_Copy_Mode` уходит с глаз (`Visible = False` под
`#If Not NETFRAMEWORK`, как это уже сделано для
`chkbox_Independent_Thread_For_File_Operation`), а её место занимает новая.
Сам контрол и его net48-обработчик остаются - net48 продолжает им пользоваться.

Новый текст:

- RU (ключ): **`Переходить к следующему файлу после копирования`**
- EN: `Go to the next file after copying`

Новый тултип:

- RU: `Если отмечено, после копирования программа сразу показывает следующий файл. Если снять галочку, после копирования остаётся текущий файл. По умолчанию включено.`
- EN: `If checked, after copying the app immediately shows the next file. If unchecked, it stays on the current file after the copy. On by default.`

Современная оболочка настроек: в
[src/Table_Form.ModernLayout.vb](../../src/Table_Form.ModernLayout.vb) строка
`"copy_mode"` заменяется на `"advance_after_copy"` - и в `AddSettingRow`, и в обоих
`Select Case` (заголовок + описание). Иначе новая галочка окажется без подписи, а
старый идентификатор - без контрола.

Персистентность ([src/Main_Form.Lifecycle.vb](../../src/Main_Form.Lifecycle.vb),
рядом с чтением/записью `CopyMode`):

- новый ключ `AdvanceAfterCopy`
- значения `"0"`/`"1"`
- дефолт `"1"`

Старый ключ `CopyMode`:

- в mainline больше не влияет на поведение;
- **продолжает читаться и сохраняться**, потому что net48 из того же реестрового улья
  им живёт (§0.1); mainline просто не даёт его менять;
- миграция в новый флаг **не нужна**, потому что это другая по смыслу настройка.

### 4.2 Клавиатура `0..9`

Это самый чувствительный участок: сейчас цифровые клавиши уже заняты переносом.
Нужен **рядом простой способ копирования**, не требующий захода в настройки.

Обязательное требование:

- у каждой горячей клавиши переноса должен появиться парный, легкообъяснимый путь
  копирования в тот же слот.

Рекомендуемая реализация:

1. `0..9` оставляем за **переносом**.
2. `Shift+0..9` вводим как **копирование** в тот же слот.

Причины выбора:

- это действительно «рядом»;
- не ломает мышечную память для основного сценария переноса;
- визуально и ментально объясняется просто: «цифра - перенести, Shift+цифра - скопировать».

Технические ограничения, которые надо учесть при реализации:

- ветка `If e.Shift Then` в `KeybUse` уже занята: `Shift+PageUp/PageDown` (прыжок на
  100 файлов), `Shift+R` (поворот против часовой), `Shift+T` (авто-OCR). Цифры с ними
  не конфликтуют, но новые `Case` добавляются именно туда, а не в `Else`-ветку.
- **`Shift+NumPad` ненадёжен**: при включённом NumLock Windows временно снимает NumLock
  на время удержания Shift, и вместо `Keys.NumPad1` приходит `Keys.End`, вместо
  `NumPad0` - `Keys.Insert` и т.д. Поэтому копирование вешается на **верхний ряд
  `Keys.D0..D9`**; `NumPad0..9` остаются только переносом. В подсказке/справке это надо
  сформулировать честно («Shift + цифра верхнего ряда»), а не обещать numpad.
- на `Shift+D2` и подобных `e.KeyCode` остаётся `Keys.D2` (символ `@` появляется только
  в `KeyPress`), так что `KeyDown` разбирает их корректно.

Альтернативы вроде `Ctrl+0..9` или отдельного режима клавиатуры здесь не рекомендуются:
они хуже читаются, хуже документируются и частично конфликтуют с привычными
системными сочетаниями.

### 4.3 Плавающий оверлей получателей

Сейчас оверлей показывает по одной строке на слот и клик по строке делает одно
действие, которое зависит от глобального режима.

После переработки глобального режима в mainline нет, поэтому оверлей должен явно давать
оба действия.

Требование спецификации:

- рядом с каждым **каталогом-получателем** в оверлее должны быть **две простые зоны
  действия**: `Перенести` и `Скопировать`.

Рекомендуемый UI:

- строка получателя = путь;
- справа две компактные кнопки или две явные кликабельные зоны:
  `M` / `C` или лучше локализованные `Перенести` / `Скопировать` в краткой форме.

Исключение: строка удаления (слот `-1`, подпись `× Удалить`) остаётся одним действием -
у удаления нет копии.

Нельзя оставлять вариант, где:

- строка делает только `Move`, а `Copy` снова прячется в настройках;
- строка делает «что-то одно» по неочевидному модификатору клавиатуры без подсказки.

### 4.4 Контекстные меню изображения/видео

Сейчас подменю строится как **либо** `Move to`, **либо** `Copy to`.

Это надо заменить на одновременную доступность обоих действий:

- `Переместить в`
- `Скопировать в`

Оба подпункта показывают один и тот же список слотов-получателей.
Различается только передаваемый `RecipientActionKind`.

Преимущество: пользователь видит оба варианта сразу, без скрытого режима.

### 4.5 Таблица получателей в настройках

Сегодня двойной клик по колонке 0 сразу исполняет действие для этой строки.
После отмены глобального режима такой запуск тоже не должен зависеть от несуществующей
галочки.

Требование:

- рядом с запуском `Move` в этой поверхности тоже должен существовать простой запуск
  `Copy`.

Рекомендуемый вариант:

1. двойной клик по номеру клавиши оставить за `Move`;
2. `Shift+двойной клик` по номеру клавиши сделать `Copy`;
3. строка 0 (DEL) - без изменений: удаление и по обычному, и по `Shift`-клику;
4. тултип и подсказку под таблицей обновить явно.

Допустима альтернатива с контекстным меню строки (`Перенести` / `Скопировать`), если
она окажется понятнее и чище в коде, но одинарный сценарий «только перенос» здесь
оставлять нельзя.

### 4.6 Панель миниатюр (`Image_Panel_Form`)

Панель - пятая точка запуска (§1.2.5) и единственная, которая копирует/переносит
своими руками, для мультивыделения.

Требование: после снятия глобального режима она не должна остаться поверхностью,
которая молча переносит всё, что раньше копировала.

Допустимые решения (в порядке предпочтения):

1. те же `Shift+цифра` = копирование выделенного, что и в главном окне, с явным типом
   в подтверждающем диалоге;
2. если полноценно свести панель на `ExecuteRecipientAction` в этой работе не выходит -
   зафиксировать это в спецификации явно и оставить панели собственный, но **локальный**
   выбор типа (параметр метода), а не чтение глобального флага.

Тихо оставить `Is_Copying_not_Moving` внутри `PoMove_for_Panel` нельзя: в mainline
этот флаг больше нечем переключить, и панель навсегда застрянет в режиме переноса.

### 4.7 Локализация

В проекте 13 языков, ключ - это русская исходная строка
(`Localization.T` / `TF` / `TC`), см. `CLAUDE.md`, раздел «Localization».

Требования:

- новые подписи, тултипы, пункты меню и подсказки регистрируются в таблицах
  [src/Localization/](../../src/Localization) (подписи настроек - в

## 5. Поведение файловых операций

### 5.1 История и undo

Существующая логика уже хранит `history_Was_Copy` отдельно от текущего флага и
должна быть сохранена как принцип: undo обязан отменять **фактически выполненное**
действие, а не читать текущие настройки UI.

После рефакторинга это должно стать проще:

- `Move` записывается как `Move`;
- `Copy` записывается как `Copy`;
- никакого участия глобального режима в undo больше нет.

### 5.2 Следующий файл после копирования

Новая галочка меняет только пост-эффект Copy.

Требования:

1. **Move** работает как сейчас.
2. **Copy + галочка ON**:
   после успешного копирования переход к следующему файлу.
3. **Copy + галочка OFF**:
   после успешного копирования остаться на текущем файле.
4. При ошибке копирования перехода не происходит независимо от галочки.

Поскольку .NET 10 всегда работает через фоновую очередь файловых операций, это означает:

- UI должен принимать решение на основании результата операции;
- если перелистывание делается оптимистически до завершения I/O, нужно отдельно
  проверить, что поведение `Copy + OFF` остаётся корректным и не ломает очередь.

Это главный технический риск данной работы.

## 6. Обратная совместимость и миграция

### 6.1 Поведенческая совместимость

- Основной быстрый сценарий `0..9 = перенести` должен сохраниться.
- Мышечная память существующих пользователей не должна ломаться для move.
- Копирование должно стать быстрее, но не ценой скрытого изменения старых move-путей.
- В net48 всё остаётся как было (§0.1).

### 6.2 Настройки

- `CopyMode` в mainline считается устаревшим и не влияет на поведение, но продолжает
  читаться/писаться ради net48 из общего улья `SZA\FastMediaSorter`.
- Если пользователь ранее оставил `CopyMode=1`, это **не** должно автоматически
  включать или выключать `AdvanceAfterCopy`, потому что смысл настроек разный.
- Старая mainline-версия, запущенная после новой, увидит `CopyMode` в прежнем значении
  и не сломается; новая при отсутствии `AdvanceAfterCopy` берёт дефолт `"1"`.

## 7. Риски

1. **Очередь modern + Copy without advance**:
   если нынешний код жёстко связан с немедленным показом следующего файла после любой
   операции, поведение `Copy + OFF` потребует аккуратного разведения UI- и I/O-слоёв.
2. **Размножение ad-hoc логики**:
   если каждая поверхность (`KeyboardInput`, `RecipientsOverlay`, `MediaMenu`,
   `Table_Form`, `Image_Panel_Form`) будет по-своему решать, что такое copy, поведение
   быстро разойдётся. Нужна одна авторитетная точка исполнения.
3. **Перегруженный оверлей**:
   добавление второго действия в строку может ухудшить читаемость на маленьких окнах.
   Нужен компактный, но однозначный UI.
4. **Коллизии клавиатуры**:
   `Shift+NumPad` работает не так, как ожидается (§4.2), а `Shift`-ветка уже занята
   четырьмя сочетаниями. Перед финальным выбором проверить, что цифры не перехватываются
   в фокусируемых контролах (поле пути уже отсекается в начале `KeybUse`).
5. **Расхождение сборок**:
   изменения идут в общем исходнике; забытый шов `#If NETFRAMEWORK` либо ломает сборку
   x86, либо тихо меняет её поведение вопреки §0.1.

## 8. Приёмка

1. Чистый запуск mainline: в настройках нет галочки `Copy mode`; вместо неё есть
   `Переходить к следующему файлу после копирования`, и она включена.
2. `0..9` по-прежнему переносят файл в соответствующий слот.
3. `Shift+0..9` (верхний ряд) копируют в те же слоты.
4. В оверлее у каждого каталога-получателя доступны и `Перенести`, и `Скопировать`;
   строка удаления осталась одним действием.
5. В контекстном меню одновременно видны `Переместить в` и `Скопировать в`.
6. Из таблицы получателей в настройках можно и перенести, и скопировать без похода
   к отдельной глобальной галочке; строка DEL по-прежнему удаляет.
7. Панель миниатюр не зависит от несуществующего глобального режима (§4.6).
8. `Undo` после `Move` возвращает файл назад; `Undo` после `Copy` удаляет созданную
   копию, а не трогает оригинал.
9. `Copy + AdvanceAfterCopy=ON`: после успешного копирования показывается следующий файл.
10. `Copy + AdvanceAfterCopy=OFF`: после успешного копирования остаётся текущий файл.
11. Ошибка copy/move не приводит к ложному переходу на другой файл и не ломает
    список/очередь.
12. `.\build.ps1` собирает обе сборки; в `FastMediaSorter_x86.exe` галочка `Copy mode`
    и её поведение сохранились без изменений.
13. `LocalizationParityTests` и `LocalizationCoverageTests` зелёные.

**Два отступления от текста спецификации, оба осознанные:**

1. **§4.1, персистентность.** Ключ реестра - ровно тот, что требовала спецификация
   (`AdvanceAfterCopy`, `"0"`/`"1"`, дефолт `"1"`, тот же улей `SZA\FastMediaSorter`),
   но пишется он не отдельной строкой в `Main_Form.Lifecycle.vb` рядом с `CopyMode`, а
   через уже существующий `ModernViewerPreferences` - механизм персистентности
   **только mainline-настроек** (`ReadBool`/`WriteBool` дают тот же формат значения).
   Отдельная строка в `Lifecycle` добавила бы второй механизм для одного и того же и
   потребовала бы заглушку для net48, которому настройка не нужна вовсе. `CopyMode`
   продолжает читаться и сохраняться, как и требует §6.2.
2. **§4.6, панель миниатюр** - взят **второй** из двух допустимых вариантов: панель
   сохраняет собственную реализацию для мультивыделения (она единственная работает
   сразу с многими файлами и не проходит через однофайловую очередь главного окна), но
   тип операции стал **параметром метода**, а не чтением глобального флага. Клавиши -
   те же, что в главном окне: цифра переносит выделение, `Shift` + цифра верхнего ряда
   копирует.

**Дополнительно к §5.2 (риск §7.1).** Оптимистичное перелистывание после копирования
сохранено (иначе быстрая раскладка встала бы на время I/O), но у операции появился флаг
`FileOp.AdvancedPastSource`: если копирование **упало**, а вид уже ушёл вперёд, UI
возвращается к тому файлу, на котором операция не удалась, - сообщение об ошибке
относится к картинке перед глазами, а не к уехавшей. Список при копировании не
меняется, поэтому починки списка тут не нужно.
