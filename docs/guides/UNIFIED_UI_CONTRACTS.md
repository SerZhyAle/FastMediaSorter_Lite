# Unified UI contracts - product profile, inventory and migration plan

> Status: **migration in progress, nothing here is a conformance claim.** Opened 2026-10-20 from local
> specification 243. The contracts are cited by id and section; their text lives in the shared catalog
> (see the pointer [UNIFIED-UI](../contracts/UNIFIED-UI.md)). A plan is not conformance: an adoption row
> advances only after measured proof.

## 2. Size-profile record (proposed, awaiting owner confirmation)

| Item | Value |
| --- | --- |
| Profiles | pointer/keyboard (default), touch (explicit user choice, today `ChromeSize = touch`), compact (explicit) |
| Ordinary targets | 32 pointer, 48 touch (logical px) |
| Compact floor (**provisional**, Q-2) | 28 - the value `ChromeMetrics.MinTarget` already holds and `UiSizing.CompactTargetFloor` declares; `UiSizing.TargetPx` never goes below the floor scaled by 0.75 (`MinTargetScale`), so a stray scale cannot shrink a target to nothing; to be tested on screen before a compact mode is exposed |
| Glyph tiers | 16 pointer, 20 touch, 16 compact; text-only enlargement grows a glyph by half of the text excess (`1 + 0.5 x (text - 1)`), never beyond 1.5 x its tier (`UiSizing.GlyphGrowthLimit`; reached at text factor 2.0), text factor bounded to 1.0..2.25 |
| Interface scale range | System, 90..150 percent plus presets (`UiScale`); a change must apply live (today the Settings window needs a restart) |
| Text enlargement | independent of interface scale; composes Windows text size once (not implemented) |
| Resolver | `src/Chrome/UiSizing.vb` (T-3, pure, linked into the Share Manager): tokens per profile and density, `DevicePx`, `TargetPx`, `GlyphPx`, `SystemTextScale()` (Windows Text size, read but **not yet wired** into any layout). `ButtonGlyphs`, `SettingsCheckBox` and `SettingsCollapsibleGroup` take their literals from it; the chrome keeps `UiScale` + `ChromeMetrics` (pinned equal by `UiSizingTests`, moved in T-9); dialogs still scale by DPI only (T-8) |

## 3. Permanent variants to record (not expiring exceptions)

- The viewer chrome is one semantic toolbar reached through F10 (ring mode) rather than ordinary Tab stops
  (`BUTTONS` section 4 rule 6 permits one tab stop plus arrows).
- Packed collapsed group headers are **off** in the viewer Settings window and the Share Manager; every
  header is its own full-width row. Initial group states are per-group flags in the page registration.
- The flexible path box in the chrome is a text field, not a command; it is the only element that stretches.
- The Share Manager settings window has no footer Accept/Cancel by owner design (Escape or Close leaves);
  a safe-default rule must not re-add a footer.
- Navigation identity inks (11 viewer pages, Manager aliases) stay: `SETTINGS-NAVIGATION` section 2 rule 3
  prefers identity-coloured destinations; the table is gated by `SettingsNavPaletteTests`.
- Settings rail breakpoint (`SETTINGS-NAVIGATION` section 2 rule 6): **no drawer; a documented minimum window width.** Viewer Settings
  window 780 x 400 logical, content column at least 480 logical px in all 13 languages at 100 and 150 percent (worst case German,
  547 and 561); Share Manager settings window 740 x 360 (raised from 640 on 2026-10-20; worst case Russian, 483 at both scales).
  Pinned by `SettingsRailTests` in both test projects.
- Rail glyph treatment: identity-coloured destinations with the monochrome ink only in the selected and high-contrast states
  (state, not a mixed level); the Manager's child destinations carry a glyph only where the catalogue has a meaning - 6 do, 14 are
  listed in `Share_Settings_Form.ItemsWithoutMeaning` as missing meanings (ICON-SET proposal owed, owner decision).

## 7. Open owner questions

- **Q-1** Do the Sftp and Media Exchange Server settings windows (two and one pages, same class as the
  Manager window) owe their own rail, a theme and language first page and an About last page? The contract
  gives small utilities no exemption, but a second editor for theme or language breaks "one setting, one
  editor". Options: keep one About and one general page reached from every window; or give each window
  both pages.
- **Q-2** Confirm 28 as the compact floor, or name another value.
- **Q-3** Share Manager rail child rows are 26 logical px by owner revision 2026-10-13; the pointer baseline
  is 32. Raise the hit target (visible height may stay lower where rows do not overlap) or declare compact.
- **Q-4** Website pointer targets are 44 px, which already meets the 32 baseline; only coarse pointers owe 48.
  Keep 44 for fine pointers as a recorded choice?
  *Recorded 2026-10-20 (T-10a):* `BUTTONS` section 3 and `UI-SIZING` section 2 are not silent (32 pointer, 48 touch), so the
  adapter applies them: 32 for a fine pointer and 48 under `@media (pointer: coarse)`, as rem tokens in
  `assets/fms-buttons.css` (`--btn-min`). 44 stays only on the site's plain text links and cards, which are not covered
  components. Keeping 44 for fine pointers instead would be a one-token change plus a dated registry exception; it is the
  owner's call. There is no explicit profile switch for hybrid devices: the browser's primary pointer decides.
- **Q-5** Website palette: remove `btn-gold` and allow one primary action per view?
- **Q-6** The Welcome wizard's buttons have a 44 px target by specification 184 rule 6, and its footer row is fixed at 32 px
  (no override in `DialogButtonRow`). The contract values are 32 pointer / 48 touch, so 44 matches neither. Convert the
  wizard footer onto `DialogButtonRow` at 32 (pointer) / 48 (touch) and retire rule 6, or keep 44 as a recorded
  permanent variant? Until answered the wizard footer stays hand-built (answer order Back first, forward last is already so).
- **Q-7** The `Image_Editor_Form` footer puts a command strip and the status line in one row; moving Cancel/Apply into
  reading order means regrouping that strip. Regroup (Cancel, Apply in a `DialogButtonRow` under the strip), or record the
  editor footer as a toolbar rather than an answer row?
- **Q-8** The close question of `Main_Form.Lifecycle` (unfinished file operations) stays a system box: there "No" closes the
  program and loses the queue, and Escape on a product-owned question answers "No", so routing it as it stands would turn
  Escape into "quit and lose the queue". Name the answers (for example "Keep working" as the Escape answer and "Close
  anyway") and move it onto `Ask_Dialog`, or keep it a system box as an OS-level confirmation?

## 8. Evidence protocol

Static reading proves nothing about pixels. Every `needs-runtime-evidence` row closes only with a real
capture or measurement that names build, device, locale, scale and contract version, using the existing
scenes (`SettingsLayoutScenes`, `SettingsTimingScenes`, `ModernChromeScenes`, `WindowsUiAudit`) extended
for the matrices of `BUTTONS` section 5, `BOOLEAN-OPTION` section 5, `COLLAPSIBLE-GROUP` section 5 and
`SETTINGS-NAVIGATION` section 6. The website has no browser harness yet; a render check is part of T-10.
