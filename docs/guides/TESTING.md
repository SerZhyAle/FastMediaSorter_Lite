# Автоматическое тестирование (три программы пакета)

Дата аудита: 2026-07-13. Обновлено и **перезапущено 2026-07-16** под раскладку «два
exe»: набор вьювера теперь **мультитаргетный** и гоняется под ОБОИМИ рантаймами
пакета. Все наборы зелёные, `Run-AllTests.ps1` exit 0:

| Набор | Результат |
|---|---|
| Вьювер, **net10** (мейнлайн `FastMediaSorter_LITE.exe`) | **51 тест** |
| Вьювер, **net48** (`FastMediaSorter_x86.exe`) | **17 тестов** |
| Share Manager (net10) | 36 тестов |
| SFTP-воркер (Go) | 5 пакетов |

Разница 51 vs 17 - не пробел, а сам смысл швов; наборы намеренно **разные**, потому
что вьюверы разные:
- **33 теста зума** (`ZoomMathTests`) - только net10: классической модели зума в
  x86-вьювере нет вовсе, `ZoomMath.vb` там компилируется в ничто.
- **3 теста декодера** в `ImageDecoderSeamTests` - только net10: проверяют то, чего
  net48 принципиально не умеет (анимированный WEBP без OS-кодека).
- **Тесты `LibWebp_*`** - только net48: бьют по `libwebpdecoder.dll` (libwebp 1.6.0,
  спецификация 270) напрямую через `LegacyLibWebp`, потому что через шов до него не
  достучаться (WIC на Windows 11 отрабатывает раньше фолбэка); `LibWebp_IsThePinnedBuild`
  сверяет версию и SHA-256 с `payload/libwebp/PROVENANCE.txt`.
- **`ImageBackendMigrationTests`** - только net10: таблица сигнатур (`ImageSignature`),
  отказ для всего, чего в ней нет (SVG/MVG/MSL/PDF/PS не доходят до ImageMagick),
  обход чанков WEBP/APNG (`AnimationHeader`), вырезание первого кадра без декода
  анимации, лимиты Magick (`Disk = 0`, площадь = бюджет декода).

> **Грабли, которые это поймало (2026-07-16).** Набор просмотрщика был **красным** с самого
> введения швов: `Lite.Tests` линкует `src/Utils.vb`, а тот после Ф0 зовёт
> `ImageDecoderProvider` из `src/Imaging/` - файла в проекте не было, сборка падала
> с `BC30451`. Починено линковкой шва (+ его хвоста: `AppFileLogger`,
> `Common_Module`, пакет ImageSharp 2.1.8) и **`DefineConstants=NETFRAMEWORK=True`**:
> SDK-проект под net48 эту константу сам не определяет - ровно та же грабля, что и в
> `src/FastMediaSorter.vbproj` (см. CLAUDE.md «Two builds, one source tree»).
> **Вывод: `Run-AllTests.ps1` надо гонять после правки любого шва** - линкующие
> проекты ломаются молча, обычная сборка приложения при этом зелёная.

Пакет Fast Media Sorter & Sharing for Windows состоит из трёх отдельных программ, у каждой свой рантайм
и своя тестовая система. Один оркестратор запускает всё сразу:

```powershell
.\tools\Run-AllTests.ps1              # все три набора (unit/логика), быстро, без сети/телефона
.\tools\Run-AllTests.ps1 -Integration # + живой round-trip по пайпу к запущенному воркеру
.\tools\Run-AllTests.ps1 -OcrScenes   # + стенд OCR-сцен на собранном вьювере (минуты, окно на экране)
.\tools\Run-AllTests.ps1 -SkipGo      # без Go-набора (если репозиторий воркера не склонирован)
```

Коды возврата - по контракту `CHECK-VERDICT` (общий помощник [tools/lib/Verdict.ps1](../../tools/lib/Verdict.ps1)):
**0** - всё, что запускалось, прошло; **1** - набор запустился и упал; **2** - не удалось проверить
(нет проекта, `dotnet`, `go.exe`, репозитория воркера, живого воркера) и при этом ничего не упало.
«Не смог проверить» никогда не считается проходом. Набор, выключенный `-SkipGo`, в таблице и в строке
вердикта значится как **SKIPPED**, а не как пройденный. Последняя строка прогона - вердикт, например
`Run-AllTests: PASS (4 passed)` или `Run-AllTests: COULD NOT VERIFY (not verified: worker-go, 3 passed)`.
Репозиторий воркера по умолчанию ищется рядом с этим (`..\fms_companion`); другой путь - `-WorkerRepo`
или переменная `FMS_WORKER_REPO`.

Какой раннер владеет какой проверкой, записано в [tools/check-placement.jsonl](../../tools/check-placement.jsonl)
(контракт `CHECK-PLACEMENT`), и `tools/Test-CheckPlacement.ps1` в каждом прогоне сверяет реестр с кодом
раннеров в обе стороны.

| # | Программа | Рантайм | Проект/набор | Команда |
|---|---|---|---|---|
| 1 | Сортировщик (просмотрщик) | net48 (x86-собрат) | `tests/Lite.Tests` (xUnit) | `dotnet test` |
| 2 | Менеджер воркера / Share Manager | net10.0-windows | `tests/Companion.Tests` (xUnit) | `dotnet test` |
| 3 | SFTP-воркер | Go | `P:\windows\fms_companion` | `go test ./...` |
| + | Реестр размещения проверок | PowerShell | `tools/Test-CheckPlacement.ps1` | всегда |
| + | Живой протокол (интеграция) | PowerShell | `tests/Integration/WorkerRoundTrip.ps1` | `-Integration` |
| + | OCR-сцены на собранном вьювере | PowerShell | `tests/Integration/OcrOverlayScenes.ps1` | `-OcrScenes` |
| + | Логика помощника службы (реестр выдач, блокировка, лог), без прав администратора | PowerShell 5.1 и 7 | `tests/Integration/ShareServiceHelperLogic.ps1` | `-Integration`, §5 |
| + | Повышенный помощник службы | PowerShell (администратор) | `tests/Integration/ShareServiceHelper.ps1` | запуск вручную, §5 |

**Сортировщик теперь два exe.** Мейнлайн `FastMediaSorter_LITE.exe` (net10, x64,
`src/Modern/FastMediaSorter.Modern.vbproj`) и `FastMediaSorter_x86.exe` (net48,
`src/FastMediaSorter.vbproj`) компилируют **одно и то же** дерево исходников (расхождения -
через `#If NETFRAMEWORK`). Набор `tests/Lite.Tests` **мультитаргетный** и гоняет ту же
логику под обоими рантаймами, так что «покрыты оба» - это факт, а не допущение.

Тестовые проекты **намеренно не входят** в `FastMediaSorter.sln` (в решении три проекта:
net48-вьюер, `Modern`-вьюер и Companion), чтобы не менять релизную сборку
(`build.ps1` / `release.yml`); их гоняет только оркестратор через `dotnet test`
(сам делает restore).

## 1. Вьювер (net48 + net10) - `tests/Lite.Tests`

Приложение почти целиком UI (WinForms/GDI+/WebBrowser/LibVLC) и потому в основном
проверяется вручную (см. CLAUDE.md «Testing & Validation» и чек-лист «оба exe» в
[BUILD_AND_RELEASE.md](BUILD_AND_RELEASE.md)). Юнит-тестами покрыта
**чистая логика, живущая только в просмотрщике** (не в Share-подсистеме). Исходники не
референсятся как сборка, а **линкуются** (`<Compile Include>`), чтобы не тянуть
весь ILMerge/LibVLC/Tesseract-хвост; `RootNamespace=fmsl`, так что модули видны по
своим именам.

Переименование net48-сборки в `FastMediaSorter_x86` набор **не задело** (он линкует
исходный `src/Utils.vb`, а не референсит выходную сборку), а вот **введение швов -
задело**: линкуемый файл потянул за собой `src/Imaging/` + `AppFileLogger` +
`Common_Module` + ImageSharp, и проекту понадобилась своя `NETFRAMEWORK=True` (см.
врезку вверху).

### Мультитаргет - зачем

`<TargetFrameworks>net48;net10.0-windows</TargetFrameworks>`. Линкуемые исходники
компилируются в ОБА поставляемых exe, поэтому и проверяться должны под обоими
рантаймами: прогон только под net48 ничего не сказал бы про сборку, которую
получает большинство пользователей. Каждая нога тянет **свой** декодер - ровно тот,
что везут сами вьюверы (с 2026-10-25, спецификация 270: net48 - WIC + libwebp 1.6.0 из
`payload/libwebp/`, net10 - Magick.NET-Q8-x64 15.0.0), так что тестируется настоящая
пара декодеров. `dotnet test` прогоняет обе ноги сам.

### Что проверяет `ImageDecoderSeamTests`

- **`Provider_ResolvesThePlatformDecoder`** - тот самый тест, который поймал бы
  забытую/опечатанную `NETFRAMEWORK`: под net48 провайдер обязан отдать
  `LegacyWicImageDecoder`, под net10 - `ModernMagickDecoder`. Без него подмена
  декодера проходит молча (компилятор не ругается, приложение собирается).
- **`ModernDecoder_DecodesAnimatedWebp_WithoutAnOsCodec`** (только net10) -
  пиннит причину всей миграции: анимированный WEBP декодируется без OS-кодека
  (на Server 2025 его нет), отдаётся как GIF-транскод, чтобы завёлся существующий
  GDI+-путь анимации. Файл-фикстура не нужен - webp зашит байтами в тест.
- **Деградация** - битый webp обязан вернуть `Size.Empty`, а не бросить исключение
  (фоновый воркер зовёт `GetImageDimensions` на всём, что лежит в папке). Проверяется
  под обоими рантаймами.

Под net48 webp-тесты сознательно выключены (`#If Not NETFRAMEWORK`): там путь идёт
через WIC и зависит от наличия в системе кодека «WebP Image Extensions», то есть
результат менялся бы от машины к машине. Это не пробел покрытия, а зафиксированная
разница поведения.

Покрыто (12 тестов): `Utils` -
- `AddAt`/`RemoveAt` - вставка/удаление в массиве по индексу (края и середина);
- `GetOppositeColor` - контрастный чёрный/белый по яркости фона;
- **`GetImageDimensions`** - разбор размеров из ЗАГОЛОВКА файла (PNG/GIF/BMP/JPEG)
  без GDI+-декодирования. Это критично: фоновый воркер читает размер, пока UI-поток
  может делать `GetPixel` по тому же изображению, и параллельный GDI+-декод портит
  общее состояние. Плюс поведение на неизвестном/отсутствующем файле (`Size.Empty`).

WEBP-ветка `GetImageDimensions` (через WPF `BitmapDecoder`) в юнит-тестах не гоняется
(нужен реальный webp + инициализация WIC) - проверяется вручную при загрузке webp.

## 2. Менеджер воркера / Share Manager (net10) - `tests/Companion.Tests`

Референсит проект `FastMediaSorterCompanion` и проверяет **портированную Share-логику**
(она же покрывает соответствующий код, ранее живший в просмотрщике - это один и тот же код).

Покрыто (25 тестов):
- **`ShareRootParams`** - таблица истинности `IsWritable()` (обычная/RO/destination),
  `IsDefault()` (все дефолты -> v1; любое поле -> не дефолт; слайдшоу 10с = дефолт),
  `Clone()` (глубокая копия + нормализация null), `Store.GetFor` неизвестного пути ->
  дефолт без записи в реестр. Это единый источник флага readOnly - если он «поедет»,
  вернётся баг «телефон показывает Move/Delete, а SFTP rm запрещён».
- **`WorkerIpc` (замороженный протокол пайпа)** - точная форма JSON запроса
  `SetSharedFolders` (`schemaVersion`/`type`/`folders[].name/hostPath/readOnly`),
  пропуск `folders` у `GetStatus` (`WhenWritingNull`), разбор ответа воркера
  (camelCase -> PascalCase DTO, вложенные status/reachability/roots), envelope ошибки.
- **`ShareConfigBuilder` (замороженный контракт `.fmscfg`)** - `Build` строится из
  in-memory статуса (без воркера): обязательные ключи, порядок `accessPaths`
  (`lan` -> `ipv6` -> `portforward`), пропуск внешних адресов при «только LAN»,
  сейф-гард «не включать пароль», per-root `readOnly`, рендер QR-PNG. **Android-клиент
  выпускается ровно против этой формы** (SPECIFICATION_QR_IMPORT_ANDROID.md).
- **`ShareText`/`NetworkInfo`/`ServerFeatures`** - локализованные строки RU/EN
  непусты и различаются, `AccessNote` не падает на null-reach, `LocalIPv4` - валидный
  IPv4 или пусто, гейт серверных функций (`IsEnabled/CanEnable/MarkerPath`) безопасно
  вызывается в любой момент.

`WorkerIpc.Send` по РЕАЛЬНОМУ пайпу проверяется интеграционным набором ниже, а не
юнитом (нужен запущенный воркер).

## 3. SFTP-воркер (Go) - `P:\windows\fms_companion`

`go test ./...` (Go в `C:\Program Files\Go\bin`). Замороженный бинарник не трогаем -
исходники живут в **отдельном репозитории** (правило CLAUDE.md), тесты запускаются
там же.

Покрыто (4 пакета, все зелёные): `internal/config` (схема `.fmscfg`), `internal/ipc`
(протокол пайпа), `internal/netaccess` (проброс порта/reachability), `internal/sftpserver`.

**Пробел покрытия (для follow-up):** без тестов - `internal/app`, `internal/service`,
`cmd/worker`, `cmd/devserve` и корневой пакет. Это в основном lifecycle/точки входа;
кандидаты на добавление unit-тестов - `internal/app` (сборка статуса, применение
shares) и `internal/service`. Оркестратор явно печатает число пакетов без тестов,
чтобы пробел не выглядел как «всё покрыто».

## 4. Живой протокол (интеграция) - `tests/Integration/WorkerRoundTrip.ps1`

Framework-free проверка: коннектится к `\\.\pipe\fms-companion` запущенного воркера,
шлёт `GetStatus`, валидирует форму ответа (Appendix A). **Только чтение** - никаких
`SetSharedFolders`, `shares.json` пользователя не трогается. Если воркер не запущен, проверять
нечего: `WorkerRoundTrip: COULD NOT VERIFY`, exit 2 - не проход и не падение. Запустите Share
Manager (или воркер) и повторите с `-Integration`.

## 5. Повышенный помощник службы - `tests/Integration/ShareServiceHelper.ps1`

Проверки `publishing/installer/install-share-service.ps1` из тикета 054 (H-09, H-13, H-14).
**Нужна PowerShell с правами администратора**; без них скрипт пишет `NOT RUN` и выходит с
кодом 2 («не удалось проверить»), а не 0. В `Run-AllTests.ps1` не входит: оркестратор работает
без прав администратора.

- Всегда (служба не затрагивается, всё во временном каталоге под `%ProgramData%`, добавленные
  ACE снимаются): `grant-roots` выходит с кодом 12, а не 0, если хоть одна папка не выдана
  (её нет, или это системная папка), пишет причину и выдаёт остальные; перевыдача при
  start/restart (`Grant-StateRoots`, загружается из самого помощника) касается только папок из
  защищённого реестра одобренных и не выдаёт ничего, если реестр эту защиту потерял.
- Только с `-ServiceInstall` и только если служба `FastMediaSorterCompanionSFTP` **не**
  зарегистрирована (то есть на ВМ): `install` регистрирует службу от `NT AUTHORITY\LocalService`,
  затем `remove` её снимает - вместе с правилом брандмауэра «FastMediaSorter Companion SFTP».

Тикет 102 (реестр выдач `granted-roots.json`, лог, блокировка) добавляет к этому набору:

- Всегда (только `grant-roots` во временных каталогах): реестр `[]` допускает первую выдачу;
  пустой файл, битый JSON и запись без `path` дают код 15, ничего не выдают, файл остаётся
  побайтно прежним и без `.tmp-`/`.bak-`; повторные выдачи сохраняют всю историю, итоговый
  файл принадлежит Administrators, защищён от наследования и содержит только SYSTEM и
  Administrators; четыре помощника параллельно на одном каталоге не теряют записей.
- Только с `-ServiceInstall` (ВМ): `remove` без каталога состояния завершается кодом 0, не
  создаёт каталог и оставляет запись в `%TEMP%\install-share-service.log` повышенной учётной
  записи; `remove` с нечитаемым реестром оставляет его побайтно прежним и пишет
  «completed WITH WARNINGS».
- Параметр `-HelperShell powershell.exe` запускает один и тот же помощник под Windows
  PowerShell 5.1 (установщики запускают именно его), даже если сам скрипт идёт под `pwsh`.
  Прогоняйте оба.
- Без прав администратора `tests/Integration/ShareServiceHelperLogic.ps1` грузит функции
  самого помощника через AST и проверяет ту же логику с поддельным `icacls` (чтение и форма
  реестра, публикация через временное имя, откат выдач, коды 15/16/17, блокировка, лог,
  неполный отзыв при `remove`). Подмены (SYSTEM/Administrators -> текущий пользователь,
  поддельный `icacls`) названы в самом скрипте; настоящее владение и ACE проверяет только
  `ShareServiceHelper.ps1` на ВМ. Сценарий деинсталлятора (S23-1) - только ручной, на ВМ с
  настоящим установщиком; жёсткое прерывание процесса между выдачей и записью реестра
  автоматикой не покрыто.

Коды возврата: 0 - всё прошло, 1 - проверка упала, 2 - не проверено.

**Уязвимости ImageSharp 2.1.8 - ЗАКРЫТО (2026-07-16) бампом до 2.1.13.**
Раньше restore ругался `NU1903`/`NU1902` (4 advisory) на ImageSharp 2.1.8, который
везёт net48-вьювер через `packages.config`. Здесь ранее предлагалось три варианта, и
один из них - «урезать x86 по `FEATURE_FULL`, тогда ImageSharp там не нужен» - был
**просто неверен**: ImageSharp в x86 тянет `LegacyWicImageDecoder` (запасной декодер
WEBP), а не OCR/перевод/Share, поэтому урезка фич эту зависимость не убрала бы.
Настоящее решение оказалось скучным: **в линии 2.1 есть 2.1.13** - тот же net472,
та же лицензия Apache-2.0 и **ровно те же 5 зависимостей**, что у 2.1.8 (дельта

**Найденный при этом настоящий предел (не регрессия):** ImageSharp **2.x не умеет
анимированные WEBP вообще** - поддержка появилась только в 3.x. Значит на
**Windows 7/8.1**, где у WIC нет WebP-кодека, x86-вьювер анимированный WEBP открыть
не может **и никогда не мог**; на Windows 10/11 он открывается через WIC до
фолбэка. Исключение ловится в `FileManager.LoadImageWithStream`, приложение не
падает. Зафиксировано тестом `BundledImageSharp_CannotDecodeAnimatedWebp_KnownLegacyGap`.

> **2026-10-25, спецификация 270:** ImageSharp убран из обеих сборок (лицензионный ключ).
