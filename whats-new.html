Added

  • Image decoding without a licence-keyed library (specification 270): the 64-bit viewer and the Share Manager now read and write pictures through Magick.NET 15 (ImageMagick) instead of ImageSharp; the 32-bit viewer reads the WEBP files Windows cannot through libwebp 1.6.0 instead. The same formats open as before and no new ones were switched on: the file's own header decides the format, and anything outside the known table (SVG, PDF, PostScript, ImageMagick scripts) is refused without being handed to the decoder. Size limits are checked from the header before any pixels are allocated, nothing spills to temporary files, and a long animated WEBP still shows its first frame without decoding the whole animation. The editor keeps EXIF, ICC, XMP and IPTC, removes the stale embedded thumbnail and saves JPEG at quality 92 and WEBP lossless as before. The decode cache format moved to version 3, so pictures cached by the old decoder are decoded again once. The 32-bit viewer still runs on Windows 7/8.1 and still cannot open animated WEBP there. Every build and package is checked for leftover ImageSharp files, and malformed BigTIFF and ICC files are tried in isolated processes on every test run. That check found that a local release-style build (ZIP, both setups, MSIX) also packed the rollback copies of old programs the local build keeps; they are left out now. Not yet tried on a real Windows 7/8.1 machine, from an installed Store package or in a Manager-only Server installation.
  • Exchange outside links: creating, rotating and removing a folder link now shares one transaction boundary with background publication, so an older publication pass cannot restore the previous link state. Deterministic create/remove and snapshot-ordering regressions preserve the sealed-record and PIN/proof checks.
  • Release help and catalog actions: the live receiver, Live Broadcast producer and Google Drive settings have real window captures in all 13 languages and both themes. Live help explains source selection, explicit start, listener credentials, link/file hand-off and stop. Help generation requires existing captures and never draws substitute windows. Skip and Create desktop shortcuts use their dedicated catalog glyphs. README/site/Store copy describes modern JXL viewing and the implemented live producer/receiver; physical-device acceptance remains open.
  • Legacy WebP fallback hardening: after WIC refuses an image, the x86 viewer validates the WebP header and explicitly invokes the WebP decoder. A TIFF disguised as WebP never reaches the fallback decoder. Normal WebP fallback behavior remains covered. (The fallback decoder itself is now libwebp, see specification 270 above, which also closes the ImageSharp remediation of specification 266; dependency warnings were never suppressed.)
  • File manager mode in the Grid panel (modern viewer, specifications 256-262): the F3 panel features an integrated file manager mode accessible via the toolbar mode selector ("Sorting" vs "File manager"). It allows independent browsing of local drives, configured SFTP/SMB resources, and connected exchange devices with full address bar navigation, Back/Forward/Up/Refresh history, and content filtering (Media only, Media & documents, All files, plus hidden files toggle). File operations (copy, move, rename with case-only support, new folder, delete to Recycle Bin or permanent deletion, and undo) execute through the application's shared operation queue. Includes built-in verified ZIP creation with SHA-256 and CRC readback verification, safe ZIP/7z/RAR extraction with path traversal guards, safe opening policies blocking executables and scripts, and a dedicated settings page under modern preferences. The legacy x86 .NET Framework 4.8 viewer retains its existing triage panel unchanged. Combined acceptance suite and operational guide added (docs/guides/FILE_MANAGER.md).
  • Live broadcast: share one window, and listener passwords the exchange server can check (specification 263): the Share Manager's Live Broadcast window can capture a single chosen window instead of a whole monitor (a closed window ends the broadcast with one sentence, a resized window keeps its proportions with bars instead of stretching). A password-protected broadcast can now go through the exchange server too: the server checks the listener's password against salted hashes the broadcaster uploads and never holds the password itself, and the Live window says in words when the exchange server declines to list a broadcast. The copied broadcast link now uses the fmsbcast://import form. On air, "Allow viewers on my network" can be changed without stopping the broadcast, a change of the PC's network address updates the broadcast by itself, and the viewers who come through the exchange server can be capped (0 means no cap). Covered by automated tests, including a run against the real exchange server program; the broadcast has not been tried on real devices.
  • Encrypted exchange broadcasts (modern viewer, specification 234): the viewer opens sealed media from the exchange server before handing it to the player, verifies the producer's pinned TLS certificate inside a broadcast tunnel, and stops on a damaged or unauthenticated stream. Guest broadcast access uses a separate group key and follows guest-device changes and withdrawals. The first connection to an exchange server asks once per server identity, and server settings and the privacy page explain content encryption and visible metadata. Folder guest access retains the existing availability gate.
  • Google Drive channel in the Share Manager (specification 203): Manager settings has a "Google Drive" page right after "Exchange account": sign in with your own Google account, see the state in plain words, sign out. It asks Google only for the app's own hidden storage on your Drive (drive.appdata) - no access to your files - and signing out deletes this PC's records there, revokes the grant and removes the stored token. While signed in, the PC lists itself and each shared folder in that storage (name, identity and lock mark only, never an address, password or link), and the viewer's resource list shows what your other devices list there; such a folder is listed but cannot be attached through Drive. Offline help describes the page in all 13 languages. A build without a Google sign-in client of its own shows "not configured in this build", the Sign in button stays off and nothing is written; no release build carries a client yet. The viewer shows the Drive rows only on a PC that also has an exchange-server account. Not tried against a real Google account or on two PCs yet.
  • Disk autostart visible in both lists (specification 254): the Share Manager's .fdd disk table shows an Autostart column with Yes/No for every disk and a dash when the worker does not support the setting. FileDO rows in the main resource list also mark enabled autostart. Both lists update after disk actions, and the disk table fits its rows and measures localized column text. The selected disk's note keeps the worker's error and uses the same autostart text. All 13 UI languages and offline help, plus the disk guide, describe the mark. No setting or protocol changed.
  • Two settings windows instead of three (specification 253): the Share Manager's SFTP sharing pages (Network and Hosting) now sit in Manager settings, in a group headed "SFTP sharing" between General and Scheduled file operations, with page titles and search results that repeat the scope ("SFTP sharing: Network"). The group is there while the SFTP sharing component is installed; a deep link to it without the component gets the usual "component unavailable" message. The tray has one "Manager settings" entry plus the local exchange server entry, and the footer link switches between the two windows. The unapplied port draft still survives page and window switches and is asked about on close only while it is pending. The window remembers its page from the former SFTP window the first time and nothing stored is rewritten or deleted. Offline and in-app help, the settings guide, the READMEs and the site pages now describe two windows. No setting, file or protocol changed. Not looked at on a 150/200 percent display, in high contrast or with a screen reader yet.
  • Exchange server status that agrees with itself, and the build in every log: the Share Manager's tray item and the exchange settings window could disagree - the tray said "stopped" for a state it had not read (before the first read, an unknown or a stopping service) while the window, refreshed only after its own actions, kept an old "running as a Windows service". The tray now names a server stopped only on a read that says so, the window re-reads the service state on its poll tick whatever the group's fold state, and both write what they show to the log. A failed "is my server visible from outside" check now logs why (refused, slow, no network). Every log file now starts with the program version: the Share Manager's session header, each daily server log and audit file, and the service installer's helper log (server and binary hash).
  • Share Manager details (specification 252): a broadcast whose lifetime the worker has marked as final now reads «Expired» in the Expires column of the broadcasts window, in all 13 languages, instead of its old end time. The access-test window draws a server that hung up before answering as a warning, the same way the resource list in the viewer does. The .spres file of a broadcast no longer lists an outside address that the broadcast gateway's own check found closed (an address never checked is still listed), the same choice the folder-share file already made. Not looked at on screen yet.
  • Logs are redacted as they are written and again when they are packed (specification 252, diagnostic report 0.14): in the 64-bit viewer and the Share Manager, every log line now passes a redactor before it reaches the file, and the "send logs to the author" archive redacts each line again before a long log is cut to its head and tail. Passwords, access PINs, device tokens, pairing codes, exchange logins and server addresses, certificate fingerprints, secret query parameters (also after an HTML-escaped separator), credentials inside web addresses and whole private-key blocks become [REDACTED], so a cut log can no longer begin in the middle of a key and the product no longer depends on every writer keeping such values out. The Server host's support collector follows the same order (redact, then cut) with the shared truncation line, and its archive is now fms-host-logs-<stamp>.zip with an environment.txt; the computer name is no longer in the file name. Tried on made-up secrets only; a real bundle from a machine with exchange logs and the mail hand-off were not tried again.
  • One row per live source in the exchange broadcast list (specification 252, live broadcast): when the exchange directory holds two records of one source (the same sourceId, for example a broadcast restarted before the old record expired), the «Open live broadcast» window now lists one row, the one that started later, instead of two rows for the same channel. The records are ordered by their start time, not by the writing device's clock, as the exchange contract states. Records that are refused, or that name no source, are still listed as before. Modern viewer only.

The site and the READMEs now describe the product as three independent, optional parts - the media viewer and sorter, local SFTP folder sharing (FileDO disk hosting is a capability of sharing, not a part of its own) and a server that is still in development - and two install intents: viewer first (the full package, the ZIP, winget or the Microsoft Store) and server first (the Server edition, with the viewer as an unticked extra). The server page carries an availability table: what each package installs by default, which parts are optional, where hosting runs unattended and where administrator rights are needed. The Microsoft Store copy says what the Store package is: the viewer and the Share Manager, with no Windows service and no FileDO hosting.

The free release pre-flight tools\Build-OfflineRelease.ps1 no longer stops on a leftover -Server argument of Stage-ServerViewerPayload.ps1 (found by a full local run), and a new test reads every Stage-*.ps1 call of the packagers against the parameters the script declares.
  • Separate sharing settings: SFTP sharing and the local exchange server now have independent settings windows with reciprocal links and direct tray access. Manager preferences, remote-account publishing and schedules retain their own home. Each window remembers its context; switching windows preserves an unapplied SFTP port. Updated offline help keeps the old topic anchors working.
  • Exchange clipboard and audit: the Share Manager's exchange-account settings now offer Send, Get and metadata-only Refresh, with each account's slot size and an explicit encrypted-size label. Server connections and administrative changes have a bounded daily operational audit with safe setting deltas, refusal results and no clipboard contents or credentials.   • A refused copy or move names the real reason on the status line (64-bit viewer). When a recipient folder could not be reached, the line used to say only "no connection with the folder". It now says what the system actually reported: the computer is not found on the network (off, on another network or the name is wrong), the shared folder does not exist on it, the network to it is down, the connection was cut, the drive or card is not ready, or - for a folder on a saved server - the server's own answer (the login was not accepted, the folder is denied, the server did not answer in time). The name in the sentence is the computer, share, drive or server from the folder's path. A folder that does not answer within the check's limit says "did not answer within N s" at once, and if the check finishes a moment later with the real cause the line is restated with it. Every refusal, including the "this resource does not allow this operation" one, is now written to the log with its reason; before, a refusal left no trace in a release build. No exception text is shown. Strings are in all 13 UI languages.
  • A long animated WEBP opens at once (64-bit viewer). A large animation used to hold the window until the whole file was decoded and turned into a GIF - 21 seconds for a 711-frame sample, longer than the 20-second wait the viewer allows, so such a file was refused as "too slow". Now the first frame appears immediately, the status line says Animation is being prepared.. frames: N while the rest is converted in the background, and the finished animation replaces the first frame in place (zoom, pan and the picture frame stay as they were) and starts playing. The conversion is cheaper too: for animations up to 100 megapixels in total it still uses the dithered palette, and above that it skips the dithering, which halves the time for the largest files with no visible difference at normal speed. Details you may notice: the editor, OCR and translation buttons stay hidden while only the first frame is shown (a save would flatten the animation); turning the first frame with R keeps it as you turned it; an animation too long for the decode budget (over 400 megapixels in total) is no longer dropped from the list - its first frame is shown with a line saying so, and "Replace with video" is offered for it; preview thumbnails and the look-ahead for the next file use the first frame only and never convert a whole animation unasked. Decoded animations are cached on disk up to 128 MB per file (was 64 MB), and a one-line Animation prepared: entry in the log names the size, the frame count, the time spent and whether it was cached. The 32-bit program for Windows 7/8.1 is unchanged. Strings are in all 13 UI languages (spec 241).
  • Long animations can play as a short-lived encrypted video (64-bit viewer, setting "Animated graphics through video", on by default). A long animated WEBP, an animation over the decode budget and a huge GIF (16 MB or 50 megapixels and up) are no longer swapped in as a GIF: FFmpeg encodes them in memory, the video is sealed into a temporary FileDO container under %TEMP%\FastMediaSorter-av with a key that exists only in the running program, and LibVLC plays it silently in a loop. No plaintext video byte is ever written to disk, the original is never changed, locked or deleted, and the previous video is removed the moment you leave its file. While one plays, the next animation in the folder is prepared in the background at low priority and starts at once when you flip to it (never more than two containers at a time); a leftover folder of a killed program is swept at the next start. A video has no zoom, pan, perspective bars, OCR or editor, and the setting's hint says so; switching the setting off restores the previous behaviour at once. FFmpeg is not bundled: the first eligible file asks once to fetch it, and a No is remembered (the Settings button remains). If anything fails the file opens as before and the status line says Animation shown without video. The 32-bit program for Windows 7/8.1 is unchanged (spec 242).

  • "Send the logs to the author" keeps both ends of a long log, brings the rolled-over log along and adds a machine-readable summary (64-bit program and Share Manager). A log longer than 2 MB used to contribute only its last 2 MB, so the start of the session - the version and the settings the program logs on startup - was missing. It now keeps the first 256 KB and the latest part, with a line [Diag] LOG TRUNCATED | dropped_middle_bytes=.. between them that says exactly how much was left out; the text is cleaned of your Windows user name before it is cut, not after, and a log too large to scan at all (over 64 MB) is replaced by a one-line marker instead of being read. The log the program rolled over at 8 MB (previous.log, and companion.previous.log for the Share Manager) now travels with the current one, from the folder where the current one was found. The archive is named fms-logs-<version>-<date>-<time>.zip without the random tail it used to carry, and holds an environment.txt beside report.txt: program version, runtime, system, architecture and language as key=value lines in UTC with schema_version=1, and nothing that names a person or a path. The dialog before sending lists the new file like every other, and the program still hands the archive to your own mail client rather than sending anything itself.
  • Switching the interface language in the Share Manager settings window is quick again (64-bit Share Manager).   • Send the clipboard to your exchange server and get it back with one press (64-bit Share Manager; the Drive path is not in this build). The Share Manager's main window gets two buttons, "Send the clipboard to the server" and "Get the clipboard from the server", and its tray menu the same two items; the settings page has "Create desktop shortcuts", which makes two desktop shortcuts that run the same functions (--clipboard-send / --clipboard-get) - nothing is created unless you press it. Send reads the clipboard once - one file, else an image, else text - and puts it on every server your accounts reach, with one result line per server; get takes the newest value by the servers' own receive time, names the device it came from and puts it into the clipboard (a text or an image as such, a file saved under its own or a free name into the received-files folder, Downloads by default, and placed as a file drop; a file is never overwritten and keeps the Windows "downloaded from the internet" mark). Several files or a folder are refused with "one object at a time: archive them first" and nothing is sent. A clipboard another program holds ends in a sentence within a few seconds, never a hang; the reading runs off the interface thread with a progress line and a cancel. The shortcuts are not available in the Microsoft Store package (it has no command-line entry for them); the buttons and the tray items are. Strings are in all 13 UI languages.   • The exchange server hands out one-time invitations, lets people register themselves and manages accounts through their whole life (server and Share Manager; the server component stays out of released packages). The operator creates an invitation - for a member or for a guest - and gets a one-time code and a connection string (FMSEXCH1:..&i=<code>, with a QR code) to hand over; the code never expires, is spent by the first registration that succeeds and is kept on the server as a hash only, the log showing eight hex digits of it. An optional shared invitation password lets a group register without a code each (it can be switched off by clearing it). A new person registers from the connection string alone: the server checks the rate, the invitation, the account cap (10 by default, changeable), the login and the password policy in that order, and a refused attempt spends nothing. Guests can read and receive but are refused publishing, broadcasting, uploading and casting (not-permitted); the directory a guest sees is filtered. Each account can carry its own limits (clipboard 5 GiB by default; the number of devices, folders, broadcasts per device). Changing or resetting a password signs the account's other devices out - they learn it on their next hello - while their records stay until someone deletes them; an account can delete itself through the same path the operator's removal uses. Password checks are paced at one per second per login and per address, with no lockout and no growing delay - nothing remembers a wrong password, so the right one is checked within a second of its turn. The Share Manager's exchange page gets the invitation list (create, withdraw, copy, show the QR code), the shared password, the account kind and the limits dialog in all 13 languages; the same operations are available from the server's command line and the local admin channel. The wire vectors are regenerated for DEVICE-EXCHANGE 0.28, and the viewer's connection-string reader now names the invitation member i (it read inv), so a string made by the server is read by the viewer and the reverse.

  • Scheduled file operations in the Share Manager (64-bit; not in the 32-bit fallback). A new page of the Share Manager's settings, "Scheduled file operations", lets you define an operation - copy, move, delete or archive the files of a folder, selected by type, name mask, exclude mask, age, size, time since the last run or "last hour / last day" - and run it on a daily time plus a repeat interval (15 minutes at least), by hand, or both. The feature is part of the Share Manager: it is installed with the share component, run by the Share Manager while it is running in your session, and managed from its settings and its tray menu; the viewer only has one folder-menu entry, "Schedule an operation for this folder..", that opens the page with the folder as the source. Sources and targets are folders of this PC (local or UNC) or registered SFTP/SMB resources; a run asks nothing, so a resource whose password is not stored or whose key is not pinned stops the operation with one note instead of a question. A delete follows the viewer's own Recycle Bin setting and what the volume allows (a permanent verdict is shown in the editor and recorded on every log line - it is never silent and never asks); an archive is one timestamped zip per run, and "delete the originals after verification" removes them only after the archive has been read back and every entry checked; name clashes are skipped, overwritten or kept as name (2).ext. A run that was due while the program was closed is run once at the next start, or skipped - your choice per PC; Pause all stands the schedule down and nothing catches up when it is released. History and a journal of every moved or deleted file stay on this PC (%LOCALAPPDATA%\SZA\FastMediaSorter\scheduled-operations); nothing is sent anywhere. The share component's description in the installer now says it, in all three installer languages; strings are in all 13 UI languages.
  • Switching a settings page or opening and closing a group lays out only the page you are on, once (64-bit viewer; the window looks the same). A page switch used to measure all eleven pages and every row sized itself with the page's layout live, so a toggle or a switch cost a layout pass per row; the group now holds its own layout and its page's while it changes, the shown page is sized once with its group bodies held, the other ten are left alone and the remembered scroll position is restored after that layout. The page is the same, which was checked rather than assumed: every control's bounds, the scroll range and the rendered pixels of 110 steps - both passes over the eleven pages, every group, expand and collapse all, reopening, resizing - are identical to the previous build at 100 % and at 175 %, and the layout passes of a step fell from 1704 to 915 over a first visit of all pages and from 2499 to 1367 over sixty group toggles. On a quiet machine a repeat visit of a page took about 16 ms instead of about 45 ms and a group toggle about 14 ms instead of about 39 ms. The settings window's own opening was not changed and is still slow; FMS_UI_TIMING=1 makes the viewer write how long each page and window took to its own log (a switch for measuring, nothing is sent anywhere).
  • Japanese, Chinese and Korean lettering is read as text instead of one spaced character at a time, and two touching speech balloons stop being one plate (both viewers). The recognizer cuts CJK lettering into single characters, and the overlay used to put a space between every two of them - コモ ナ 市 長 の 私 が for コモナ市長の私が - which broke search, gave the translator a boundary the lettering does not have and made the plate's source text longer than the lettering it covers. A line's words and a plate's lines are now joined with no space where they meet on Han, kana or CJK punctuation (the fullwidth comma, the prolonged sound mark and the middle dot included); a space next to a Latin word, a digit or an ASCII mark is kept, and a Hangul pair is joined only when its two boxes stand under a third of the line's type height apart, so Korean keeps the spaces between its words and loses the ones inside them. Separately, a word whose box stands more than 1.6 times the line's median word height - the touching outlines of two adjacent balloons, which the recognizer reads as one tall token of the stitched line - now ends the plate before it, where the gap rule could not see it. Both are the shared OCR contract's amendments 1.7 A and 1.8, held by the reference implementation's own cases. Nothing that is decided moves: which lines are kept and which attempt wins still read the spaced text. The OCR pipeline version is 11, so a result cached by an earlier build for such a page is read again once.

The service runs under its own Windows account rather than yours, so a folder you can obviously open may be invisible to the thing that actually serves it - and the fix was a button in the "Manage hosting.." window, which nobody has any reason to look for after simply adding a folder; until you found it the phone got a folder it could not open, with no explanation anywhere. Now the permission is granted at the moment you choose the folder: the program checks first and stays silent when nothing is missing, so the single Windows confirmation appears only when it is actually needed, and declining it says what it costs instead of failing later on the phone. The second half: that grant only ever gave read access, so a folder marked writable let the phone browse and download and then refused every delete, move and upload. It now follows the folder list - read for a read-only folder, read and write for a writable one - and switching a folder to writable afterwards re-applies it instead of quietly leaving the old read-only permission behind.
  • Share Manager: "Check access from the internet" stops being permanently grey on a share that works. The button was disabled for the duration of every operation, as buttons are - but unlike the others its enabled state is worked out from the sharing status rather than set in one place, and nothing re-asked for it once the operation finished. So on a share that had just been started - exactly when you want to check that the outside world can reach it - the button went grey and stayed that way until the program was restarted.
  • Share Manager: "Open Fast Media Sorter" in the tray menu works in the Server edition. That package installs the Share Manager on its own, and the menu item only ever looked for the viewer in its own folder - so on a server machine it did nothing at all, silently. It now finds a normally installed viewer wherever it is, and when there really is none the item is simply not shown.
  • The program survives being left open for days, and stops growing while it sits there. A code audit of everything that only goes wrong after hours or thousands of files found and fixed a set of problems you could never reproduce in a minute of use. The worst three: the thumbnail panel (F3) no longer builds a card for every file from the start of the folder up to wherever you are standing - open it at photo ten thousand of a fifteen-thousand-file folder and it opens at once, instead of decoding ten thousand images and running the program out of window handles until it had to be restarted; a folder that goes unreachable mid-session no longer crashes the program - when a network drive drops, the viewer used to skip through the remaining files until it ran out of stack and died instantly, taking with it every setting, recent-folder entry and reading position changed since launch; and the log file next to the program stops growing for ever - it used to gain a line for every single image you looked at, a megabyte or two a day, and nothing ever trimmed it.
  • Your settings are no longer lost if the program does not close normally. Destination folders for the number keys, the recent files and folders lists, the position in the folder and every option were written only when the window was closed cleanly - so a crash, a power cut or ending the task threw away everything changed since the last proper exit, even days of it. Editing a destination folder now saves it immediately, and everything else is written a minute after it changes.
  • Closing the program while files are still being moved no longer loses them silently. Sorting keys pressed during the "finishing file operations.." wait were accepted, reported as done and then discarded - the file stayed where it was while the program said it had been moved. Those keys are now refused with a clear message. If the transfers need longer than the fifteen seconds the program waits, it asks whether to keep waiting instead of closing regardless, and a move between two different disks or network shares is now staged through a temporary name, so an interrupted transfer can no longer leave a half-copied file under the real file's name.
  • The window stops freezing on a sleeping network drive. Reading a folder, opening a file passed from Explorer, waiting for a file that is still downloading, and checking whether an image can be translated all used to run on the same thread that draws the window, so a share that had gone to sleep froze everything for as long as Windows took to give up - up to four minutes on the 32-bit program when a second copy was launched with a network path. A picture that cannot be read within twenty seconds is now reported as unavailable instead of holding the program hostage, and the errors that used to appear as pop-up dialogs - one per file when a key was held down - now go to the status line.
  • Automatic translation no longer bogs the program down over a long session. Switching pictures while OCR was running left the abandoned recognitions running to the end anyway, queueing up behind each other; they now stop as soon as their picture is gone. Both translation caches are now kept within a size limit - including the megabyte limit the settings window offered, which until now was displayed and saved but enforced by nothing, so the cache kept growing regardless of what you set it to.
  • Share Manager: "Share this folder with phone.." now works when the manager window is already open. The folder was quietly discarded in that case - nothing was added, nothing was said - so the feature appeared to work at random depending on whether the window happened to be closed. The manager also no longer wedges permanently if its background component stops responding: every request to it now has a time limit, and it stops polling a component that is not there.
  • iPhone photos really do open now: HEIC, HEIF and AVIF were announced but did not work in the installed program. The library that decodes them was built, but it was left behind when the package was assembled - so the feature worked when the program was run from the developer's build folder and failed everywhere else. Nothing about the feature changed; it is simply in the package now. This affected the installer, the portable archive and the Store version alike, from the release that introduced the formats.
  • The program no longer ships a log file from the machine it was built on. Every package carried a current.log left over from testing, with the build machine's own folder paths inside it, and installed it next to the program - so your own log began with someone else's sessions. It is excluded from all four packages now.
