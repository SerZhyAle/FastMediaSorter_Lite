## Project Overview

**Fast Media Sorter & Sharing for Windows** (the name is set in [docs/guides/PRODUCT_NAMING.md](docs/guides/PRODUCT_NAMING.md); "Sharing" is giving media to a phone, another copy of the program or an SFTP client) is a Windows Forms application for viewing, sorting and sharing image and video files. It ships as **two exes side by side in one folder**, built from **one source tree**: the **.NET 10 x64 mainline** (`FastMediaSorter_LITE.exe` - LibVLC-only playback, ImageSharp 3 decoding) and a **net48 x86 fallback** (`FastMediaSorter_x86.exe`) for Windows 7/8.1 and 32-bit Windows, which keeps the legacy stack (IE WebBrowser for H.264/MP4 + LibVLC fallback for AVI, ZMBV, VP9, MKV, etc.). Read "Two builds, one source tree" below before touching anything build- or media-related.

### Naming rule (ticket 111, decided 2026-10-03)

## Two builds, one source tree - read before editing a seam

The viewer is **one app** shipped as **two exes in one folder**. Design: `SPECIFICATION_DOTNET10_MODERN_BUILD.md` (local specification); live implementation journal: [PROGRESS_DOTNET10_MODERN_BUILD.md](docs/guides/PROGRESS_DOTNET10_MODERN_BUILD.md).

| | **Mainline** | **Fallback** |
|---|---|---|
| Exe | `FastMediaSorter_LITE.exe` (frozen anchor) | `FastMediaSorter_x86.exe` (new name) |
| Project | [src/Modern/FastMediaSorter.Modern.vbproj](src/Modern/FastMediaSorter.Modern.vbproj) (SDK-style) | [src/FastMediaSorter.vbproj](src/FastMediaSorter.vbproj) (old-style) |
| Target | `net10.0-windows`, x64, self-contained single-file (runtime inside the exe) | net48, genuinely `PlatformTarget=x86` (32-bit process), ~3 MB |
| Built by | `dotnet publish` | `msbuild` |
| Runs on | Windows 10 1607+ / 11 / Server 2016+ | Windows 7/8.1 and 32-bit Windows |
| Video | **LibVLC only** | IE WebBrowser (H.264) + LibVLC fallback |
| Images | ImageSharp 3 | WIC + ImageSharp 2 fallback |
| Managed deps | NuGet `PackageReference`; publish lays them down | `packages.config`; every managed dep embedded as a `FmsPayloadmanaged/*.dll` resource, resolved by `RuntimeBootstrap` `AssemblyResolve` (ILMerge is imported but never runs) |

**Rules - do not "fix" these away:**
- **Clarify ambiguity first (owner decision, 2026-07-19):** When a request does not clearly identify the target screen, runtime, or expected outcome, ask a concise clarifying question before changing code. Do not infer the target from similarly named legacy/shared UI.
- **Maintenance policy (owner decision, 2026-07-19):** .NET 10 x64 is the active development target. Do not add features, UI refinements, or intentional behavior changes to the net48 x86 fallback; touch it only to fix an actual bug that is found. When a shared-source change is mainline-only, preserve net48 behavior with a `#If NETFRAMEWORK` seam.
- **Shared Windows UI (owner decision, 2026-10-05):** adopt `WINDOWS-UI` 0.1, `APP-SETTINGS` 0.2 section 8 and `APP-STYLE` 0.12 section 10 from the shared catalog. The modern viewer/settings are the reference for navigation, independent groups/context, side-by-side editors, conventional left checkboxes, readable native numeric controls, complete live theme coverage, DPI and floating viewer chrome. Secondary windows follow the same control conventions. `ICON-RENDER` 0.16 section 11 permits navigation identity inks. See [APP-UX pointer](docs/contracts/APP-UX.md); normative rules stay in the catalog. Portfolio owner opt-in is recorded; other products require their own implementation and conformance audit; net48 maintenance policy remains unchanged.
- **One app, not two**: one folder, one mutex `FastMediaSorterSingleInstanceMutex`, one registry hive `SZA\FastMediaSorter`. Launching either exe while the other runs forwards the file to the running window - so [Application_Events.vb](src/Application_Events.vb) searches **both** process names (`Viewer_Process_Names`): `GetProcessesByName` matches on name only, and searching just our own name would find nothing when the sibling is the one running, cancelling the launch **silently** with no window and no file opened.
- **Both projects compile the SAME sources**, but a NEW file has to be added to the net48 list BY HAND: the modern vbproj links `..\**\*.vb` (picked up automatically), while the old-style [src/FastMediaSorter.vbproj](src/FastMediaSorter.vbproj) carries an explicit `<Compile Include="..">` list. Drop a `.vb` under `src/` and only the mainline sees it - the x86 build then fails on the first thing that references it (`BC30451: '..' is not declared`), which is the *good* case; a file nothing references yet just silently is not in that exe. Add the `<Compile Include>` entry (with `<DependentUpon>Main_Form.vb</DependentUpon>` for a `Main_Form.*.vb` partial) in the same commit. Divergences live behind `#If NETFRAMEWORK` seams, never in per-project file lists.
- **`NETFRAMEWORK` is defined BY HAND**: old-style projects do **not** define it, so [src/FastMediaSorter.vbproj](src/FastMediaSorter.vbproj) sets `<DefineConstants>NETFRAMEWORK=True</DefineConstants>` in **both** configurations. Delete or typo it and every seam silently compiles the wrong branch - no error, just a modern-only code path inside the net48 exe.
- **Never delete a seam to "simplify"** - each exists because the two runtimes genuinely differ. **Do not look for the list of seams here** - it was hand-maintained, fell four-fifths behind the tree, and the tree answers in one line: `grep -rlE '#If (Not )?NETFRAMEWORK' src/ --include=*.vb`. Whole-file seams (the file is one runtime's only) are worth knowing by shape rather than by name: [src/Imaging/](src/Imaging) decoders and encoders, `Ocr/OcrPlateColors.vb` + `Ocr/OcrDiagnostics.vb`, `Main_Form.Zoom.vb` + `ZoomMath.vb`, `Main_Form.PerspectiveHalo.vb`, both `*.ShareLauncher.vb`, `Table_Form.SendLogs.vb` + `Support/LogPackage.vb`.
- **Shared adjacent libraries, resolved per process bitness** out of the same tree: `libvlc\win-x64` vs `libvlc\win-x86`, `x64\tesseract50.dll` vs `x86\` (`CurrentArchFolder()`/`CurrentVlcArchFolder()` in [OptionalRuntimeManager.vb](src/OptionalRuntimeManager.vb)). This needed no code change - don't "unify" it.
- **The x86 build keeps OCR and translation; only Share is cut** (owner decision, 2026-07-16). Share is gone because it *cannot* work there: the Companion it wakes is `net10.0-windows` **x64**, so it does not start on Windows 7/8.1 or 32-bit Windows - exactly the machines the x86 exe exists for. `Main_Form.ShareLauncher.vb` and `Table_Form.ShareLauncher.vb` are whole-file `#If Not NETFRAMEWORK`, and the installer's `share` component carries `MinVersion: 10.0.14393` so it is not offered where it could not run. **There is no `FEATURE_FULL` constant and no stripped build configuration** (the mechanism epic O-7 asked about): there is exactly ONE net48 build and it IS the x86 fallback, so `NETFRAMEWORK` already names the thing precisely - a second constant would only add a way for the two to disagree. Note the epic's §1.1 still describes a leaner legacy (no OCR/translate, "tens of MB instead of hundreds"); that was written before the two-exe directive, and in one shared folder the OCR/codec/companion trees are installed for the x64 mainline anyway, so cutting them from x86 would have saved the exe alone.

**Modern-only compatibility pins** (each deliberate; removing one is a visible regression):
- `ApplyApplicationDefaults` in [Application_Events.vb](src/Application_Events.vb) now selects `HighDpiMode.PerMonitorV2` + `Microsoft Sans Serif` 8.25 for the modern viewer. The **shipped net48 exe never embedded `app.manifest`**, so DPI-unaware IS the reference behavior; .NET would otherwise default to `SystemAware` + Segoe UI 9pt and shift the pixel-tuned Designer layout. The modern floating chrome measures from `DeviceDpi` and reanchors on DPI changes; the x86 viewer retains the reference behavior.
- The modern vbproj sets `System.Globalization.UseNls=true` so `abc`/`xyz` file sorting matches net48 (.NET 5+ uses ICU, net48 uses NLS).
- Tesseract's loader needs `InteropDotNet.LibraryLoader.Instance.CustomSearchPath` under single-file publish (`Assembly.Location` is `""` there).
- A portable JSON facade in `TranslateHttp` ([src/Translate/OllamaTranslator.vb](src/Translate/OllamaTranslator.vb)) keeps `JavaScriptSerializer` on net48 and uses `System.Text.Json` on modern, shaped to the same untyped graph so the **OCR disk cache stays compatible** across both exes.

### Version Auto-Generation
Both viewers stamp the same `YY.M.D.HHmm` version (e.g., `26.6.2.0124`) at build time: the net48 project via its `UpdateVersion` target (rewrites `My Project\VersionInfo.vb` before compilation), the modern project via its `AutoVersion` property. Both accept a release override (`-p:ReleaseVersion=..`); keep the two exes' stamps identical. `build.ps1` does so by picking ONE stamp up front and passing it to msbuild and to both `dotnet publish` runs; every packager and `release.yml` pass it to the Companion publish too, whose project carries the same `AutoVersion`/`ReleaseVersion` block (ticket 055 I-08), so all three programs of one package report one version. That claim is **checked on the artifact, not the source** ([tools/Test-ArtifactVersion.ps1](tools/Test-ArtifactVersion.ps1), contract `BUILD-EVIDENCE` rule 2): `build.ps1` reads the version resource of every exe it just built and deploys nothing unless all carry its stamp, and the release preflight does the same for the staged package and both setup.exe files against the tag. The comparison is numeric - the resource holds `26.7.30.0108` as `26.7.30.108`.

### Release Pipeline (CI)
Releases are cut by **pushing a `vYY.M.D.HHmm` tag** (or running the `Release` workflow manually with a tag input). Either way the workflow first validates the tag against that pattern (the dispatch input goes through `env`, never spliced into a script) and checks out **the tag itself**, then proves `HEAD` is the tagged commit - a manual re-run used to build `main` and publish it under the old tag. [.github/workflows/release.yml](.github/workflows/release.yml) runs on `windows-latest` and:
1. Restores NuGet, `msbuild .. /t:Rebuild` in Release (which yields only the **x86** viewer), **then `dotnet publish` the modern project** (`-o modern-publish`, `-p:ReleaseVersion=` so both exes carry the tag's version) and the Companion. Since msbuild alone never produces the mainline exe, **every packager runs its own publish** ([tools/Build-Installer.ps1](tools/Build-Installer.ps1), [tools/Build-OfflineRelease.ps1](tools/Build-OfflineRelease.ps1), [.github/workflows/release.yml](.github/workflows/release.yml), [publishing/msix/build-msix.ps1](publishing/msix/build-msix.ps1)).
2. Stages everything in `bin/Release` **except `.pdb`/`.xml`** (plus `README.md`, `LICENSE`) into `stage/FastMediaSorter-<version>-windows-x64/`, then drops the published `FastMediaSorter_LITE.exe` in next to its x86 sibling - **two exes, one set of support trees**, since one package serves modern and legacy Windows.
3. Runs [tools/Prepare-OcrOfflinePayload.ps1](tools/Prepare-OcrOfflinePayload.ps1), which downloads all OCR `tessdata_fast` languages shown in the UI plus their `tessdata_best` counterparts into `tessdata/` and `tessdata-best/` - from **pinned upstream commits**, every file checked against the committed [tools/tessdata.sha256](tools/tessdata.sha256) (a mismatch stops the run naming the file; moving to a newer commit means updating the script's SHAs and that manifest together). Downloads are cached in `tools/ocr-cache/`, which is also what CI caches. It **trims the 32-bit native trees by default** (~100 MB; the x86 viewer downloads them on demand via `OptionalRuntimeManager`) - pass `-KeepX86` to keep the x86 fallback fully offline.
4. Packages two **offline-ready** assets from that staged tree: a **portable ZIP** and an **Inno Setup installer EXE** (compiled via [publishing/installer/FastMediaSorter.iss](publishing/installer/FastMediaSorter.iss); Inno Setup installed on the runner with `choco install innosetup`). Each gets a `.sha256` sidecar. The installer ships **both** exes and points the Start-menu/desktop shortcut, the post-install launch and the file associations at whichever exe **runs on that OS** (`UseModernExe`: Windows 10 build >= 14393 gets the mainline, older gets `FastMediaSorter_x86.exe`); `MinVersion=6.1` still lets Setup run on Windows 7.
5. Builds the Server edition's `..-server-setup.exe` from its own lean stage, then publishes a GitHub Release with six files attached: the ZIP, both setups and a `.sha256` for each.

For a local release-style build, run:
```powershell
.\tools\Build-OfflineRelease.ps1
```
This mirrors the CI packaging flow and emits offline-ready artifacts in `dist/`. It is also the free pre-flight `tools/Release.ps1` runs before the tag push, so it **fails without Inno Setup** instead of building a ZIP and skipping both installers. The local scripts restore with a **pinned** `nuget.exe` ([tools/Get-PinnedNuGet.ps1](tools/Get-PinnedNuGet.ps1): versioned URL + SHA-256; a copy that does not match is refused, never run).

### Standalone copy-anywhere installer ("сборка", not a release)
[tools/Build-Installer.ps1](tools/Build-Installer.ps1) - also the last step of `build.ps1`, which calls it with `-SkipBuild` - produces **only** the offline `setup.exe` in `dist/` - a package you can copy to any Windows machine and run (per-user, no admin, no internet at install time). It reuses the frozen `publishing/installer/FastMediaSorter.iss` and `Prepare-OcrOfflinePayload.ps1`, runs its own `dotnet publish` of the modern project (so the setup carries both viewer exes), explicitly bundles the Android-share worker into `companion/`, and **never creates or pushes a `v*` tag** - it is a local convenience, not `tools/Release.ps1`. Unlike `Build-OfflineRelease.ps1` it skips the portable ZIP and, by default, the heavy `tessdata_best` models (fast OCR models only → ~lean installer; best models download on demand). Flags: `-IncludeBest` (fully offline incl. best OCR), `-SkipOcr` (smallest; OCR downloads on demand), `-SkipBuild` (repackage the current `bin/Release`), `-Open` (reveal in Explorer). Needs Inno Setup 6 (`winget install JRSoftware.InnoSetup`); it fails fast with that hint if missing.

The version in the tag is authoritative for asset names but is independent of the build-time `UpdateVersion` stamp - keep them consistent. See `SPECIFICATION_GITHUB_STORE.md` (local specification) for the rationale behind shipping an EXE installer (GitHub-Store discoverability; a ZIP-only release is invisible to that marketplace).

### Publishing to winget - read before touching the manifest
**The winget manifest must point at the Inno `setup.exe` directly (`InstallerType: inno`) with NO declared dependencies.** This was learned the hard way (see `SPECIFICATION_WINGET_PUBLISHING.md` (local specification)). Quick rules:
- **Never** point winget at `single-exe.zip` - Defender ML flags the self-extracting bootstrap as `Program:Script/Wacapew.A!ml` (persistent false positive). It's a GitHub-only convenience download.
- **Don't** use the portable `windows-x64.zip` shape - the ~99 MB payload aborts the install with `0x80004004` after extraction.
- **Don't** declare the `Microsoft.VCRedist.2015+.x64` dependency - it sends winget into a resolution loop and aborts with `0x8A150044`; the app installs fine without it (validation never launches the app).
- **Don't** add `Scope: user` - it forces the harness into a non-elevated `--scope user` flow and the install fails with `0x8A150044` ("no suitable installer found for --scope user"). Omit `Scope` so validation runs elevated/machine.
- The "Missing `NestedInstallerType` / fewer `Tags`" inconsistency note is a non-blocking `Validation-Guide`, not a failure.
- Get the *real* failure reason from the build's `InstallationVerificationLogs` artifact, not the generic GitHub bot comments - the doc has a copy-paste snippet.
- **Before the winget PR** (and, with `-Wack` in an elevated console, before the Partner Center upload) run [tools/Store-Prepublish-Checks.ps1](tools/Store-Prepublish-Checks.ps1) `-Expect <version>`: `winget validate` of both editions, `InstallerSha256` against the published release's `.sha256` sidecars (never against `dist\`), and the six manifests' consistency and frozen anchors - ticket `024` (local specification). It needs the release to exist, so it is a hand-run check, not part of the pre-tag preflight.

### Publishing to the Microsoft Store (MSIX) - see [STORE_PUBLISHING.md](docs/guides/STORE_PUBLISHING.md)
The Store path (Path A: MSIX) is **additive** - it does not change the GitHub release or winget flows. Full playbook + filled listing copy (description, features, runFullTrust justification, privacy text) is in [STORE_PUBLISHING.md](docs/guides/STORE_PUBLISHING.md); packaging detail in [publishing/msix/README.md](publishing/msix/README.md). Key facts:
- **No app code change is needed** - the app is already MSIX-safe: everything mutable goes to `%LOCALAPPDATA%\SZA\FastMediaSorter` (OCR downloads/cache via `OcrPaths`) or the registry, both writable inside the package container; bundled `tessdata` next to the exe is only ever read (the install dir is read-only under MSIX).
- **MSIX is x64 only and packages the mainline exe only** - the x86 fallback is never packaged (the Store target floor is well above Windows 7).
- Build with [publishing/msix/build-msix.ps1](publishing/msix/build-msix.ps1): MSBuild Release + `dotnet publish` the modern project → stage the **offline payload** (same `bin/Release` tree minus `*.pdb`/`*.xml` and minus everything that exists only for the x86 exe - the exe and its `.exe.config`, the loose net48 managed assemblies, the `x86\`/`libvlc\win-x86\`/`runtimes\win-x86\` trees - run through [tools/Prepare-OcrOfflinePayload.ps1](tools/Prepare-OcrOfflinePayload.ps1)); pass `-ReleaseVersion <tag without v>` for a Store upload, or the package is stamped with the current minute → generate logos from [assets/icons/store-icon-256.png](assets/icons/store-icon-256.png) → fill manifest → `makeappx pack`. `-SelfSign` makes a sideload-testable build; **no `-SelfSign` for the Store** (Microsoft re-signs on certification - no paid cert needed).
- [publishing/msix/AppxManifest.xml](publishing/msix/AppxManifest.xml) wraps the exe as a **full-trust** desktop app (`rescap:runFullTrust` keeps LibVLC/GDI+/file-access/local-HTTP working) and declares image **file associations** (the manifest equivalent of the Inno per-user registry writes). Identity (`Name`/`Publisher`/`PublisherDisplayName`) is `__PLACEHOLDER__` filled at pack time from Partner Center (Product ▸ Product identity) via `-IdentityName`/`-Publisher`/`-PublisherDisplayName` - must match **exactly** or upload is rejected.
- **Version remap (Store requires revision = 0):** the script maps the exe's `YY.M.D.HHmm` stamp to `YY.(M*100+D).HHmm.0` (each part ≤ 65535). Don't hand-edit it.
- Needs the Windows SDK for `makeappx.exe`/`signtool.exe` (`winget install Microsoft.WindowsSDK`); they live under `C:\Program Files (x86)\Windows Kits\10\bin\*\x64\`.

It takes the finished bars from `Draw_Perspective` and fades them towards `Me.BackColor` the further they get from the photo - a **permanent** property of the frame, not just an intro. Its own sub-option `Is_Animated_Perspective` (registry `AnimatedPerspective`, **on** by default - its parent is already off until switched on by hand) decides whether a new photo *grows* that halo out from the photo edge or just has it there. How long that growth takes is a third setting, `Halo_Animation_Speed` (registry `AnimatedPerspectiveSpeed` = `slow`/`medium`/`fast`, **default `medium`**): `HaloDurationMs()` returns the historical 350 ms for `slow`, half that for `medium` and a quarter for `fast`, and the value is snapshotted into `halo_Running_Duration_Ms` when a growth starts, so changing the speed lands on the next photo instead of jolting a running animation. The 15 ms frame cap is unchanged - a faster setting draws fewer frames, it does not draw them harder. One code path does both: at progress `p` the ramp spans `p * barWidth` out from the photo and plain background lies beyond it, so `p = 1` **is** the resting halo (drawing instantly = entering at `p = 1`) and the growing front never steps against the background. On top of every frame goes `halo_Underlay` - the frame that was on screen when the growth started, taken over from the picture box rather than disposed - at alpha `1 - eased`, so a new photo dissolves out of the old frame instead of the bar blinking to flat background first. **It fades with TIME, never with distance**: at `eased = 1` it draws nothing, which is what keeps the resting frame pixel-identical to what it was before the underlay existed (verified by comparison, not by eye). Fading it by distance was tried and is wrong twice - the bar ends the growth showing the old frame, and painting a picture through a gradient means constant-alpha bands, visible as stripes and corner blocks. Frames cannot be accumulated (a grown ramp gives a pixel *less* background than the frame before), so each is recomposed from the kept bars bitmap. `Draw_Perspective(animate)` only reports *a new photo asked* ([.MediaLoading.vb](src/Main_Form.MediaLoading.vb), and the first image via `Main_Form_Shown`; resize/zoom never does) - whether that grows is the halo layer's call; `perspective_Animate_Pending` carries that intent across the throttle's trailing timer.

**Display resilience** (these never let a transient failure drop the image):
- `UpdateControlVisibility()`'s dynamic-background colour analysis and `Draw_Perspective()` both run their GDI+ pixel work inside a `Try/Catch`. GDI+ can transiently throw (`OverflowException`, `"Parameter is not valid"`) - e.g. while the background worker decodes on a slow network share - and the image is already on the PictureBox, so the analysis failure is swallowed and the frame keeps the previous tint/bars instead of aborting the load.
- `Draw_Perspective()` debounces with a trailing-edge timer: a redraw skipped by the `how_long_wait_before_draw_perspective` throttle is retried once scrolling stops, so the image you settle on always gets its bars.
- The background worker reads image dimensions via `Utils.GetImageDimensions()` (header parse, no GDI+) instead of `Image.FromFile`, so it never decodes the current image concurrently with the UI thread's `GetPixel`.
- **First media gets its bars too**: the first image at startup (a command-line file/the restored last folder) loads inside `Form1_Load` while `is_form_shown` is still `False`, so every `Draw_Perspective()` in that path is gated off. `Main_Form_Shown` redraws once (the form is now at its final size and `is_form_shown = True`); `Draw_Perspective` self-gates if no picture box is visible or perspective is off.
- **Seam fix**: `GetDisplayedVerticalEdgeColors`/`GetDisplayedHorizontalEdgeColors` sample one pixel **in** from the very edge (`edgeInset`). The outermost downscaled row/column folds in the darkest border/vignette pixels and comes out a few levels darker than what the `Zoom` PictureBox actually paints, leaving a faint dark seam between photo and bar; the second row/column matches the displayed edge, so the bar joins seamlessly.

**[Application_Events.vb](src/Application_Events.vb)** - `My.MyApplication` startup hooks for single-instance behavior (plus the modern-only `ApplyApplicationDefaults` DPI/font pin - see "Two builds, one source tree")
- On `Startup`: a path-independent named mutex (`FastMediaSorterSingleInstanceMutex`) detects an already-running instance (VB's built-in `IsSingleInstance` only matches same exe path, so debug/release/renamed copies would each start their own). If found, the new process forwards its command-line file path to the running window via `WM_COPYDATA` and cancels (`e.Cancel = True`). **The running instance may be either exe**, so the search runs over **both** names in `Viewer_Process_Names` - see the two-exe rules above. An instance whose window is hidden or minimized can have `Process.MainWindowHandle` zero - the sender falls back to `EnumWindows` over the process's top-level windows. The hand-off rules live in [SingleInstanceProtocol.vb](src/SingleInstanceProtocol.vb) (audit 053): the forward carries a `dwData` tag, `Main_Form.WndProc` acts only on a tagged message, answers it with 1 and opens the file after returning, and the sender counts a delivery **only on that answer** - a WinForms process's helper windows (GDI+, broadcast) answer 0 and must never pass for a delivery. The sender retries for up to 6 s while a viewer process exists (a still-starting first instance). A mutex owned by an elevated viewer throws `UnauthorizedAccessException` for an ordinary launch - that means "another instance exists", forward to it; and an elevated process runs with `IsSingleInstance = False`, because the framework's `CurrentUserOnly` pipe cannot connect across integrity levels. (The same reverse pattern is what `Main_Form.ShareLauncher.vb` uses to wake the tray-resident Companion.)
- On `StartupNextInstance`: the running instance receives the new args, calls `Main_Form.ProcessArgument()`, and deliberately avoids stealing focus (restores the previously-foreground window).
- **Bare relaunch** (no file argument) = the user re-ran the exe just to get the window back; both paths restore it instead of doing nothing: `StartupNextInstance` calls `Main_Form.RestoreMainWindow()` directly, the mutex path forwards `Main_Form.Show_Window_Command` (`::fms-show-window::`) which `External_message` intercepts. The window reappears (it was only minimized/behind, never torn down) and - unlike a file open - DOES take focus (a bare launch has no other purpose). `RestoreMainWindow()` (in `Main_Form.Lifecycle.vb`) is now just "unminimize + activate + BringToFront" - **the viewer no longer has any tray-resident/close-to-tray mode** (that moved to the Share Manager with the share feature), so closing the viewer closes it like a normal viewer.
- `WM_COPYDATA` payload is **UTF-8** on both send and receive (the receiver in `Main_Form.vb` decodes the bytes as UTF-8, not `PtrToStringAnsi`, so non-ASCII filenames survive).
- `ProcessArgument()` doesn't trust a single `File.Exists` for a `\\server` path: it probes with `File.GetAttributes` to tell a genuinely-missing file (fail fast) from a network hiccup (retry for the SMB session to recover) from an access-denied **lock** (the file is still being written/downloaded). A locked file is watched on a timer and **opens automatically once it unlocks**, instead of being silently dropped.

**[src/Secure/](src/Secure)** - `.fd-sec` secure containers, modern-only (whole-file `#If Not NETFRAMEWORK`), reader half only - `026_SPECIFICATION_SECURE_CONTAINER_FD_SEC_DOTNET10.md` (local specification), against contracts `FDSEC-FORMAT` and `FDSEC-BEHAVIOUR`. A container is one ordinary file holding another file's bytes, its true name and its timestamps behind a credential, and carrying **no marker at all** - so nothing but the credential can tell it from noise, and **there is no dispatch by looking**: the only screen that exists before the password is the length rule (`FdSecScreen`), and a file that passes it still says nothing. Read this before touching any of it:
- **The boundary is one sentence: no decrypted byte ever reaches the disk.** Not a temporary folder, not the decode cache, not the OCR cache, not a log. That is the opposite of the archive answer above, deliberately (owner decision 3): an archive entry is not a secret. `FdSecStream` is what makes it cheap - the payload is independently sealed chunks at fixed offsets, so `Seek` is arithmetic and a video plays through `LibVLCSharp`'s `StreamMediaInput` with the decrypting stream AS the media input. Everything in `Main_Form.Secure.vb`'s refusals follows from it: the editor and "replace with video" are hidden, the external-player fallback and the browser-translate hand-off are refused (both pass a **path** to another program), and the decode and OCR **disk** caches are bypassed in both directions.
- **The three outcome classes never merge** (`FdSecOutcome`, and `SecureMessages.ForOutcome` maps them). *Wrong credential / not a container / tampering* is ONE class carrying three readings, because a wrong key and a flipped byte fail an AEAD tag identically - that is a security property, not a gap. *Damaged* never blames the password; *unsupported* is refused by name and never called damage. `FdSecRuleTests` walks the enum and fails if two classes ever share a sentence.
- **Conformance is decided by the catalog's vectors, never by reading the code.** They are vendored as artifacts into `tests/Lite.Tests/TestData/fdsec-vectors/` beside a `PROVENANCE.txt` whose SHA-256s the suite asserts first. A one-byte deviation anywhere produces a reader that is perfectly self-consistent and opens nothing anyone else made - and the seven porting mistakes of `FDSEC-BEHAVIOUR` §13.1 each have a test rather than a reading. **The KDF profile is not ours to tune**: it belongs to the format version, and the lowered one is a test-only parameter no shipped path passes.
- **`src/Secure/` has no product dependencies** - it never logs, never shows a dialog, never reads a setting. The viewer's side is [Main_Form.Secure.vb](src/Main_Form.Secure.vb) plus [Secure_Password_Form.vb](src/Secure_Password_Form.vb), and the credential lives in memory for the process only: never the registry, never a file, never the DPAPI store the OCR keys use.
- **The writer is deferred to its own ticket** (owner decision 4), because `FDSEC-BEHAVIOUR` §6 - the read-back proof, the temporary file, the disposition of the original - is what decides whether the feature destroys data. Do not fold a packer in beside the display path.
- The streaming reader is a **recorded deviation**: it authenticates every byte it returns but cannot verify the sealed digest of a chunk it never read, so the viewer never claims a container is intact and offers an explicit "verify this container" instead. Filed as an amendment to propose, not taken locally - see [docs/contracts/FDSEC.md](docs/contracts/FDSEC.md).

### OCR + On-Image Translation
See `SPECIFICATION_OCR_TRANSLATION_OVERLAY.md` (local specification) for the full design. Summary:
- **Hotkeys**: `T` runs OCR + translate (or toggles the overlay) when the feature is enabled; `Shift+T` toggles auto-OCR mode. When the feature is off, `T`/`Shift+R` keep their legacy rotate meaning. The **Перевод / Translate** toolbar button triggers the same pipeline.
- **Pipeline** ([Main_Form.OcrTranslate.vb](src/Main_Form.OcrTranslate.vb), `RunOcrPipeline`): OCR the image → `OcrLineSplitter` cuts any line the engine read straight across two columns or two balloons and puts the pieces back in reading order → `OcrBlockBuilder` groups lines into blocks (and drops isolated tiny blocks that are texture noise) → `OcrLanguageGuard` refuses the whole run when the source language was only ASSUMED (`auto`) and the discard record says the page could not be read - no overlay, and a status naming the fix (`OCR-OVERLAY` rule 10) → translate all blocks in one batch → render the translated text as an overlay over each block ([Main_Form.OcrOverlay.vb](src/Main_Form.OcrOverlay.vb)). Overlay text is sized to the **original** text: `OcrOverlayFit.FontCandidates` starts from the median height of the source block's **words** (`OcrOverlayFit.MedianLineHeight`, line boxes only as a fallback - a line box is stretched by whatever fell inside it) and walks a geometric ladder: shrink to the floor, grow the plate downwards within a budget that stops at the next plate in the column, then **release** the plate past that budget to whatever height the text needs, bounded by the bottom of the picture (`OCR-OVERLAY` rule 9). There is no ellipsis and no crop at any rung, the top edge never moves, and where a released plate overlaps the one below, plates are painted in reading order so the lower one wins (the overflow rule at the top of `Main_Form.OcrOverlay.vb`). The plate is **opaque by default** (`OverlayOpacity` 255, rule 7; a lower value is the user's own slider choice, and a stored 210 from an older build is kept) and has **no padding** - both recorded decisions of ticket 033 Ф-4. The paragraph direction follows the drawn text, so an Arabic or Hebrew plate is laid out right to left whatever the UI language. Results are cached in memory and (optionally) on disk by `TranslationCache` under `OcrResultPolicy.BuildCacheKey`: file path + write-time + the **displayed pixel grid** (size, on-screen quarter turns since the picture was shown, `Is_Exif_AutoRotate`) + engine + provider + languages - where the **engine** key folds in OCR model quality, page mode and `OcrPipelineVersion`, and the **provider** key folds in the Ollama model. `R` cancels a running job and moves the key; a document whose size is not the picture's is neither applied nor painted. **Only a complete translation is cached** (`OcrResultPolicy.IsCacheable`): a translator that was unreachable, timed out, refused the language or handed segments back untranslated produces a document shown with a status that ends in "T will retry", marked `IsPartial`, and `T` then re-runs instead of toggling. An expired HTTP timeout is a failed batch, never an `OperationCanceledException` - only the job's own token ends a run silently. **Empty (`No text found`) results are never cached** either; opening the settings dialog also clears the cache.
- **OCR engine**: multi-pass Tesseract (`TesseractOcrEngine`), loading images via `Pix.LoadFromMemory`. Instead of one `PageSegMode.Auto` pass it runs several scored attempts - single-language passes (in `OcrAttemptCodes` order, e.g. `rus → ukr → eng` for `auto`) across page-segmentation modes and light preprocessing (grayscale / inverted), upscaling small images - and keeps the highest-scoring result. The picture is resampled ONCE per recognition (`OcrImageScale.ComputeScale`) and each preprocess buffer is built only when an attempt asks for it (most pages are won by the first). `fast` (`tessdata`) or `best` (`tessdata_best`) packs download on demand; a missing pack is reported by name, with the way to download it, in both builds. The **OCR mode** setting can force a specific `PageSegMode` (auto/block/sparse/line/vertical). At shutdown the engine is disposed only if no pass holds it (`RetireEngine`) - closing never waits for a recognition in flight.
- **Translators** (`CreateTranslator()` picks by `ocr_Settings.Provider`): `OllamaTranslator` (default - local LLM at `localhost:11434`, batches blocks, repairs a bad segment with one retry) and `LibreTranslateTranslator` (its own language codes - `zt`, `nb` - and an up-front refusal for a target it has no model for). What counts as a bad segment is `TranslationQuality`: a refusal is judged by SHAPE - the model talks about the request in words the source never used - never by everyday words like "пожалуйста" or "sorry", and an echo is accepted when the source is already in the target language or is one Latin word (a name). Both parse JSON arrays through `TranslateHttp.JsonItemToString`, which pulls the real string out of a wrapped object (`{"translation":".."}`) - a raw `Convert.ToString` on such a `Dictionary` would otherwise leak ``System.Collections.Generic.Dictionary`2[..]`` into the overlay.

### Android Folder Share (Companion app + Go worker)
Two tiers now: a **standalone .NET 10 Companion app** (`src/FastMediaSorterCompanion/`, "Share Manager - Fast Media Sorter & Sharing") drives a **bundled headless Go worker** (`companion\fms-share-worker.exe`). The viewer is only a launcher (`ShareLauncher`, above). See `SPECIFICATION_SHARE_COMPANION_APP.md` (local specification) for the viewer→Companion split, `SPECIFICATION_SHARE_STATS_AND_TRAY_HUB.md` (local specification) for the connection-stats + tray-hub layer, `SPECIFICATION_ANDROID_FOLDER_SHARE.md` (local specification) for the worker IPC protocol / `.fmscfg` schema, and `SPECIFICATION_QR_IMPORT_ANDROID.md` (local specification) for the frozen wire contract (Android side). Summary:
- **Architecture in one sentence**: neither the viewer nor Companion implements SFTP - the **Companion app** drives the headless sidecar `companion\fms-share-worker.exe` (prebuilt Go binary vendored at `payload/companion/` and **committed** to this repo via a narrow `.gitignore` negation - `!payload/companion/fms-share-worker.exe` + its `.sha256`, so a fresh clone **has** the Share feature; built from a separate `fms_companion` repo at `P:\windows\fms_companion` - **never build or hand-edit it from this repo**) over a named-pipe JSON control channel (`\\.\pipe\fms-companion`, schema-versioned request/response, one round-trip per connection; contract `WORKER-IPC`). The host **reads `ok`** on every answer, a **version refusal is shown, never swallowed** (`WorkerVersionRefusedException`, turned into a typed result by `WorkerProcess.Exchange` - the one exchange point), and **nothing is spawned after any answer**: a worker that answered owns the pipe. The worker owns the SFTP server, credentials, ed25519 host key, folder confinement, mDNS announce, UPnP/NAT-PMP port mapping, and the local-only connection stats (`stats.json`, `GetStatus.status.stats` / `ResetStats`). `WorkerProcess.IsAvailable()` returns `False` when the payload is missing and the UI degrades gracefully ("unavailable") - the normal state on a dev machine that hasn't fetched the payload.
- **Never regenerate or touch the worker's data dir** (`%LOCALAPPDATA%\FastMediaSorterCompanion\`) from VB - the host key is TOFU-pinned by paired phones; deleting it breaks every paired device.
- The `.fmscfg` export JSON and its QR PNG are built **on the viewer side** by `ShareConfigBuilder`, not via the worker's own `ExportConfig` - only that lets the viewer advertise a manually-forwarded router port or schema-v2 per-root params (destination/writable folders, media-type filters, PIN, slideshow interval - see `ShareRootParams`).

- **Distribution**: both the Companion exe (`<app dir>\FastMediaSorterCompanion.exe`) **and** the worker (`<app dir>\companion\fms-share-worker.exe`) ship as siblings of the viewer exe in every channel - portable ZIP, Inno installer ([FastMediaSorter.iss](publishing/installer/FastMediaSorter.iss) `[Files]`: the Companion exe is a selectable `share` component; [publishing/installer/stop-companion.ps1](publishing/installer/stop-companion.ps1) kills a running worker/Companion before Setup/Uninstall replaces files - that `PrepareToInstall` script is the ONLY mechanism for it, so **never add `AppMutex=FastMediaSorterCompanionSingleInstanceMutex`** to either `.iss`: Inno checks a mutex at startup, BEFORE `PrepareToInstall`, and the Share Manager sits in the tray from logon, so a silent install (`/SUPPRESSMSGBOXES`, i.e. winget) has the "close it" prompt answered Cancel and aborts with exit code 1 before a single file is touched - which is what broke every `winget upgrade` of the Server edition up to 26.9.20), and Store MSIX (a second `<Application>` + `uap5:StartupTask` retargeted to Companion + `desktop2:windows.firewallRules`, since an HKCU Run write inside an MSIX container is silently virtualized away). `build.ps1` publishes Companion via `dotnet publish -c Release -r win-x64` (skip with `-SkipCompanion`) and deploys both siblings next to the viewer exe. **The Media Exchange Server (`exchange\`, ticket 141) is a third, optional tree** - exactly five files, staged by [tools/Stage-ExchangePayload.ps1](tools/Stage-ExchangePayload.ps1) (the only place that names them): `exchange\fms-exchange-server.exe` + `.sha256` (built from `exchange-server/`, never vendored), `enable-exchange-server.ps1`, `install-exchange-service.ps1` and `README.txt`. Gate shut: no `exchange\` folder in any stage (a stage that has one fails the build) and ISCC is called with `/DNoExchange`, which compiles the component, its `[Files]`, messages, task and uninstall code out of both `.iss` files (`#ifndef NoExchange`); a hand compile of an `.iss` without that define expects the tree to exist. Gate open: the build throws when the binary or its sidecar is missing - a package claiming a component it lacks is worse than a failed build. `stop-companion.ps1` also stops `fms-exchange-server.exe`, but only a copy that runs from `<app dir>\exchange\` and never a Windows service instance. No Windows service anywhere else (blocked by Store policy).
- **The listen port is GUARANTEED, and it is a setting, not a mode** (`015_SPECIFICATION_SHARE_MANUAL_PORT.md` (local specification), still `schemaVersion` 1). The number is printed in every QR/`.fmscfg` and typed into router forwarding rules, so it moves when the owner moves it and at no other time. Owner decision (2026-09-01), after a "Fixed port" **checkbox** was built and rejected: a toggle implies the port otherwise drifts by design, and offers a second state nobody wants for a number that lives inside a printed code. So there is **no auto mode and no fallback anywhere** - `settings.json` carries `port` and no `portFixed`, and HKCU `Share_ListenPort` (0 = "not recorded here", never "let it float") rides the **existing** `SetNetworkPolicy` request as a nullable `port` where 0 and absent both mean *unchanged*. Rules: the OS chooses **exactly once**, on the first ever start, and that choice is persisted immediately and is then the port; a bind is **retried ~2 s** (`portRetryAttempts`), because what used to move the port was our own previous listener during a restart, not another program; a port that still cannot be bound leaves the server **down** with `Status.LastStartError` (additive, cleared by a successful start) - the boot-restore path has no requester to answer, so without it a refusal reads as a plain "not running". `Status.DesiredPort` reports the number **while down**, which is exactly when the UI has to show it. `ShareController.PortWarning` turns all of that - plus `Status.PortSupported=False`, which identifies a **stale worker** rather than guessing - into the one line the main window's state row and the settings note show. **Never `SO_REUSEADDR`** to help a bind, nor in `FreePortFinder`'s probe: on Windows it lets an unrelated process steal a live one. The firewall rule is program-scoped, so a port change needs no elevation and must never acquire a reason to.
- **Opt-in server features + firewall** ([ServerFeatures.vb](src/FastMediaSorterCompanion/Core/ServerFeatures.vb), `SPECIFICATION_SHARE_SERVER_OPTIN_INSTALL.md` (local specification)): the bundled worker is dormant until the user opts in, because nothing ever opened the Windows Firewall port (the worker's own `AddFirewallRule()` is dead code from the discontinued standalone GUI, never on the `cmd/worker` path) - so an exported public address timed out from outside. Enabling adds a program-scoped inbound firewall allow for the worker exe, either via the installer checkbox (elevated install; hive-safe machine marker file) or the deferred in-app opt-in (one UAC prompt via `enable-share-server.ps1`; HKCU flag). This is the sole **owner-approved scoped exception** to Invariant #4's "no firewall/elevation" rule - never silent. The whole Share UI + the worker spawn (all inside Companion) are gated behind `ServerFeatures.IsEnabled()`.
- **Two hosts, one worker - User edition vs Server edition** (`SPECIFICATION_SHARE_SYSTEM_SERVICE.md` (local specification)): the same `fms-share-worker.exe` runs either in the interactive session (the Share Manager starts it - the default) or as the Windows service **`FastMediaSorterCompanionSFTP`** (frozen name), which starts at boot and serves with nobody signed in. A packaging + host-mode distinction, **never a fork**: one SFTP implementation, one IPC schema, one `.fmscfg` format, one Android reconnect contract, one identity. The rules:
  - **The Server edition carries the viewer as an optional, UNTICKED component** (ticket 132): the server leads, the viewer rides along. `tools/Stage-ServerViewerPayload.ps1` stages the User installer's Compact files from the User stage of the SAME version into `<server stage>\viewer\`, and `FastMediaSorterServer.iss` defines the component only when `viewer\FastMediaSorter_LITE.exe` exists (`#if FileExists`), so a stage without it compiles a Server installer with no viewer row - never a row with nothing behind it. The shipping packagers (`release.yml`, `Build-OfflineRelease.ps1`) pass `-Require`. The component has no `Types:` on purpose (a silent install never gets it), is disabled next to an installed User edition, and its shortcut is `Viewer - Fast Media Sorter & Sharing`, never the User edition's own shortcut name in the shared Start-menu group. Default payload, AppId, ARP name, directory, winget package and service name do not move. The site's three doors (viewer / share to Android / the reserved `Media Exchange Server` slot) and the family sentence are in `tools/site-copy.json` and the hand-authored `index.html`/`server.html`.
  - **An optional Windows service is permitted ONLY for the Server edition.** It is never created by a Store install, by a default or silent User install, by a phone request, or by any IPC command - only by the elevated Server installer or by one visible UAC prompt from the Hosting console. Everything machine-affecting (register / repair / restart / remove / migrate / grant a folder to the service account / firewall) goes through the single auditable helper [publishing/installer/install-share-service.ps1](publishing/installer/install-share-service.ps1).
  - **The two never run concurrently, and the service wins.** `ServerFeatures.HostMode()` is authoritative (live SCM query + validation that the registration is ours). `WorkerProcess.EnsureRunning` connects instead of spawning whenever the service is registered *or* merely running, and `cmd/worker` in the worker repo refuses to start a foreground worker while the service is up - they would otherwise fight over the frozen pipe, the listen port and the host key.
  - **One state store.** Once `%ProgramData%\FastMediaSorterCompanion` exists, `sftpserver.DataDir()` prefers it over the per-user directory, so both hosts read and write the **same** shares/settings/stats/host key and a phone sees the same folder list either way. That is why the installer grants the enrolled management user **Modify** (not read) on that directory - read-only would silently split the editions into two folder lists.
  - **The migration runs ONCE, and the machine store then wins.** The Server installer passes `/MIGRATEFROMUSER` on *every* install, so `migrate-to-server` also fires on ordinary upgrades; `Copy-State` is therefore called with `-OnlyWhenTargetIsFresh` and returns untouched the moment `%ProgramData%` already holds the identity. Without that guard every reinstall copied the per-user directory - a snapshot of whenever the User edition last ran - over the LIVE state, rolling back the listen port (silently killing the router forward and every exported QR), the share list, the credential and the counters, while the host key matched and the install looked perfect. `migrate-to-user` deliberately does NOT pass the switch: there the machine store *is* the authority being handed back.
  - **The host key is never regenerated** on a migration, restart, update, reboot or mode change (the installer helper [install-share-service.ps1](publishing/installer/install-share-service.ps1) is where this repository holds `SHARE-SESSION` guarantee 3). Migration validates the fingerprint before and after the copy (`fms-share-worker.exe --inspect-datadir`) and aborts *before* the service is registered on any mismatch, because a new identity unpairs every phone.
  - **Session 0 changes the pipe DACL.** The worker's control-pipe ACL must not come from `os/user.Current()` when it runs as LocalService; the installer enrols the management SID(s) and the service passes them via `--manage-sid`.
  - Separate everything the channels correlate on: its own Inno `AppId`, ARP DisplayName, install dir, release asset (`..-server-setup.exe`, built by [tools/Build-ServerInstaller.ps1](tools/Build-ServerInstaller.ps1) and by `release.yml`) and its own winget package `SerZhyAle.FastMediaSorter.Server` ([publishing/winget/server/](publishing/winget/server)). **Store/MSIX stays User mode only.** Public page: [server.html](server.html).
- **Tray + close-to-tray lifecycle** ([TrayContext.vb](src/FastMediaSorterCompanion/TrayContext.vb)): the **Companion** is the tray-resident host - closing its window hides it to the tray while a share is active, keeping the worker and its controls reachable, and it only truly exits on explicit Quit or once sharing stops. The viewer itself no longer has any close-to-tray behavior (that was removed with the migration); closing the viewer during an active share closes it immediately, leaving Companion's tray icon running.

## Localization - 13 languages, one layer, two programs

Design + full record: `013_SPECIFICATION_THIRTEEN_UI_LANGUAGES.md` (local specification).

- **The key IS the Russian source string.** `Localization.T("Удалить")` - no resource ids, no
  `.resx`. Adding a language is one column in a table instead of a ternary in every file. A key with no
  entry returns the Russian source: visible, never a crash, never `MISSING_KEY_42`.
- **Engine in [src/Localization/](src/Localization)**, string tables beside it. The **Share Manager
  links the same two engine files** (`Localization.vb`, `.Persistence.vb`) via `<Compile Include>` and
  supplies its **own** `RegisterStrings()` + tables under
  [src/FastMediaSorterCompanion/Localization/](src/FastMediaSorterCompanion/Localization). Linked, not
  copied - a fix to `T`/`TF`/`TC` must not need doing twice. A project that links the engine and forgets
  its tables fails with `BC30451`, which is the right failure.
- **Anything carrying a value uses `TF` with a placeholder**, never concatenation: word order and
  direction differ per language, so `"Файл занят: " & name` cannot be translated correctly and
  `TF("Файл занят: {0}", name)` can. `TC(context, key)` disambiguates the handful of Russian words that
  are genuinely two different things.
- **Storage**: `UiLanguage` (ISO code) under the same `SZA\FastMediaSorter` hive, with the pre-13
  `Is_Russian_Language` still written as a mirror so an older exe still lands on a sane language. Both
  programs read and write it, so a switch in either shows in the other on its next start.
- **`Is_Russian_Language` is a derived compatibility shim** in `Common_Module` (viewer only - Companion
  has none). New code must not read it.
- **Two tests, and the second one is the one that matters.** `LocalizationParityTests` proves every key
  has all 12 translations, matching placeholder arity, no leaked Cyrillic, and that every `T`/`TF`/`TC`
  call site is registered. `LocalizationCoverageTests` counts **strings, not flag reads** - the first
  metric was reads under a budget, and one `Dim rus As Boolean = Is_Russian_Language` at the top of a
  `Select Case` hid 44 untranslated strings behind a single read. Every Cyrillic literal must reach the
  layer or be a registered key; the exemptions are listed with reasons in the test.
- **Never put a smart double quote in a literal, in any language.** The VB compiler treats `“`/`”`
  (U+201C/U+201D) as string delimiters, so German `„…“` and Chinese `“…”` silently break the file and
  cascade `BC30035` dozens of lines below. Use `«…»` and `「…」`.
- **RTL is `RightToLeft = Yes` only, never `RightToLeftLayout`.** The second flag mirrors the whole
  window device context - Arabic came out as a mirror image, glyphs and Latin title bar alike. In the
  viewer it would also move the media PictureBox that `Draw_Perspective` and the OCR overlay derive
  their geometry from.
- **Script fonts** (`Localization.FontFamily()`): Nirmala UI for hi/bn, Microsoft YaHei UI for zh,
  Segoe UI for ar/ur - the app is pinned to Microsoft Sans Serif, which has no Arabic at all. In the
  **viewer** the font goes on individual controls, never the form: that layout is DPI-unaware and
  pixel-tuned. In the **Companion** it goes on the form, which is safe because those windows scale by
  `AutoScaleMode.Dpi`, so the font is not the scaling baseline.
- **The x86/net48 fallback ships RU+EN only** (`#If NETFRAMEWORK` cuts `Codes`), because Nirmala UI
  arrived in Windows 8 and offering a language that renders as boxes is worse than not offering it. A
  `UiLanguage` it does not ship falls back to English rather than throwing.
- **Site**: 12 per-language pages under **one** root folder, `lang/<code>/index.html`, generated by
  [tools/Build-SitePages.ps1](tools/Build-SitePages.ps1) from [tools/site-copy.json](tools/site-copy.json).
  They are render targets - edit the JSON and re-run, never the HTML (canon invariant 16); `-Check`
  proves the committed pages still match **and** fails if a legacy per-language folder is left in the
  repo root. **`robots.txt` and `sitemap.xml` are render targets of the same script** - the sitemap's
  public set is "every `*.html` in the repo root, plus one directory per translated language", derived at
  run time, so adding a page needs no edit here; the root entry is listed as the bare directory URL to
  match `canonical`, and only that entry carries the `xhtml:link` alternates. The **shared social assets
  are named once** at the top of the script (`$OgImage`, `$Favicon`): both previously pointed at
  `assets/og-image.png` and `assets/favicon.ico`, which have never existed, so all 12 translated pages
  shipped a dead link preview and a dead favicon while the hand-authored root page pointed at the real
  files. The prefix is the script's single `$LangDir` - URL, hreflang and output path all follow it,
  but the root `index.html` (the hand-authored trilingual entry) carries its own switcher and hreflang
  block that must be edited by hand to match. Pages is branch-based here (`main:/`), so a clean
  `/lang/ru/` URL needs a real directory; `/ru/` and friends are gone and are **not** redirected.

## Code Style & Constraints

**VB.NET Strict Mode** - All modules enforce:
```vb
Option Explicit On    ' All variables must be declared
Option Strict On      ' No implicit type conversions
Option Compare Binary ' Case-sensitive string comparison
Option Infer On       ' Allow type inference where possible
```

**File Organization**:
- `.vb` files are code-behind; `.Designer.vb` files are auto-generated (don't edit manually)
- Form classes inherit from `System.Windows.Forms.Form`
- Modules are for shared utilities and P/Invoke declarations
- `Main_Form` is one logical class spread across multiple `Partial Class Main_Form` files (`Main_Form.*.vb`). Fields/methods are shared across all of them - put a change in the file matching its concern, and watch for name collisions across partials.
- **Every `src/*.vb` file compiles into BOTH viewer exes** (the modern project links `..\**\*.vb`). Platform divergence goes behind `#If NETFRAMEWORK` / `#If Not NETFRAMEWORK`, never into project file lists - and a change to shared code must make sense on both runtimes. See "Two builds, one source tree".
- Build treats a fixed set of VB warnings as errors (`WarningsAsErrors`, kept identical in both viewer projects; the authoritative list is in [the modern project](src/Modern/FastMediaSorter.Modern.vbproj) and [the fallback project](src/FastMediaSorter.vbproj)), so these will fail the build, not just warn.

**Keyboard Shortcuts** - Most features driven by hotkeys, not menus:
- Stored in app settings (persisted to registry/config)
- Hardcoded hotkey array in Common_Module for folder shortcuts
- Inspect Main_Form keyboard event handlers for the full mapping
- **Video track keys are the modern build only** (`Main_Form.VideoTracks.vb`): **A** cycles the audio track, **V** the subtitles, and a "Tracks" button appears in the toolbar **only when the file offers a choice** (via `SetToolbarItemHidden`, the same mechanism the image-only translate buttons use). Modern-only for a real reason: on net48 a video goes to the IE WebBrowser first and only reaches LibVLC if IE refuses it, so the same control would work for an MKV and silently do nothing for an MP4. VLC's own audio-track key is `B`, which is already "previous file" here - hence `A`. The choice is remembered **by ISO language code**, not by id (per-file) or name (VLC returns composites like `Russian - [Russian]` that only match within one release); `player.Media.Tracks` keeps a clean `Language` field even after the `Media` object is disposed. Note `AudioTrackDescription`/`SpuDescription` always include a `Disable` entry with **id -1** - count real tracks, not `Length`.
- **Zoom keys are the modern build only** (`Main_Form.Zoom.vb` + `ZoomMath.vb` are whole-file `#If Not NETFRAMEWORK`): the **grey** NumPad block - `+`/`-` zoom at the cursor, `/` fits, `*` is 100 %. Only the grey block, because every `Ctrl` combo is already taken and NumPad `0..9` are the sort hotkeys. The first-run help gets its mainline-only lines from `ModernHelpLines()` in `Main_Form.Localization.vb`, which returns `""` on net48 so the x86 viewer never advertises keys it does not have.
- **Move vs copy is chosen at the moment of the action, mainline only** (`SPECIFICATION_COPY_ACTIONS_REWORK.md` (local specification)): `0..9` move, **`Shift` + a TOP-ROW digit copies** into the same slot (not numpad - with NumLock on, Windows drops NumLock while Shift is held, so `Shift+NumPad1` arrives as `Keys.End`). Every single-file entry point - keys, the recipients overlay's per-row "copy" zone, both media menus' side-by-side `Переместить в`/`Копировать в`, `Shift`+double-click in the settings grid - passes an explicit `RecipientActionKind` to the ONE implementation `Main_Form.ExecuteRecipientAction`. The **thumbnail panel is the exception** (corrected 2026-09-25, audit T-01): it acts on a whole selection, so it keeps its own multi-file loop (`PoMove_for_Panel` in [Image_Panel_Form.vb](src/Image_Panel_Form.vb)) and takes move-or-copy as a parameter there instead. **`PoMove(slot)` is now a thin wrapper and, on modern, no file operation consults `Is_Copying_not_Moving`**: on net48 two places still honour the global copy mode (whose checkbox lives on there) - `PoMove` and the panel's `#If NETFRAMEWORK` branch - and on modern `PoMove` always means Move. Do not reintroduce a `Is_Copying_not_Moving` read anywhere else - in the mainline UI nothing can switch it. Whether a copy advances to the next file is `AdvanceAfterCopy` (default on).

**UI Threading**:
- Image/video loading happens on background threads to avoid UI freeze
- Use `Invoke()` or `BeginInvoke()` when updating UI controls from worker threads
- LibVLC video playback is asynchronous; use `MediaPlayer.Play()` callbacks

**File Locking**:
- `LoadImageWithStream()` keeps the MemoryStream open to allow Windows to release the file handle
- Disposed explicitly when image is no longer needed
- Critical for fast file operations in a media sorter

into a pass, nor into a defect). `-SkipGo` reports that suite as **SKIPPED** on the verdict line, never as

### Supporting a New Media Format
1. Add extension to `Image_File_Extensions` or `video_File_Extensions` in Main_Form.vb
2. Test playback in **both** exes: modern always goes to LibVLC; on net48 the WebBrowser tries first and LibVLC picks up what it can't play. A new *image* format belongs behind the `IImageDecoder` seam ([src/Imaging/](src/Imaging)), not in a new `FileManager` branch.
3. Verify no memory leaks (dispose Image/Bitmap, MemoryStream)

## Environment Notes

- Support matrix: the **mainline x64 exe** covers Windows 10 1607+ / 11 / Server 2016+; the **x86 exe** covers Windows 7/8.1 and 32-bit Windows. Developed primarily on Windows 11.
- Executables built to `bin/Release/FastMediaSorter_LITE.exe` (mainline) and `bin/Release/FastMediaSorter_x86.exe` (fallback) - `bin/Release` is the distribution shape, both exes plus their shared library trees
- Settings/state persisted to Windows registry (`SZA\FastMediaSorter` - one hive for both exes)
- Single-instance enforced via app mutex (`app_Mutex_Name = "FastMediaSorterSingleInstanceMutex"`) - one mutex across both exes; forwarding searches both process names
