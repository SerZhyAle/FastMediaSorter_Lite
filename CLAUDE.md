## Project Overview

**Fast Media Sorter for Windows** (formerly **FastMediaSorter LITE**) is a Windows Forms application for viewing and managing image and video files. It ships as **two exes side by side in one folder**, built from **one source tree**: the **.NET 10 x64 mainline** (`FastMediaSorter_LITE.exe` - LibVLC-only playback, ImageSharp 3 decoding) and a lean **net48 x86 fallback** (`FastMediaSorter_x86.exe`) for Windows 7/8.1 and 32-bit Windows, which keeps the legacy stack (IE WebBrowser for H.264/MP4 + LibVLC fallback for AVI, ZMBV, VP9, MKV, etc.). Read "Two builds, one source tree" below before touching anything build- or media-related.

### Naming rule (light rebrand, 2026-07)
Display name is **Fast Media Sorter for Windows** and now appears on every user-visible surface across all channels. Each channel keeps ONE *frozen technical anchor* that carries update-correlation; only the anchor is off-limits - the visible name rides on top of it:
- **App / GitHub**: window title, exe properties, site, README, and the GitHub release title/body already use the new name. ## Two builds, one source tree - read before editing a seam

The viewer is **one app** shipped as **two exes in one folder**. Design: [SPECIFICATION_DOTNET10_MODERN_BUILD.md](docs/specifications/done/SPECIFICATION_DOTNET10_MODERN_BUILD.md); live implementation journal: [PROGRESS_DOTNET10_MODERN_BUILD.md](docs/guides/PROGRESS_DOTNET10_MODERN_BUILD.md).

| | **Mainline** | **Fallback** |
|---|---|---|
| Exe | `FastMediaSorter_LITE.exe` (frozen anchor) | `FastMediaSorter_x86.exe` (new name) |
| Project | [src/Modern/FastMediaSorter.Modern.vbproj](src/Modern/FastMediaSorter.Modern.vbproj) (SDK-style) | [src/FastMediaSorter.vbproj](src/FastMediaSorter.vbproj) (old-style) |
| Target | `net10.0-windows`, x64, self-contained single-file (runtime inside the exe) | net48, genuinely `PlatformTarget=x86` (32-bit process), ~3 MB |
| Built by | `dotnet publish` | `msbuild` |
| Runs on | Windows 10 1607+ / 11 / Server 2016+ | Windows 7/8.1 and 32-bit Windows |
| Video | **LibVLC only** | IE WebBrowser (H.264) + LibVLC fallback |
| Images | ImageSharp 3 | WIC + ImageSharp 2 fallback |
| Managed deps | NuGet `PackageReference`; publish lays them down | ILMerge + `packages.config` + `RuntimeBootstrap` `AssemblyResolve` |

**Rules - do not "fix" these away:**
- **Clarify ambiguity first (owner decision, 2026-07-19):** When a request does not clearly identify the target screen, runtime, or expected outcome, ask a concise clarifying question before changing code. Do not infer the target from similarly named legacy/shared UI.
- **Maintenance policy (owner decision, 2026-07-19):** .NET 10 x64 is the active development target. Do not add features, UI refinements, or intentional behavior changes to the net48 x86 fallback; touch it only to fix an actual bug that is found. When a shared-source change is mainline-only, preserve net48 behavior with a `#If NETFRAMEWORK` seam.
- **One app, not two**: one folder, one mutex `FastMediaSorterSingleInstanceMutex`, one registry hive `SZA\FastMediaSorter`. Launching either exe while the other runs forwards the file to the running window - so [Application_Events.vb](src/Application_Events.vb) searches **both** process names (`Viewer_Process_Names`): `GetProcessesByName` matches on name only, and searching just our own name would find nothing when the sibling is the one running, cancelling the launch **silently** with no window and no file opened.
- **Both projects compile the SAME sources**, but a NEW file has to be added to the net48 list BY HAND: the modern vbproj links `..\**\*.vb` (picked up automatically), while the old-style [src/FastMediaSorter.vbproj](src/FastMediaSorter.vbproj) carries an explicit `<Compile Include="..">` list. Drop a `.vb` under `src/` and only the mainline sees it - the x86 build then fails on the first thing that references it (`BC30451: '..' is not declared`), which is the *good* case; a file nothing references yet just silently is not in that exe. Add the `<Compile Include>` entry (with `<DependentUpon>Main_Form.vb</DependentUpon>` for a `Main_Form.*.vb` partial) in the same commit. Divergences live behind `#If NETFRAMEWORK` seams, never in per-project file lists.
- **`NETFRAMEWORK` is defined BY HAND**: old-style projects do **not** define it, so [src/FastMediaSorter.vbproj](src/FastMediaSorter.vbproj) sets `<DefineConstants>NETFRAMEWORK=True</DefineConstants>` in **both** configurations. Delete or typo it and every seam silently compiles the wrong branch - no error, just a modern-only code path inside the net48 exe.
- **Never delete a seam to "simplify"** - each exists because the two runtimes genuinely differ. Seams live in: [src/Imaging/](src/Imaging) (whole-file), `Application_Events.vb`, `Main_Form.vb`, `.MediaLoading.vb`, `.VideoPlayer.vb`, `.FileOperations.vb`, `.DragDrop.vb`, `.Lifecycle.vb`, `AppFileLogger.vb`, `RuntimeBootstrap.vb`, `OptionalRuntimeManager.vb`, `Table_Form.vb`, `Translate/OllamaTranslator.vb`.
- **Shared adjacent libraries, resolved per process bitness** out of the same tree: `libvlc\win-x64` vs `libvlc\win-x86`, `x64\tesseract50.dll` vs `x86\` (`CurrentArchFolder()`/`CurrentVlcArchFolder()` in [OptionalRuntimeManager.vb](src/OptionalRuntimeManager.vb)). This needed no code change - don't "unify" it.
- **The x86 build keeps OCR and translation; only Share is cut** (owner decision, 2026-07-16). Share is gone because it *cannot* work there: the Companion it wakes is `net10.0-windows` **x64**, so it does not start on Windows 7/8.1 or 32-bit Windows - exactly the machines the x86 exe exists for. `Main_Form.ShareLauncher.vb` and `Table_Form.ShareLauncher.vb` are whole-file `#If Not NETFRAMEWORK`, and the installer's `share` component carries `MinVersion: 10.0.14393` so it is not offered where it could not run. **There is no `FEATURE_FULL` constant and no stripped build configuration** (the mechanism epic O-7 asked about): there is exactly ONE net48 build and it IS the x86 fallback, so `NETFRAMEWORK` already names the thing precisely - a second constant would only add a way for the two to disagree. Note the epic's §1.1 still describes a leaner legacy (no OCR/translate, "tens of MB instead of hundreds"); that was written before the two-exe directive, and in one shared folder the OCR/codec/companion trees are installed for the x64 mainline anyway, so cutting them from x86 would have saved the exe alone.

**Modern-only compatibility pins** (each deliberate; removing one is a visible regression):
- `ApplyApplicationDefaults` in [Application_Events.vb](src/Application_Events.vb) pins `HighDpiMode.DpiUnaware` + `Microsoft Sans Serif` 8.25. The **shipped net48 exe never embedded `app.manifest`**, so DPI-unaware IS the reference behavior; .NET would otherwise default to `SystemAware` + Segoe UI 9pt and shift the pixel-tuned Designer layout. (PerMonitorV2 is a deliberate future step, needs re-testing at 125/150%.)
- The modern vbproj sets `System.Globalization.UseNls=true` so `abc`/`xyz` file sorting matches net48 (.NET 5+ uses ICU, net48 uses NLS).
- Tesseract's loader needs `InteropDotNet.LibraryLoader.Instance.CustomSearchPath` under single-file publish (`Assembly.Location` is `""` there).
- A portable JSON facade in `TranslateHttp` ([src/Translate/OllamaTranslator.vb](src/Translate/OllamaTranslator.vb)) keeps `JavaScriptSerializer` on net48 and uses `System.Text.Json` on modern, shaped to the same untyped graph so the **OCR disk cache stays compatible** across both exes.

### Prerequisites
- **.NET 10 SDK** - builds the **mainline x64 viewer** (`src/Modern/FastMediaSorter.Modern.vbproj`) **and** the Companion app (`src/FastMediaSorterCompanion/FastMediaSorterCompanion.vbproj`), both via `dotnet publish`
- **.NET Framework 4.8** targeting pack - builds the x86 fallback viewer (`src/FastMediaSorter.vbproj`)
- Visual Studio 2022 (or MSBuild CLI). A full build spans two toolchains (MSBuild/net48 + dotnet/net10) across **three programs**; `build.ps1` orchestrates all of them. **`msbuild` alone does NOT produce the mainline exe** - the sln yields only the x86 viewer + Companion in `bin\Release`; the self-contained single-file x64 build only comes out of `dotnet publish` (which is why every packager runs its own).
- NuGet: the net48 project restores via `packages.config` (vendored `packages/`); the two SDK-style projects use `PackageReference`. Project files live in `src/`; the solution `FastMediaSorter.sln` (all three projects) is at the repo root.
- Project identity (both viewer projects): `RootNamespace = fmsl`, startup object `fmsl.My.MyApplication`; `AssemblyName` is `FastMediaSorter_LITE` (modern) vs `FastMediaSorter_x86` (net48) - see "Two builds, one source tree" above
- ILMerge (3.0.41) applies to the **x86 build only**: it bundles most managed dependencies into that exe at build time, while heavier/native-interop ones (LibVLCSharp, Tesseract, QRCoder, SixLabors.ImageSharp and their transitive `System.*` shims) are embedded as `FmsPayloadmanaged/*.dll` resources and resolved at runtime by [RuntimeBootstrap.vb](src/RuntimeBootstrap.vb) - see "Single-exe support infrastructure" under Core Components. The mainline uses single-file publish instead (no ILMerge, no managed payload resources).

### "Сборка" vs "Релиз" - two distinct flows (see [BUILD_AND_RELEASE.md](docs/guides/BUILD_AND_RELEASE.md))

- **Сборка / build** = LOCAL only: `.\build.ps1` (builds all three programs - MSBuild Rebuild for the x86 viewer, `dotnet publish` for the x64 mainline and the Companion - then deploys **both viewer exes side by side** to the user's work folders). Test by hand, then commit/push. **Never creates or pushes a `v*` tag.** Pushing to a branch is free - GitHub Actions does NOT run on branch pushes.
- **Релиз / release** = GitHub build + winget + Microsoft Store: `.\tools\Release.ps1 -Push` (runs a free local check-build first, then creates and pushes the `vYY.M.D.HHmm` tag). The release `workflow` ([.github/workflows/release.yml](.github/workflows/release.yml)) is triggered **ONLY by pushing a `v*` tag** - that tag push is the single billable operation.
- **When the user asks for a "сборка"/"build"/"собери", run the LOCAL flow only and do NOT create or push a tag.** A tag (= paid GitHub run) requires an explicit "релиз"/"release" instruction. `tools/Release.ps1` defaults to a dry-run (no push) for safety; it pushes only with `-Push`.

### Build Commands

Full local build - **all three programs**, deployed into the distribution shape:
```powershell
.\build.ps1
```
Flags: `-SkipModern` (x86 viewer + Companion only), `-SkipCompanion`, `-NoClean`.

Partial builds (syntax checks only - neither shape is shippable on its own):
```powershell
# x86 viewer + Companion; does NOT produce the mainline exe
msbuild FastMediaSorter.sln /p:Configuration=Release /p:Platform="Any CPU"
# the mainline x64 viewer on its own
dotnet publish src\Modern\FastMediaSorter.Modern.vbproj -c Release -r win-x64
```

Run the app. **`bin\Release` IS the distribution shape** - both viewer exes plus the shared `libvlc\`, `x64\`, `x86\`, `flags\` and `companion\` trees:
```powershell
.\bin\Release\FastMediaSorter_LITE.exe   # mainline (Windows 10 1607+)
.\bin\Release\FastMediaSorter_x86.exe    # 32-bit fallback (Windows 7/8.1)
```

Or open in Visual Studio and press F5 to debug.

### Version Auto-Generation
Both viewers stamp the same `YY.M.D.HHmm` version (e.g., `26.6.2.0124`) at build time: the net48 project via its `UpdateVersion` target (rewrites `My Project\VersionInfo.vb` before compilation), the modern project via its `AutoVersion` property. Both accept a release override (`-p:ReleaseVersion=..`); keep the two exes' stamps identical.

### Release Pipeline (CI)
Releases are cut by **pushing a `vYY.M.D.HHmm` tag** (or running the `Release` workflow manually with a tag input). [.github/workflows/release.yml](.github/workflows/release.yml) runs on `windows-latest` and:
1. Restores NuGet, `msbuild .. /t:Rebuild` in Release (which yields only the **x86** viewer), **then `dotnet publish` the modern project** (`-o modern-publish`, `-p:ReleaseVersion=` so both exes carry the tag's version) and the Companion. Since msbuild alone never produces the mainline exe, **every packager runs its own publish** ([tools/Build-Installer.ps1](tools/Build-Installer.ps1), [tools/Build-OfflineRelease.ps1](tools/Build-OfflineRelease.ps1), [.github/workflows/release.yml](.github/workflows/release.yml), [publishing/msix/build-msix.ps1](publishing/msix/build-msix.ps1)).
2. Stages everything in `bin/Release` **except `.pdb`/`.xml`** (plus `README.md`, `LICENSE`) into `stage/FastMediaSorter-<version>-windows-x64/`, then drops the published `FastMediaSorter_LITE.exe` in next to its x86 sibling - **two exes, one set of support trees**, since one package serves modern and legacy Windows.
3. Runs [tools/Prepare-OcrOfflinePayload.ps1](tools/Prepare-OcrOfflinePayload.ps1), which downloads all OCR `tessdata_fast` languages shown in the UI plus their `tessdata_best` counterparts into `tessdata/` and `tessdata-best/`. It **trims the 32-bit native trees by default** (~100 MB; the x86 viewer downloads them on demand via `OptionalRuntimeManager`) - pass `-KeepX86` to keep the x86 fallback fully offline.
4. Packages two **offline-ready** assets from that staged tree: a **portable ZIP** and an **Inno Setup installer EXE** (compiled via [publishing/installer/FastMediaSorter.iss](publishing/installer/FastMediaSorter.iss); Inno Setup installed on the runner with `choco install innosetup`). Each gets a `.sha256` sidecar. The installer ships **both** exes and points the Start-menu/desktop shortcut, the post-install launch and the file associations at whichever exe **runs on that OS** (`UseModernExe`: Windows 10 build >= 14393 gets the mainline, older gets `FastMediaSorter_x86.exe`); `MinVersion=6.1` still lets Setup run on Windows 7.
5. Publishes a GitHub Release with all four files attached.

For a local release-style build, run:
```powershell
.\tools\Build-OfflineRelease.ps1
```
This mirrors the CI packaging flow and emits offline-ready artifacts in `dist/`.

### Standalone copy-anywhere installer ("сборка", not a release)
[tools/Build-Installer.ps1](tools/Build-Installer.ps1) produces **only** the offline `setup.exe` in `dist/` - a package you can copy to any Windows machine and run (per-user, no admin, no internet at install time). It reuses the frozen `publishing/installer/FastMediaSorter.iss` and `Prepare-OcrOfflinePayload.ps1`, runs its own `dotnet publish` of the modern project (so the setup carries both viewer exes), explicitly bundles the Android-share worker into `companion/`, and **never creates or pushes a `v*` tag** - it is a local convenience, not `tools/Release.ps1`. Unlike `Build-OfflineRelease.ps1` it skips the portable ZIP and, by default, the heavy `tessdata_best` models (fast OCR models only → ~lean installer; best models download on demand). Flags: `-IncludeBest` (fully offline incl. best OCR), `-SkipOcr` (smallest; OCR downloads on demand), `-SkipBuild` (repackage the current `bin/Release`), `-Open` (reveal in Explorer). Needs Inno Setup 6 (`winget install JRSoftware.InnoSetup`); it fails fast with that hint if missing.

The version in the tag is authoritative for asset names but is independent of the build-time `UpdateVersion` stamp - keep them consistent. See [SPECIFICATION_GITHUB_STORE.md](docs/specifications/done/SPECIFICATION_GITHUB_STORE.md) for the rationale behind shipping an EXE installer (GitHub-Store discoverability; a ZIP-only release is invisible to that marketplace).

### Publishing to winget - read before touching the manifest
**The winget manifest must point at the Inno `setup.exe` directly (`InstallerType: inno`) with NO declared dependencies.** This was learned the hard way (see [SPECIFICATION_WINGET_PUBLISHING.md](docs/specifications/done/SPECIFICATION_WINGET_PUBLISHING.md)). Quick rules:
- **Never** point winget at `single-exe.zip` - Defender ML flags the self-extracting bootstrap as `Program:Script/Wacapew.A!ml` (persistent false positive). It's a GitHub-only convenience download.
- **Don't** use the portable `windows-x64.zip` shape - the ~99 MB payload aborts the install with `0x80004004` after extraction.
- **Don't** declare the `Microsoft.VCRedist.2015+.x64` dependency - it sends winget into a resolution loop and aborts with `0x8A150044`; the app installs fine without it (validation never launches the app).
- **Don't** add `Scope: user` - it forces the harness into a non-elevated `--scope user` flow and the install fails with `0x8A150044` ("no suitable installer found for --scope user"). Omit `Scope` so validation runs elevated/machine.
- The "Missing `NestedInstallerType` / fewer `Tags`" inconsistency note is a non-blocking `Validation-Guide`, not a failure.
- Get the *real* failure reason from the build's `InstallationVerificationLogs` artifact, not the generic GitHub bot comments - the doc has a copy-paste snippet.

### Publishing to the Microsoft Store (MSIX) - see [STORE_PUBLISHING.md](docs/guides/STORE_PUBLISHING.md)
The Store path (Path A: MSIX) is **additive** - it does not change the GitHub release or winget flows. Full playbook + filled listing copy (description, features, runFullTrust justification, privacy text) is in [STORE_PUBLISHING.md](docs/guides/STORE_PUBLISHING.md); packaging detail in [publishing/msix/README.md](publishing/msix/README.md). Key facts:
- **No app code change is needed** - the app is already MSIX-safe: everything mutable goes to `%LOCALAPPDATA%\SZA\FastMediaSorter` (OCR downloads/cache via `OcrPaths`) or the registry, both writable inside the package container; bundled `tessdata` next to the exe is only ever read (the install dir is read-only under MSIX).
- **MSIX is x64 only and packages the mainline exe only** - the x86 fallback is never packaged (the Store target floor is well above Windows 7).
- Build with [publishing/msix/build-msix.ps1](publishing/msix/build-msix.ps1): MSBuild Release + `dotnet publish` the modern project → stage the **offline payload** (same `bin/Release` tree minus `*.pdb`/`*.xml`, run through [tools/Prepare-OcrOfflinePayload.ps1](tools/Prepare-OcrOfflinePayload.ps1)) → generate logos from [assets/icons/store-icon-256.png](assets/icons/store-icon-256.png) → fill manifest → `makeappx pack`. `-SelfSign` makes a sideload-testable build; **no `-SelfSign` for the Store** (Microsoft re-signs on certification - no paid cert needed).
- [publishing/msix/AppxManifest.xml](publishing/msix/AppxManifest.xml) wraps the exe as a **full-trust** desktop app (`rescap:runFullTrust` keeps LibVLC/GDI+/file-access/local-HTTP working) and declares image **file associations** (the manifest equivalent of the Inno per-user registry writes). Identity (`Name`/`Publisher`/`PublisherDisplayName`) is `__PLACEHOLDER__` filled at pack time from Partner Center (Product ▸ Product identity) via `-IdentityName`/`-Publisher`/`-PublisherDisplayName` - must match **exactly** or upload is rejected.
- **Version remap (Store requires revision = 0):** the script maps the exe's `YY.M.D.HHmm` stamp to `YY.(M*100+D).HHmm.0` (each part ≤ 65535). Don't hand-edit it.
- Needs the Windows SDK for `makeappx.exe`/`signtool.exe` (`winget install Microsoft.WindowsSDK`); they live under `C:\Program Files (x86)\Windows Kits\10\bin\*\x64\`.

## Architecture

### Core Components

**Main_Form** - Primary UI window, split across one `partial class` per concern (all `Partial Class Main_Form`; edit the relevant file, not just the main one):
- **[Main_Form.vb](src/Main_Form.vb)** (~665 LOC - a decomposed "shell"; see [SPECIFICATION_MAIN_FORM_DECOMPOSITION.md](docs/specifications/done/SPECIFICATION_MAIN_FORM_DECOMPOSITION.md), the class was split from one 3,356-LOC file into ~20 partials totaling ~7,700 LOC) - core: file browsing, slideshow, keyboard shortcuts, drag-drop, recent files/folders (~100 max), English/Russian switching via `Is_Russian_Language`. **First-run UI language follows the Windows display language** (`SystemDefaultIsRussian()` in [Main_Form.Localization.vb](src/Main_Form.Localization.vb): Russian display language → Russian, everything else → English); once the user toggles it, the saved `Is_Russian_Language` registry value wins. Hosts the `COPYDATASTRUCT` declaration and `ProcessArgument()` entry point used for cross-instance arg forwarding (see Application_Events below).

**Display resilience** (these never let a transient failure drop the image):
- `UpdateControlVisibility()`'s dynamic-background colour analysis and `Draw_Perspective()` both run their GDI+ pixel work inside a `Try/Catch`. GDI+ can transiently throw (`OverflowException`, `"Parameter is not valid"`) - e.g. while the background worker decodes on a slow network share - and the image is already on the PictureBox, so the analysis failure is swallowed and the frame keeps the previous tint/bars instead of aborting the load.
- `Draw_Perspective()` debounces with a trailing-edge timer: a redraw skipped by the `how_long_wait_before_draw_perspective` throttle is retried once scrolling stops, so the image you settle on always gets its bars.
- The background worker reads image dimensions via `Utils.GetImageDimensions()` (header parse, no GDI+) instead of `Image.FromFile`, so it never decodes the current image concurrently with the UI thread's `GetPixel`.
- **First media gets its bars too**: the first image at startup (a command-line file/the restored last folder) loads inside `Form1_Load` while `is_form_shown` is still `False`, so every `Draw_Perspective()` in that path is gated off. `Main_Form_Shown` redraws once (the form is now at its final size and `is_form_shown = True`); `Draw_Perspective` self-gates if no picture box is visible or perspective is off.
- **Seam fix**: `GetDisplayedVerticalEdgeColors`/`GetDisplayedHorizontalEdgeColors` sample one pixel **in** from the very edge (`edgeInset`). The outermost downscaled row/column folds in the darkest border/vignette pixels and comes out a few levels darker than what the `Zoom` PictureBox actually paints, leaving a faint dark seam between photo and bar; the second row/column matches the displayed edge, so the bar joins seamlessly.

**[Application_Events.vb](src/Application_Events.vb)** - `My.MyApplication` startup hooks for single-instance behavior (plus the modern-only `ApplyApplicationDefaults` DPI/font pin - see "Two builds, one source tree")
- On `Startup`: a path-independent named mutex (`FastMediaSorterSingleInstanceMutex`) detects an already-running instance (VB's built-in `IsSingleInstance` only matches same exe path, so debug/release/renamed copies would each start their own). If found, the new process forwards its command-line file path to the running window via `WM_COPYDATA` and cancels (`e.Cancel = True`). **The running instance may be either exe**, so the search runs over **both** names in `Viewer_Process_Names` - see the two-exe rules above. An instance whose window is hidden or minimized can have `Process.MainWindowHandle` zero - the sender falls back to `EnumWindows` over the process's top-level windows (only `Main_Form.WndProc` reacts to `WM_COPYDATA`, so sending to all of them is safe). (The same reverse pattern is what `Main_Form.ShareLauncher.vb` uses to wake the tray-resident Companion.)
- On `StartupNextInstance`: the running instance receives the new args, calls `Main_Form.ProcessArgument()`, and deliberately avoids stealing focus (restores the previously-foreground window).
- **Bare relaunch** (no file argument) = the user re-ran the exe just to get the window back; both paths restore it instead of doing nothing: `StartupNextInstance` calls `Main_Form.RestoreMainWindow()` directly, the mutex path forwards `Main_Form.Show_Window_Command` (`::fms-show-window::`) which `External_message` intercepts. The window reappears (it was only minimized/behind, never torn down) and - unlike a file open - DOES take focus (a bare launch has no other purpose). `RestoreMainWindow()` (in `Main_Form.Lifecycle.vb`) is now just "unminimize + activate + BringToFront" - **LITE no longer has any tray-resident/close-to-tray mode** (that moved to the Share Manager with the share feature), so closing LITE closes it like a normal viewer.
- `WM_COPYDATA` payload is **UTF-8** on both send and receive (the receiver in `Main_Form.vb` decodes the bytes as UTF-8, not `PtrToStringAnsi`, so non-ASCII filenames survive).
- `ProcessArgument()` doesn't trust a single `File.Exists` for a `\\server` path: it probes with `File.GetAttributes` to tell a genuinely-missing file (fail fast) from a network hiccup (retry for the SMB session to recover) from an access-denied **lock** (the file is still being written/downloaded). A locked file is watched on a timer and **opens automatically once it unlocks**, instead of being silently dropped.

### Perspective Background Effect
See [SPECIFICATION_BACKGROUND_EFFECT.md](docs/specifications/done/SPECIFICATION_BACKGROUND_EFFECT.md) for the full algorithm. Summary:
- Fills "black bars" (pillarbox/letterbox) when image aspect ratio ≠ viewport aspect ratio
- Two modes:
  - **Uniform**: Edge is solid color → fill with average color
  - **Perspective**: Edge is complex → extend each edge row/column into the bar
- Triggered on image load/resize; runs async to avoid UI lag
- Constants in Main_Form.vb (e.g., `percent_of_color_deviation = 4`, `step_size_while_color_Search = 100`)

### OCR + On-Image Translation
See [SPECIFICATION_OCR_TRANSLATION_OVERLAY.md](docs/specifications/done/SPECIFICATION_OCR_TRANSLATION_OVERLAY.md) for the full design. Summary:
- **Hotkeys**: `T` runs OCR + translate (or toggles the overlay) when the feature is enabled; `Shift+T` toggles auto-OCR mode. When the feature is off, `T`/`Shift+R` keep their legacy rotate meaning. The **Перевод / Translate** toolbar button triggers the same pipeline.
- **Pipeline** ([Main_Form.OcrTranslate.vb](src/Main_Form.OcrTranslate.vb), `RunOcrPipeline`): OCR the image → `OcrBlockBuilder` groups lines into blocks (and drops isolated tiny blocks that are texture noise) → translate all blocks in one batch → render the translated text as an overlay over each block ([Main_Form.OcrOverlay.vb](src/Main_Form.OcrOverlay.vb)). Overlay text is sized to the **original** text, not a tiny capped font: `FitFont` starts from the source block's median line height (`MedianBlockLineHeight × scale`) and only shrinks when a longer translation would overflow (bounds `MinOverlayFont = 8`, `MaxOverlayFont = 200` px), so headings stay big. Results are cached in memory and (optionally) on disk by `TranslationCache`, keyed on file path + write-time + engine + provider + languages - where the **engine** key folds in OCR model quality and page mode and the **provider** key folds in the Ollama model, so changing any of them invalidates cached results. **Empty (`No text found`) results are no longer cached**, so a bad first pass doesn't poison later runs; opening the settings dialog also clears the cache.
- **OCR engine**: multi-pass Tesseract (`TesseractOcrEngine`), loading images via `Pix.LoadFromMemory`. Instead of one `PageSegMode.Auto` pass it runs several scored attempts - single-language passes (in `OcrAttemptCodes` order, e.g. `rus → ukr → eng` for `auto`) across page-segmentation modes and light preprocessing (grayscale / inverted), upscaling small images - and keeps the highest-scoring result. `fast` (`tessdata`) or `best` (`tessdata_best`) packs download on demand; the **OCR mode** setting can force a specific `PageSegMode` (auto/block/sparse/line/vertical).
- **Translators** (`CreateTranslator()` picks by `ocr_Settings.Provider`): `OllamaTranslator` (default - local LLM at `localhost:11434`, batches blocks, retries once when the model echoes the source) and `LibreTranslateTranslator`. Both parse JSON arrays through `TranslateHttp.JsonItemToString`, which pulls the real string out of a wrapped object (`{"translation":"…"}`) - a raw `Convert.ToString` on such a `Dictionary` would otherwise leak `System.Collections.Generic.Dictionary\`2[…]` into the overlay.

### Android Folder Share (Companion app + Go worker)
Two tiers now: a **standalone .NET 10 Companion app** (`src/FastMediaSorterCompanion/`, "Fast Media Sorter: Share Manager") drives a **bundled headless Go worker** (`companion\fms-share-worker.exe`). LITE is only a launcher (`ShareLauncher`, above). See [SPECIFICATION_SHARE_COMPANION_APP.md](docs/specifications/done/SPECIFICATION_SHARE_COMPANION_APP.md) for the LITE→Companion split, [SPECIFICATION_SHARE_STATS_AND_TRAY_HUB.md](docs/specifications/done/SPECIFICATION_SHARE_STATS_AND_TRAY_HUB.md) for the connection-stats + tray-hub layer, [SPECIFICATION_ANDROID_FOLDER_SHARE.md](docs/specifications/done/SPECIFICATION_ANDROID_FOLDER_SHARE.md) for the worker IPC protocol / `.fmscfg` schema, and [SPECIFICATION_QR_IMPORT_ANDROID.md](docs/specifications/done/SPECIFICATION_QR_IMPORT_ANDROID.md) for the frozen wire contract (Android side). Summary:
- **Architecture in one sentence**: neither LITE nor Companion implements SFTP - the **Companion app** drives the headless sidecar `companion\fms-share-worker.exe` (prebuilt Go binary vendored at `payload/companion/` and **committed** to this repo via a narrow `.gitignore` negation - `!payload/companion/fms-share-worker.exe` + its `.sha256`, so a fresh clone **has** the Share feature; built from a separate `fms_companion` repo at `P:\windows\fms_companion` - **never build or hand-edit it from this repo**) over a named-pipe JSON control channel (`\\.\pipe\fms-companion`, schema-versioned request/response, one round-trip per connection). The worker owns the SFTP server, credentials, ed25519 host key, folder confinement, mDNS announce, UPnP/NAT-PMP port mapping, and the local-only connection stats (`stats.json`, `GetStatus.status.stats` / `ResetStats`). `WorkerProcess.IsAvailable()` returns `False` when the payload is missing and the UI degrades gracefully ("unavailable") - the normal state on a dev machine that hasn't fetched the payload.
- **Never regenerate or touch the worker's data dir** (`%LOCALAPPDATA%\FastMediaSorterCompanion\`) from VB - the host key is TOFU-pinned by paired phones; deleting it breaks every paired device.
- The `.fmscfg` export JSON and its QR PNG are built **on the LITE side** by `ShareConfigBuilder`, not via the worker's own `ExportConfig` - only that lets LITE advertise a manually-forwarded router port or schema-v2 per-root params (destination/writable folders, media-type filters, PIN, slideshow interval - see `ShareRootParams`).
- **Multi-path export (S1006/S1013/S1014, 2026-07 - all additive, still `schemaVersion` 1):** `accessPaths` is ordered `lan` -> `ipv6` -> `portforward` and the Android side **races all entries** (never trusts `[0]`). `lan` comes from `reach.LanAddress` else the hardened `NetworkInfo.LocalIPv4()` - a scored adapter pick (gateway-in-subnet > private > de-prioritize virtual/VPN > 192.168/10 tie-break) that never drops a real LAN NIC behind a VPN / virtual adapter / IPv6-only-gateway (the 2026-07 "LAN dropped from export" field bug). `ipv6` + reachability facts come from the worker: `reach.Ipv6Address`, and `ExternalPortChecked`/`ExternalPortOpen` (an **external connect-back via check-host.net** that honestly confirms a port-forward actually answers from outside - an IGD "success" alone can be a dead port). An optional localized `accessNote` (`ShareText.AccessNote`, respects the "LAN only" toggle) rides in the `.fmscfg` for the phone to show on connection failure. The worker announces `_sftp-fms._tcp` with TXT `fp=<hostKeyFingerprintSha256>`/`name`/`v=1` for the share's lifetime, so a phone on the same Wi-Fi rediscovers the PC by pin when the QR's LAN address went stale. Worker source lives in `P:\windows\fms_companion` (`internal/netaccess`, `internal/config`, `internal/ipc`) - edit it there, never the vendored binary.
- **Distribution**: both the Companion exe (`<app dir>\FastMediaSorterCompanion.exe`) **and** the worker (`<app dir>\companion\fms-share-worker.exe`) ship as siblings of the LITE exe in every channel - portable ZIP, Inno installer ([FastMediaSorter.iss](publishing/installer/FastMediaSorter.iss) `[Files]`: the Companion exe is a selectable `share` component; [publishing/installer/stop-companion.ps1](publishing/installer/stop-companion.ps1) kills a running worker/Companion before Setup/Uninstall replaces files), and Store MSIX (a second `<Application>` + `uap5:StartupTask` retargeted to Companion + `desktop2:windows.firewallRules`, since an HKCU Run write inside an MSIX container is silently virtualized away). `build.ps1` publishes Companion via `dotnet publish -c Release -r win-x64` (skip with `-SkipCompanion`) and deploys both siblings next to the LITE exe. No Windows service anywhere (blocked by Store policy).
- **Opt-in server features + firewall** ([ServerFeatures.vb](src/FastMediaSorterCompanion/Core/ServerFeatures.vb), [SPECIFICATION_SHARE_SERVER_OPTIN_INSTALL.md](docs/specifications/done/SPECIFICATION_SHARE_SERVER_OPTIN_INSTALL.md)): the bundled worker is dormant until the user opts in, because nothing ever opened the Windows Firewall port (the worker's own `AddFirewallRule()` is dead code from the discontinued standalone GUI, never on the `cmd/worker` path) - so an exported public address timed out from outside. Enabling adds a program-scoped inbound firewall allow for the worker exe, either via the installer checkbox (elevated install; hive-safe machine marker file) or the deferred in-app opt-in (one UAC prompt via `enable-share-server.ps1`; HKCU flag). This is the sole **owner-approved scoped exception** to Invariant #4's "no firewall/elevation" rule - never silent. The whole Share UI + the worker spawn (all inside Companion) are gated behind `ServerFeatures.IsEnabled()`.
- **Tray + close-to-tray lifecycle** ([TrayContext.vb](src/FastMediaSorterCompanion/TrayContext.vb)): the **Companion** is the tray-resident host - closing its window hides it to the tray while a share is active, keeping the worker and its controls reachable, and it only truly exits on explicit Quit or once sharing stops. LITE itself no longer has any close-to-tray behavior (that was removed with the migration); closing LITE during an active share closes LITE immediately, leaving Companion's tray icon running.

## Code Style & Constraints

**VB.NET Strict Mode** - All modules enforce:
```vb
Option Explicit On    ' All variables must be declared
Option Strict On      ' No implicit type conversions
Option Compare Binary ' Case-sensitive string comparison
Option Infer On       ' Allow type inference where possible
```

**File Organization**:
- `.vb` files are code-behind; `.Designer.vb` files are auto-generated (don't edit manually)
- Form classes inherit from `System.Windows.Forms.Form`
- Modules are for shared utilities and P/Invoke declarations
- `Main_Form` is one logical class spread across multiple `Partial Class Main_Form` files (`Main_Form.*.vb`). Fields/methods are shared across all of them - put a change in the file matching its concern, and watch for name collisions across partials.
- **Every `src/*.vb` file compiles into BOTH viewer exes** (the modern project links `..\**\*.vb`). Platform divergence goes behind `#If NETFRAMEWORK` / `#If Not NETFRAMEWORK`, never into project file lists - and a change to shared code must make sense on both runtimes. See "Two builds, one source tree".
- Build treats a fixed set of VB warnings as errors (`WarningsAsErrors`, kept identical in both viewer projects: 41999, 42016-42022, 42032, 42036 - mostly implicit-conversion and unused/return-path warnings), so these will fail the build, not just warn.

**Keyboard Shortcuts** - Most features driven by hotkeys, not menus:
- Stored in app settings (persisted to registry/config)
- Hardcoded hotkey array in Common_Module for folder shortcuts
- Inspect Main_Form keyboard event handlers for the full mapping
- **Video track keys are the modern build only** (`Main_Form.VideoTracks.vb`): **A** cycles the audio track, **V** the subtitles, and a "Tracks" button appears in the toolbar **only when the file offers a choice** (via `SetToolbarItemHidden`, the same mechanism the image-only translate buttons use). Modern-only for a real reason: on net48 a video goes to the IE WebBrowser first and only reaches LibVLC if IE refuses it, so the same control would work for an MKV and silently do nothing for an MP4. VLC's own audio-track key is `B`, which is already "previous file" here - hence `A`. The choice is remembered **by ISO language code**, not by id (per-file) or name (VLC returns composites like `Russian - [Russian]` that only match within one release); `player.Media.Tracks` keeps a clean `Language` field even after the `Media` object is disposed. Note `AudioTrackDescription`/`SpuDescription` always include a `Disable` entry with **id -1** - count real tracks, not `Length`.
- **Zoom keys are the modern build only** (`Main_Form.Zoom.vb` + `ZoomMath.vb` are whole-file `#If Not NETFRAMEWORK`): the **grey** NumPad block - `+`/`-` zoom at the cursor, `/` fits, `*` is 100 %. Only the grey block, because every `Ctrl` combo is already taken and NumPad `0..9` are the sort hotkeys. The first-run help gets its zoom line from `ZoomHelpLine()`, which returns `""` on net48 so the x86 viewer never advertises keys it does not have.

**UI Threading**:
- Image/video loading happens on background threads to avoid UI freeze
- Use `Invoke()` or `BeginInvoke()` when updating UI controls from worker threads
- LibVLC video playback is asynchronous; use `MediaPlayer.Play()` callbacks

**File Locking**:
- `LoadImageWithStream()` keeps the MemoryStream open to allow Windows to release the file handle
- Disposed explicitly when image is no longer needed
- Critical for fast file operations in a media sorter

## Testing & Validation

No automated test suite. Validation is manual:
1. **Build**: `.\build.ps1` - confirms both viewers compile (a shared-code change can break the *other* exe; `msbuild` alone never proves the mainline builds)
2. **Run**: Open the built `.exe` and exercise features: load folders, navigate files, test slideshow, verify video playback. **Exercise a media change in both exes** when it touches a seam (video, image decode, drag-drop, file ops). The Share Manager (the separate Companion app, launched from LITE's folder right-click or the Settings "Files and system" button) needs both `FastMediaSorterCompanion.exe` built and `payload/companion/fms-share-worker.exe` present (committed to the repo via a `.gitignore` negation - see "Android Folder Share" below) to do more than show "unavailable"
3. **Code analysis**: Visual Studio's built-in analyzer (enabled in Debug config: `<RunCodeAnalysis>true</RunCodeAnalysis>`)

## Common Development Tasks

### Adding a New File Operation
1. Add function to [FileManager.vb](src/FileManager.vb)
2. Call from Main_Form event handler (e.g., button click, keyboard shortcut)
3. Update UI state (enable/disable buttons, refresh file list)
4. Test with actual files in a temp folder

### Tuning the Perspective Background
1. Adjust constants in Main_Form.vb top (e.g., `percent_of_color_deviation`, `step_size_while_color_Search`)
2. Trigger a UI resize or image reload to see effect
3. Monitor `Debug.WriteLine()` output for timing data

### Supporting a New Media Format
1. Add extension to `Image_File_Extensions` or `video_File_Extensions` in Main_Form.vb
2. Test playback in **both** exes: modern always goes to LibVLC; on net48 the WebBrowser tries first and LibVLC picks up what it can't play. A new *image* format belongs behind the `IImageDecoder` seam ([src/Imaging/](src/Imaging)), not in a new `FileManager` branch.
3. Verify no memory leaks (dispose Image/Bitmap, MemoryStream)

## Environment Notes

- Support matrix: the **mainline x64 exe** covers Windows 10 1607+ / 11 / Server 2016+; the **x86 exe** covers Windows 7/8.1 and 32-bit Windows. Developed primarily on Windows 11.
- Executables built to `bin/Release/FastMediaSorter_LITE.exe` (mainline) and `bin/Release/FastMediaSorter_x86.exe` (fallback) - `bin/Release` is the distribution shape, both exes plus their shared library trees
- Settings/state persisted to Windows registry (`SZA\FastMediaSorter` - one hive for both exes)
- Single-instance enforced via app mutex (`app_Mutex_Name = "FastMediaSorterSingleInstanceMutex"`) - one mutex across both exes; forwarding searches both process names
