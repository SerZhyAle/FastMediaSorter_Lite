# Provider layer (SFTP/SMB resources) and .fd-sec secure containers

> Area rules for the paths above (auto-loaded). Index and the always-on rules: CLAUDE.md.

**[src/Resources/](../../src/Resources)** - the provider layer, modern-only (whole-file `#If Not NETFRAMEWORK`), spec `006_SPECIFICATION_FILESYSTEM_PROVIDER_LAYER_DOTNET10.md`. Built on the archive decision (`imaging-icons-archives.md`): **no virtual file system** - a remote file gets a real path in `%LOCALAPPDATA%\SZA\FastMediaSorter\remote-cache\<pid>-<token>\` and is fetched there before anything looks at it.
- **A plain folder is still a plain folder and must stay invisible to all of this**: `LocalProvider.ListEntries` IS the old `EnumerateConfiguredFiles` scan, moved (net48 keeps the original function), nothing local is ever materialised, and `ResourceRouting` - which `FileManager`'s copy/move/delete/rename ask first - returns False on its first line unless an open resource that materialises owns a path.
- **`ResourceBlocksFileOperations(verb)` is the ONE refusal point** for archives and for resources whose capabilities lack a verb - do not add a second.
- **Providers**: `SftpProvider` (SSH.NET - the only file that names the library; every verb is classified into the failure classes of `ResourceFailure` inside it, and a refusal - wrong credential, key not the pin, trust prompt answered No - is never retried by its reconnect ladder) and `SmbProvider` over `SmbConnectionLease` (`WNetAddConnection2` without a persistent drive; error 1219 is a typed refusal). `ProviderCapabilities` are plain booleans, so no UI asks "is this SFTP?".
- **`ResourceConnect`** is the one place a descriptor and a credential become a connected provider; the trust prompt arrives as a delegate, so no form is in it. `ResourcePins`: an accepted key is persisted BEFORE authentication, never over a different pin. `ResourceImport` (a `.fmscfg` plan into descriptors): a changed pin is taken only on an explicit yes, and a PIN-locked root refuses the WHOLE file (interim).
- **Secrets and locators**: a password is stored only through `ResourceCommit` (DPAPI blob under a handle; the registry JSON holds the handle) or kept in memory for the run when "Remember" is off; the descriptor carries a fingerprint, never a secret. A locator `sftp://user@host:port/path` is what `PersistableFolderPath()` writes, never the cache. The viewer's side is [Main_Form.ResourceOpen.vb](../../src/Main_Form.ResourceOpen.vb): one status sentence per failure class via `ResourceMessages`.
- **A slot may name a resource folder** (spec `007` section 4.2): `Hardkeys_to_move_mediafile` holds `sftp://..` and [RemoteSlots.vb](../../src/Resources/RemoteSlots.vb) owns it - `SlotPaths` glues/splits a folder and a name for a local path AND a locator (never `folder & "\" & name`), `RemoteSlotPolicy` holds the verdicts and the 7 s remote probe bound, `RemoteSlotConnections` keeps one connection per resource for the run, separate from the open resource's session. **A slot never asks the user anything**: the password prompt and the refusals (unknown server, unpinned key, read-only resource) happen in the gate on the UI thread (`RemoteSlotReadyToProbe` in Main_Form.SlotHealth.vb); a typed password is stored only after a connection proved it; the trust question is never asked from a slot. A file of an open resource goes into a slot under `TransferNameOf` (the entry's real name, never the cache's `00042_` name).
- **A move OUT of SFTP** (so also the undo of a move into a server slot) is a **checked ordinary move** (owner decision, ticket 221, replacing the blanket `CopyOnly` of the 100 section 15.6.3 rule): a writable SFTP provider advertises `SupportsCheckedSourceDelete`, which is NOT `SupportsStableSourceDelete` - standard SFTP has no atomic conditional delete and nothing here claims one. `TransferExecutor.DeleteSource` removes the source only after the destination is verified, re-stats it first (a changed source stays: `CopyOnly` / `SourceChanged`), re-checks cancellation after that stat, never repeats a remove, and reports `Completed` only when a final stat says the source is missing (an unanswerable stat is `Indeterminate`); a refused, changed or cancelled removal keeps both copies and says which. `ResourcePolicy` masks the capability on read-only and PIN-locked roots. The undo of a COPY into a server slot still needs `SupportsStableSourceDelete` and is refused by name.
- **Deleting a file of a resource is permanent and never goes through the display copy's disk**: `ResourceRouting.CaptureDelete` leases the session and the original's canonical path BEFORE the prompt (a session that closed cancels, it never falls back to the cache file), `DeletePolicy.DecideForProvider` reads the provider's capabilities before it probes a Windows volume, and `ResourceDeleteTarget.Execute` deletes once, confirms absence by stat and drops the cache entry only then (`ResourceDeleteException.Unverified` when the stat cannot answer). There is no SFTP Recycle Bin setting; the global one governs local paths only.
- **Cache and transfer**: `ResourceSession` is one open at a time and releases media before its directory is deleted; `RemoteCacheStore` never evicts the file on screen or its neighbours; `ResourceTransfer` writes `.fms-part` and verifies size before a source may go.
- **Live proof** is hand-run, never part of a default run: `tests/Integration/SftpConsumerLive.ps1` (with `tests/Integration/rwsftp`, a writable in-memory pkg/sftp server, for the slot write path).

**[src/Secure/](../../src/Secure)** - `.fd-sec` secure containers, modern-only (whole-file `#If Not NETFRAMEWORK`), reader half only - spec `026_SPECIFICATION_SECURE_CONTAINER_FD_SEC_DOTNET10.md`, against contracts `FDSEC-FORMAT` and `FDSEC-BEHAVIOUR`. A container is one ordinary file holding another file's bytes, its true name and its timestamps behind a credential, and carrying **no marker at all** - so nothing but the credential can tell it from noise, and **there is no dispatch by looking**: the only screen before the password is the length rule (`FdSecScreen`), and a file that passes it still says nothing.
- **The boundary is one sentence: no decrypted byte ever reaches the disk.** Not a temporary folder, not the decode cache, not the OCR cache, not a log. That is the opposite of the archive answer, deliberately (owner decision): an archive entry is not a secret. `FdSecStream` makes it cheap - the payload is independently sealed chunks at fixed offsets, so `Seek` is arithmetic and a video plays through `LibVLCSharp`'s `StreamMediaInput` with the decrypting stream AS the media input. Everything in `Main_Form.Secure.vb`'s refusals follows from it: the editor and "replace with video" are hidden, the external-player fallback and the browser-translate hand-off are refused (both pass a **path** to another program), and the decode and OCR **disk** caches are bypassed in both directions.
- **The three outcome classes never merge** (`FdSecOutcome`, mapped by `SecureMessages.ForOutcome`). *Wrong credential / not a container / tampering* is ONE class carrying three readings, because a wrong key and a flipped byte fail an AEAD tag identically - a security property, not a gap. *Damaged* never blames the password; *unsupported* is refused by name and never called damage. `FdSecRuleTests` walks the enum and fails if two classes ever share a sentence.
- **Conformance is decided by the catalog's vectors, never by reading the code.** They are vendored into `tests/Lite.Tests/TestData/fdsec-vectors/` beside a `PROVENANCE.txt` whose SHA-256s the suite asserts first; a one-byte deviation yields a reader that is self-consistent and opens nothing anyone else made, and each of the seven porting mistakes of `FDSEC-BEHAVIOUR` section 13.1 has a test. **The KDF profile is not ours to tune**: it belongs to the format version, and the lowered one is a test-only parameter no shipped path passes.
- **`src/Secure/` has no product dependencies** - it never logs, never shows a dialog, never reads a setting. The viewer's side is [Main_Form.Secure.vb](../../src/Main_Form.Secure.vb) plus [Secure_Password_Form.vb](../../src/Secure_Password_Form.vb); the credential lives in memory for the process only: never the registry, never a file, never the DPAPI store the OCR keys use.
- **The check runs OFF the UI thread** (124 UX-213): `FdSecContainer.OpenFile` (Argon2id, and for a picture the whole decrypt) is called only from `OpenSecureContainerOffThread`, the verify action and the prefetch - `SecureOpenOffThreadTests` reads the source and fails on a new call site. A stale attempt (its `secure_Open_Active` number, `media_Generation` or current file moved; another attempt, forgetting the password and closing also take it away) is *superseded*: it releases what it opened and draws nothing. `secure_Prompting` covers only the password WINDOW, never the check.
- **There is no user-facing writer (owner decision): do not fold a packer in beside the display path.** The read-back proof, the temporary file and the disposition of the original (`FDSEC-BEHAVIOUR` section 6) decide whether the feature destroys data, and belong to their own ticket. **One narrow exception (spec 242, Q242-1, 2026-10-17):** `src/Secure/FdSecWriter.vb` writes suite 1 for the **ephemeral animation-video store only** - input is a finished in-memory plaintext, the credential is a per-run random one held in memory, and it has **no notion of an original file** (no source path, no delete, no disposition). Do not add a caller that packs a user file; that stays its own ticket.
- The streaming reader is a **recorded deviation**: it authenticates every byte it returns but cannot verify the sealed digest of a chunk it never read, so the viewer never claims a container is intact and offers an explicit "verify this container" instead. An amendment to propose, not taken locally - see [docs/contracts/FDSEC.md](../../docs/contracts/FDSEC.md).
