# Share Manager (Companion), Go worker, exchange server

> Area rules for the paths above (auto-loaded). Index and the always-on rules: CLAUDE.md.

- **[src/FastMediaSorterCompanion/](../../src/FastMediaSorterCompanion)** - the standalone Share Manager (`ProductNames.ShareManager`): `net10.0-windows`, own `.vbproj` in `FastMediaSorter.sln`, published self-contained single-file via `dotnet publish`. It owns *everything* about sharing; the viewer is only a launcher.
  - `Program.vb` - `FastMediaSorterCompanionSingleInstanceMutex` single-instance + `WM_COPYDATA` receiver (mirrors the viewer's `Application_Events.vb`, roles reversed); `--tray` = silent logon-autostart launch, a folder arg = open and preselect it.
  - `Core/*` - the worker-driving layer: `WorkerIpc`/`WorkerProcess` (named-pipe JSON client + spawn/stop, `System.Text.Json`), `ShareController`, `ShareConfigBuilder`, `ShareRootParams`, `ServerFeatures` (the **opt-in gate**), `AutostartManager` (targets Companion, migrates a stale viewer Run value on upgrade), `CompanionGlobals` (reads the **same** `SZA\FastMediaSorter` UI-language value the viewer writes, so the language never desyncs).
  - **The main window is compact and split into four partials** (`SPECIFICATION_SHARE_MANAGER_COMPACT_WINDOW.md`): `MainWindow.vb`, `.Layout.vb`, `.Access.vb` (status -> UI, folded summaries), `.Folders.vb` (share list + server ops) - edit the file matching the concern. What is read once during setup lives in three `CollapsibleSection`s; what is interesting only once lives in destination-scoped `Share_Settings_Form` windows coordinated by `MainWindow.Settings.vb` (vertical navigation, `Share_Settings_Form.Navigation.vb`, `WINDOWS-UI` section 2; per-page anchors and the last page persist through `Share_SettingsContext`). The SFTP window owns Network and Hosting; the local exchange window owns server administration; manager settings owns common preferences, client account/publishing and schedules. The shared shell builds only its destination's controls. Reciprocal links and tray routes reuse one modeless window per destination; typed notifications refresh state. The Hosting page owns the former console's operations. Settings exit through native Close or Escape with no bottom footer; the only in-settings support-bundle command is the About button (owner decision). Two rules to keep: a **folded section is live** - its one-line summary is filled by the same `ApplyStatusToUi`/10 s tick that fills the body, never by a second code path - and the folder list is the **only** growing element, its `Absolute` row height recomputed from the sections' PREFERRED size (a `TableLayoutPanel` with no Percent row gives leftovers to its last row, so `.Height` there over-reports by ~150 px). Window size/position and open sections persist in `SZA\FastMediaSorter` as `Share_Window*` + one CSV `Share_ExpandedSections`. The SFTP password is masked (`PasswordDisplay`) while its copy button still copies the real value.
- **[ServerFeatures.vb](../../src/FastMediaSorterCompanion/Core/ServerFeatures.vb)** - the opt-in gate (`SPECIFICATION_SHARE_SERVER_OPTIN_INSTALL.md`). Exposing folders over SFTP + a firewall hole is a deliberate admin-level action, so the bundled worker is dormant and the whole Share UI + worker spawn (all inside Companion) are gated behind `ServerFeatures.IsEnabled()` = **machine marker file** `<app dir>\companion\server-features.enabled` (written by the elevated installer) **OR** HKCU `Share_ServerFeaturesEnabled=1` (deferred runtime opt-in) **OR** packaged (Store). Nothing else ever opens the Windows Firewall port (the worker's own `AddFirewallRule()` is dead code, never on the `cmd/worker` path), so without the gate an exported public address times out from outside. `EnableViaElevation()` is the single privileged step - a program-scoped inbound firewall allow for the worker exe - via one UAC prompt ([publishing/installer/enable-share-server.ps1](../../publishing/installer/enable-share-server.ps1), installed next to the exe by the Inno script, called via `ShellExecute("runas")`; a direct `netsh` fallback), then records the HKCU flag. This is the sole **owner-approved scoped exception** to "no firewall/elevation" - never silent.
- **Scheduled file operations are a Share Manager feature and nothing else** (ticket 222, `docs/specifications/done/222_SPECIFICATION_SCHEDULED_FILE_OPERATIONS.md`): *installed with the `share` component, run by the Share Manager while it runs in the signed-in session, managed from its settings page "Scheduled file operations" and its tray menu - never from the viewer, never in the x86 fallback, never behind `ServerFeatures`, never hosted by the Server edition's service.* The engine is [Core/Scheduled/](../../src/FastMediaSorterCompanion/Core/Scheduled): `ScheduleMath` is the one next-slot function for the editor's label, the arming and the missed-run path (fixed grid, no drift); `ScheduledConditions` holds the validation shared by save and run; `ScheduledStore` keeps one JSON file per operation and a run patches only its own state into it; `ScheduledExecutor` is unattended - it asks nothing, a wall stops a run once. **What it shares with the viewer is LINKED, not copied** (the group in `FastMediaSorterCompanion.vbproj`): `MediaKind`, `DeletePolicy`, `DeleteVolumeProbe`, `RecycleBinIo`/`RecycleBinIndex`, `FolderScan`/`PathFailure`, `FreeNameRule` and the whole `src/Resources/` provider layer with its checked `TransferExecutor` (ticket 221) and SSH.NET. Rules a change must keep: no exception text is stored or shown (a CODE and the file, composed into words at display time - `ScheduledFailure`/`ScheduledText`, the `NoExceptionTextReachesTheUser` gate; the journal holds codes, never sentences); a destructive step re-checks that the source is still the file that was listed; a delete never asks and always records the verdict; an archive deletes originals only after the read-back; the viewer's tree names none of the engine's types (`ScheduledSurfaceTests`). The viewer's only part is `Main_Form.FolderMenu.vb`'s "Schedule an operation for this folder.." item and `ActivateScheduleEntryPoint` in `Main_Form.ShareLauncher.vb` (`::fms-schedule::` + folder, sent only to a receiver at or above `ShareActivationPolicy.MinScheduleVersion`).
- **The viewer's side is tiny**: [Main_Form.ShareLauncher.vb](../../src/Main_Form.ShareLauncher.vb) (folder-box right-click "Share this folder..") and [Table_Form.ShareLauncher.vb](../../src/Table_Form.ShareLauncher.vb) ("Share Manager.." button in Settings) both call `ActivateShareEntryPoint()`, which finds `FastMediaSorterCompanion.exe` next to the viewer exe and either wakes the running instance (mutex found -> `WM_COPYDATA` the current folder to *all* its top-level windows) or cold-starts it. The viewer knows **nothing** about the worker, the pipe, `ServerFeatures` or the opt-in gate (invariant 8 of the Companion migration spec: `grep Companion src/*.vb` should surface only the launcher and the unrelated OCR-translate "companion"). Missing exe -> a clear "reinstall" message, never a silent no-op.

### Android Folder Share (Companion app + Go worker)

Two tiers: the standalone .NET 10 Companion drives a **bundled headless Go worker** (`companion\fms-share-worker.exe`); the viewer is only a launcher. Specs: `SPECIFICATION_SHARE_COMPANION_APP.md` (viewer -> Companion split), `SPECIFICATION_SHARE_STATS_AND_TRAY_HUB.md` (connection stats + tray hub), `SPECIFICATION_ANDROID_FOLDER_SHARE.md` (worker IPC protocol / `.fmscfg` schema), `SPECIFICATION_QR_IMPORT_ANDROID.md` (frozen wire contract, Android side).
- **Architecture in one sentence**: neither the viewer nor Companion implements SFTP - the Companion drives the headless sidecar `companion\fms-share-worker.exe` (prebuilt Go binary vendored at `payload/companion/` and **committed** via a narrow `.gitignore` negation - `!payload/companion/fms-share-worker.exe` + its `.sha256`, so a fresh clone **has** the Share feature; built from the separate `fms_companion` repo at `P:\windows\fms_companion` - **never build or hand-edit it from this repo**) over a named-pipe JSON control channel (`\\.\pipe\fms-companion`, schema-versioned request/response, one round-trip per connection; contract `WORKER-IPC`). The host **reads `ok`** on every answer; a **version refusal is shown, never swallowed** (`WorkerVersionRefusedException`, turned into a typed result by `WorkerProcess.Exchange` - the one exchange point); **nothing is spawned after any answer**: a worker that answered owns the pipe. The worker owns the SFTP server, credentials, ed25519 host key, folder confinement, mDNS announce, UPnP/NAT-PMP port mapping and the local-only connection stats (`stats.json`, `GetStatus.status.stats` / `ResetStats`). `WorkerProcess.IsAvailable()` is `False` when the payload is missing and the UI degrades to "unavailable".
- **Never regenerate or touch the worker's data dir** (`%LOCALAPPDATA%\FastMediaSorterCompanion\`) from VB - the host key is TOFU-pinned by paired phones; deleting it breaks every paired device.
- The `.fmscfg` JSON and its QR PNG are built on the **host side** (the Companion's `ShareConfigBuilder`), not via the worker's own `ExportConfig` - only that lets the host advertise a manually-forwarded router port or schema-v2 per-root params (destination/writable folders, media-type filters, PIN, slideshow interval - `ShareRootParams`).
- **Multi-path export** (all additive, `schemaVersion` still 1): `accessPaths` is ordered `lan` -> `ipv6` -> `portforward` and the Android side **races all entries** (never trusts `[0]`). `lan` comes from `reach.LanAddress` else `NetworkInfo.LocalIPv4()` - a scored adapter pick that never drops a real LAN NIC behind a VPN / virtual adapter / IPv6-only gateway. `ipv6` comes from the worker's `reach.Ipv6Address`; `ExternalPortChecked`/`ExternalPortOpen` are an **external connect-back via check-host.net** (an IGD "success" alone can be a dead port). An optional localized `accessNote` (`ShareText.AccessNote`, respects the "LAN only" toggle) rides in the `.fmscfg` for the phone to show on connection failure. The worker announces `_sftp-fms._tcp` with TXT `fp=<hostKeyFingerprintSha256>`/`name`/`v=1` for the share's lifetime, so a phone on the same Wi-Fi rediscovers the PC by pin when the QR's LAN address went stale. Worker source: `P:\windows\fms_companion` (`internal/netaccess`, `internal/config`, `internal/ipc`).
- **Distribution**: the Companion exe (`<app dir>\FastMediaSorterCompanion.exe`) **and** the worker (`<app dir>\companion\fms-share-worker.exe`) ship as siblings of the viewer exe in every channel.
  - Inno ([FastMediaSorter.iss](../../publishing/installer/FastMediaSorter.iss) `[Files]`): the Companion exe is the selectable `share` component. [stop-companion.ps1](../../publishing/installer/stop-companion.ps1) kills a running worker/Companion before Setup/Uninstall replaces files and is the ONLY mechanism for it, so **never add `AppMutex=FastMediaSorterCompanionSingleInstanceMutex`** to either `.iss`: Inno checks a mutex before `PrepareToInstall`, and the Share Manager sits in the tray from logon, so a silent install (`/SUPPRESSMSGBOXES`, i.e. winget) has the "close it" prompt answered Cancel and aborts with exit code 1 before a single file is touched - it broke every `winget upgrade` of the Server edition.
  - Store MSIX: a second `<Application>` + `uap5:StartupTask` retargeted to Companion + `desktop2:windows.firewallRules`, since an HKCU Run write inside an MSIX container is silently virtualized away.
  - **The Media Exchange Server (`exchange\`, ticket 141) is a third, optional tree** - exactly five files, staged by [tools/Stage-ExchangePayload.ps1](../../tools/Stage-ExchangePayload.ps1) (the only place that names them): `exchange\fms-exchange-server.exe` + `.sha256` (built from `exchange-server/`, never vendored), `enable-exchange-server.ps1`, `install-exchange-service.ps1`, `README.txt`. User installer: the `share\exchange` component, a child of `share` (specification 251 T-1: Setup ticks the Share Manager with it, also for `/COMPONENTS=..share\exchange`; no `Types`, so unchecked even in `full`, which silent winget installs take; `MinVersion: 10.0.14393`); Server installer: the same plus the unchecked `exchangeservice` task that registers the Windows service; the portable ZIP carries the tree; the **Store MSIX never does** (an exclusion list and a post-stage assertion in `build-msix.ps1`). **Two exclusions are permanent and independent of the gate**: the `exchange\*` entry in the `core` wildcard's `Excludes` (else the unchecked component is written by the wildcard) and the generic bin\Release copy loops skipping `exchange\*` (the tree reaches a stage only through the staging script).
  - **THE SHIPPING GATE (owner rule, 133 section 8 - nothing from the exchange module reaches a RELEASED package before rung 2 freezes the wire): everything above is opt-in and OFF by default.** `-IncludeExchange` on `Build-Installer.ps1`, `Build-ServerInstaller.ps1` and `Build-OfflineRelease.ps1`; `INCLUDE_EXCHANGE: 'false'` at the top of `release.yml` (one line to flip; it also gates the SHA-pinned `actions/setup-go`, `go test ./...` and `exchange-server\build.ps1` steps). The repo-root `build.ps1` is a local build, not a packager: it includes the server in every run unless `-SkipExchange` is given, forwards the switch to both installer builds, and fails without Go instead of skipping. Gate shut: no `exchange\` folder in any stage (a stage that has one fails the build) and ISCC is called with `/DNoExchange`, which compiles the component, its `[Files]`, messages, task and uninstall code out of both `.iss` files (`#ifndef NoExchange`); a hand compile of an `.iss` without that define expects the tree to exist. Gate open: the build throws when the binary or its sidecar is missing - a package claiming a component it lacks is worse than a failed build.
  - `stop-companion.ps1` also stops `fms-exchange-server.exe`, but only a copy that runs from `<app dir>\exchange\`, never a Windows service instance.
- **The listen port is GUARANTEED, and it is a setting, not a mode** (`015_SPECIFICATION_SHARE_MANUAL_PORT.md`, `schemaVersion` still 1). The number is printed in every QR/`.fmscfg` and typed into router forwarding rules, so it moves when the owner moves it and at no other time. Owner decision: no "Fixed port" checkbox (a toggle implies the port otherwise drifts by design) and **no auto mode and no fallback anywhere** - `settings.json` carries `port` and no `portFixed`; HKCU `Share_ListenPort` (0 = "not recorded here", never "let it float") rides the **existing** `SetNetworkPolicy` request as a nullable `port` where 0 and absent both mean *unchanged*. Rules: the OS chooses **exactly once**, on the first ever start, and that choice is persisted immediately and is then the port; a bind is **retried ~2 s** (`portRetryAttempts`) - what used to move the port was our own previous listener during a restart; a port that still cannot be bound leaves the server **down** with `Status.LastStartError` (additive, cleared by a successful start; the boot-restore path has no requester to answer). `Status.DesiredPort` reports the number **while down**, which is when the UI has to show it. `ShareController.PortWarning` turns that - plus `Status.PortSupported=False`, which identifies a **stale worker** rather than guessing - into the one line the main window's state row and the settings note show. **Never `SO_REUSEADDR`** to help a bind, nor in `FreePortFinder`'s probe: on Windows it lets an unrelated process steal a live one. The firewall rule is program-scoped, so a port change needs no elevation and must never acquire a reason to.
- **Two hosts, one worker - User edition vs Server edition** (`SPECIFICATION_SHARE_SYSTEM_SERVICE.md`): the same `fms-share-worker.exe` runs either in the interactive session (the Share Manager starts it - the default) or as the Windows service **`FastMediaSorterCompanionSFTP`** (frozen name), which starts at boot and serves with nobody signed in. A packaging + host-mode distinction, **never a fork**: one SFTP implementation, one IPC schema, one `.fmscfg` format, one Android reconnect contract, one identity. The rules:
  - **The Server edition carries the viewer as an optional, UNTICKED component** (ticket 132): `tools/Stage-ServerViewerPayload.ps1` stages the User installer's Compact files from the User stage of the SAME version into `<server stage>\viewer\`, and `FastMediaSorterServer.iss` defines the component only when `viewer\FastMediaSorter_LITE.exe` exists (`#if FileExists`) - never a row with nothing behind it. The shipping packagers (`release.yml`, `Build-OfflineRelease.ps1`) pass `-Require`. The component has no `Types:` on purpose (a silent install never gets it), is disabled next to an installed User edition, and its shortcut is `Viewer - Fast Media Sorter & Sharing`, never the User edition's own shortcut name in the shared Start-menu group. Default payload, AppId, ARP name, directory, winget package and service name do not move. The site's three doors and the family sentence live in `tools/site-copy.json` and the hand-authored `index.html`/`server.html`.
  - **An optional Windows service is permitted ONLY for the Server edition** (Store policy blocks it elsewhere). It is never created by a Store install, by a default or silent User install, by a phone request, or by any IPC command - only by the elevated Server installer or by one visible UAC prompt from the Hosting console. Everything machine-affecting (register / repair / restart / remove / migrate / grant a folder to the service account / firewall) goes through the single auditable helper [publishing/installer/install-share-service.ps1](../../publishing/installer/install-share-service.ps1).
  - **The two never run concurrently, and the service wins.** `ServerFeatures.HostMode()` is authoritative (live SCM query + validation that the registration is ours). `WorkerProcess.EnsureRunning` connects instead of spawning whenever the service is registered *or* merely running, and `cmd/worker` in the worker repo refuses to start a foreground worker while the service is up - they would otherwise fight over the frozen pipe, the listen port and the host key.
  - **One state store.** Once `%ProgramData%\FastMediaSorterCompanion` exists, `sftpserver.DataDir()` prefers it over the per-user directory, so both hosts read and write the **same** shares/settings/stats/host key. The installer therefore grants the enrolled management user **Modify** (not read) on that directory - read-only would silently split the editions into two folder lists.
  - **The migration runs ONCE, and the machine store then wins.** The Server installer passes `/MIGRATEFROMUSER` on *every* install, so `migrate-to-server` also fires on ordinary upgrades; `Copy-State` is therefore called with `-OnlyWhenTargetIsFresh` and returns untouched the moment `%ProgramData%` already holds the identity. Without it every reinstall overwrote the LIVE state with a stale per-user snapshot (listen port, shares, credential, counters) while the host key matched and the install looked perfect. `migrate-to-user` deliberately does NOT pass the switch: there the machine store *is* the authority being handed back.
  - **The host key is never regenerated** on a migration, restart, update, reboot or mode change (`install-share-service.ps1` is where this repository holds `SHARE-SESSION` guarantee 3). Migration validates the fingerprint before and after the copy (`fms-share-worker.exe --inspect-datadir`) and aborts *before* the service is registered on any mismatch, because a new identity unpairs every phone.
  - **Session 0 changes the pipe DACL.** The worker's control-pipe ACL must not come from `os/user.Current()` when it runs as LocalService; the installer enrols the management SID(s) and the service passes them via `--manage-sid`.
  - Separate everything the channels correlate on: its own Inno `AppId`, ARP DisplayName, install dir, release asset (`..-server-setup.exe`, built by [tools/Build-ServerInstaller.ps1](../../tools/Build-ServerInstaller.ps1) and by `release.yml`) and its own winget package `SerZhyAle.FastMediaSorter.Server` ([publishing/winget/server/](../../publishing/winget/server)). **Store/MSIX stays User mode only.** Public page: [server.html](../../server.html).
- **Tray** ([TrayContext.vb](../../src/FastMediaSorterCompanion/TrayContext.vb)): the **Companion** is the tray-resident host - closing its window hides it to the tray while a share is active and it exits only on explicit Quit or once sharing stops. The viewer has no close-to-tray: closing it during an active share closes it immediately, leaving the Companion's tray icon running.
- **Questions in the Share Manager go through `ManagerBox.Show`** ([Core/ManagerBox.vb](../../src/FastMediaSorterCompanion/Core/ManagerBox.vb), ticket 243 T-12b), never the stock `MessageBox.Show`, for `OKCancel` / `YesNo` / `YesNoCancel` (BUTTONS 2.0 section 1: no system dialog solely to evade a required product-owned component). It has the `MessageBox.Show` call shapes, so a call site changes by its class name; it shows the viewer's `Ask_Dialog` (linked, with `AskModel.vb` and `ViewerBoxMapping.vb`, in the group of `DialogButtonRow` - `Ask_Dialog` needs only the forwarding `DialogLayout` of `Core/DpiLayout.vb`; the viewer's `AskDialogs` / `DialogLayer` are NOT linked) modally over the owner, themed (`ThemeService.Attach`), cancel-first in the language's direction, with the call site's default answer kept. Escape and the close box answer the last answer of the set (Cancel; No of Yes/No - a system Yes/No box had no Escape at all, so every Yes/No site must treat No as the safe decline, and the sites checked at T-12b all do). An owner pinned topmost (or owned by one) makes the question topmost too; a question with no owner (the tray's "another program asks to open a folder") is centred, topmost and has a taskbar button; a caller on another thread gets the window made on its owner's thread. `OK` alone, `RetryCancel` and `AbortRetryIgnore` stay the stock box. `ManagerBoxTests` reads every source the Companion compiles (its own and its links) and fails on a question set passed to `MessageBox.Show`.
- **The Manager's collapsible group headers draw the shared `GroupMarker` triangle** (ticket 243 T-11c-a, `COLLAPSIBLE-GROUP` 1.1 section 3): both header kinds - `SettingsGroupCard`'s `CardHeader` and `CollapsibleSection`'s `SectionHeader` (main-window sections and the settings pages' sections) - fill the viewer's state triangle from [src/Chrome/GroupMarker.vb](../../src/Chrome/GroupMarker.vb) (linked, whole-file `#If Not NETFRAMEWORK`; the viewer's `SettingsCollapsibleGroup` takes its shape from the same file): right when collapsed, down when open, left when collapsed under RTL, in the caption's own ink, cell = tier 16 scaled by the window (`GroupMarker.CellPx(DeviceDpi / 96)`), 8 logical px before the caption, centred on the FIRST caption line (`FirstLineCentre`), never a `collapsibleSection`/`collapsibleSectionOpen` chevron (those IconMap meanings stay for the nav chevrons). The caption wraps in the rest of the bar and is never ellipsized; only `SectionHeader`'s right-aligned summary ellipsizes. Test seam: `SetMarkerScale(factor)` on both headers; held by `GroupMarkerHeaderTests` (pixels of the real controls, light and dark palette, ltr/rtl, 100 and 175 percent) and `SectionLayoutTests` (title budget).

- Settings navigation and close/draft/context behavior: [SHARING_SETTINGS_WINDOWS](../../docs/guides/SHARING_SETTINGS_WINDOWS.md). `SettingsRoutes` maps legacy page requests. Keep remote-client access independent of both local server payloads; `TrayContext.ShowSettingsWindow` creates an owner without running the main window's worker-start flow. Destination context keys seed from, and retain, the legacy combined context. Preference writers reload before saving; no stale full-object writes from another open editor.
